## Java 未通过项的归因

`IamS1QueryServiceImplTest` 的六项错误都发生在 `buildPythonRequest`，异常为“本任务业务知识引用并发变化，请重新发起”。当前生产代码要求业务引用冻结 CAS 更新成功，或重读后已存在相同引用；相应测试未模拟该新增更新路径，Mockito 默认返回 0，重读的对象仍没有被冻结的业务引用。

另一项失败为 `missingAttemptCompletionCannotPersistOrExposePythonPayloadThroughReadPathsOrSse`：原断言期待 mapper 更新一次，实际包含业务引用冻结与失败处理两次更新。

这些结果表明旧夹具和交互断言需要适配新增合同，不构成七项线上故障的证明。修复时仍需保留真正 CAS 失败、引用已变化和无 PROTECTED 尝试的拒绝用例；本轮未改测试使其通过。

### 下游一致性核对

- 来源质量检查写入 SOURCE 问题并维护自己的结果/覆盖。语义复查写入 SEMANTIC 结果，语义高风险问题不直接污染来源评分或阻断快照发布；RAG/问数另有事实、来源与当前权限的资格判断。
- 可追溯性质量规则检查采集关系中的缺失外键或孤立表，不创建真实数据流。业务关系审核和质量问题处理不能直接改造成血缘事实。
- 当前 S1 完成路径保存受保护的 `iam_source_trace` 并调用审计，未调用 `LineageService.saveLineage`；全量生产 Java 搜索只找到该写入口的声明与实现，没有调用者。审计实现也没有转发血缘。旧血缘入口仍围绕 `columnDerivations`，而 S1 以 PROTECTED 尝试的 `sourceTrace` 为权威，适配应从真实来源合同出发。
- 旧桥接把 FROM 表指向 JOIN 表；JOIN 的 SQL 书写顺序本身不是数据派生方向。不能只补一个旧方法调用就宣称新问数血缘准确。查询使用关系、输出来源和真正的数据流应先区分，并验证方向、来源、去重、同源及失败隔离。
