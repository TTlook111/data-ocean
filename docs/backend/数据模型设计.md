# 数据模型设计

本页确定新版的实体归属、关键关系、版本和事务边界，作为模块物理设计的共同输入。依据为[产品方案](../product/产品方案.docx)、[服务职责](../architecture/服务职责与数据流.md)及各模块原型；不从旧库推导新模型。首批物理表见[人员与权限建表设计](iam/建表.sql)，后续模块的表名为设计定位，字段级 DDL 随对应模块设计落实，当前不执行建库或迁移。

## 数据归属与共用规则

- Java 是平台 MySQL 业务事实的唯一写入方。Python 通过受控接口提交成果，自行管理 Redis 检查点和 Milvus 产物；前端不接触内部存储。
- 单企业部署，不增加无需求的 tenant_id、多租户平台或跨数据源问数。各业务源、对象、任务和引用都有明确 source_id。
- 平台关系实体用 BIGINT 稳定主键，MySQL 生成；对外字符串。任务 request_id、命令 command_id 和领域事件 event_id 用 UUID；SSE 游标与领域事件 ID 分开，详见[契约](../architecture/接口与事件契约.md)。
- 当前可变记录保存 version，内容修订表以 `(主体编号,revision)` 唯一；已引用内容不原地覆盖。列表名称、角色名、表名和文件名均不能代替稳定身份。
- MySQL 使用 InnoDB、utf8mb4、UTC DATETIME(3)。首批 DDL 不使用 JSON 代替角色、成员、依赖、规则选择等核心关系。JSON 只存类型明确且需整体固定的差异、快照和有限结构；DTO 仍定义明确字段。
- 模块内核心关系使用外键 RESTRICT，禁止级联删除历史；跨模块引用由所属服务核验并按依赖检查清理，不借直接写其他模块 Mapper 绕过业务。跨模块引用必须有反向定位索引。
- 归档是保留身份的生命周期状态，不给所有表机械增加逻辑删除字段；可删除草稿与未引用附件由所属规则决定。保留期未确定前不运行自动清理，不将“暂不清理”表述为永久保留承诺。

| datasource | `ds_capability_check`、`ds_collection_task`、`ds_snapshot` | 分项能力检查固定配置修订；采集任务与成功快照分开，失败或取消不推进当前目录 |

| query | `qry_conversation`、`qry_message`、`qry_summary_revision` | 对话归用户；消息与摘要保留来源轮次，按当前权限过滤；thread_id 不复用对话或用户编号 |
| query | `qry_request`、`qry_intent_revision`、`qry_clarification`、`qry_budget` | 一轮请求一个源；明确时间锚点与意图修订；等待和活动预算分开；新问／重新查询创建新请求并关联原请求 |
| query | `qry_evidence_ref`、`qry_sql_candidate`、`qry_check`、`qry_execution` | 实际使用依据与候选引用分开；检查绑定 SQL、参数、意图、规则、依赖和版本；execution_id 防重复执行 |
| query | `qry_result`、`qry_answer_revision`、`qry_delivery`、`qry_usage_ref` | 限量结果、答案解释、已交付事实与全部依赖分开；解释失败或重试不重发 SQL、不改变原查询时间 |
| feedback | `fb_event`、`fb_current_rating`、`fb_issue`、`fb_issue_evidence`、`fb_task`、`fb_status_event` | 原始评价事件与当前摘要、事项与任务分开；真实根因经核实，不因点踩直接认定业务事实错误 |
| feedback | `fb_group`、`fb_group_member`、`fb_verification`、`fb_completion_notice` | 分组确认、复验和回告轮次分开；通知按事项完成轮次与接收人去重，说明结案不计修复解决 |
| model | `mdl_model`、`mdl_config_revision`、`mdl_credential_revision`、`mdl_node_assignment`、`mdl_embedding_identity`、`mdl_call` | 类型与接口格式分开；18 节点逐项配置；选择与生效分开，调用保存实际配置修订，不保存完整提示词 |
| audit | `audit_record` | 管理事实与必要差异，引用业务对象；每次批准一条记录合并审批及生效结果，普通接口不编辑删除 |
| dashboard | `dash_metric_definition`、`dash_aggregate`、`dash_reconciliation` | 初期优先来源模块明确统计查询；仅有真实性能需求才建汇总，标明口径、覆盖、事件时间和对账依据 |
| infrastructure | `sys_command`、`sys_outbox`、`sys_event_receipt` | 命令防重、业务同事务待通知和消费去重；不承载 AI 节点编排或替代业务记录 |

后续模块表组明确数据责任与拆分方向；不意味着这些表已建成或每张表都有字段级详细设计。进入对应模块实施前必须完成字段、约束、索引和访问模式核对。

## 四条主关联

1. 身份：用户 → 个人角色 → 功能使用权；管理角色 → 可授予操作。部门成员 → 部门配置 → 数据来源，申请 → 子项 → 决定 → 数据来源。使用权、授予权及源访问三条链不能合成角色的一个 JSON。
2. 知识：源对象／世代 → 结构修订 → 治理条目修订 → 文档修订 → 发布清单 → 片段／索引代次 → 生效绑定。当前暂停禁止独立核验，不放进不可变发布快照当作长期许可。
3. 问数：用户 → 对话 → 请求 → 意图／依据／SQL 候选／检查 → 数据库执行 → 结果 → 答案修订与交付。请求同时固定实际知识与模型绑定，恢复不改取最新版。
4. 反馈：具体答案修订 → 反馈事件 → 问题事项 → 治理或技术任务 → 实际修复及发布 → 复验 → 结案轮次与受控回告。说明结案、发送成功和业务修复不能合成一个完成标记。

## 必须拆开的状态

| 对象 | 独立状态维度 | 不能发生的覆盖 |
| --- | --- | --- |
| 用户 | 生命周期、待改密、认证版本、临时登录风险状态 | 重置密码不改角色或授权；恢复账号不恢复旧会话和旧任务 |
| 部门 | 生命周期、保留配置的待复核状态 | 恢复组织不自动启用已结束的数据来源 |
| 数据源 | 生命周期、采集开关、连接及分项能力结果 | 重连成功不等于采集、治理或知识恢复 |
| 治理 | 草稿／内容修订、确认、来源影响、当前禁止 | 已确认不等于已发布；疑点不自动变成已确认错误 |
| 知识 | 文档确认、候选构建、逐题结果、人工裁定、发布入口、暂停 | 构建成功不能直接发布；发布与回退不能自动解除暂停 |
| 模型 | 配置启停、连接测试、节点选择、匹配索引生效 | 测试失败不隐式停用，选择 Embedding 不立即切换生效索引 |
| 问数 | 派发、图阶段、请求终态、取消进度、实际执行、结果交付、解释 | 解释失败不覆盖已交付结果；HTTP 超时不等于 SQL 未执行 |
| 反馈 | 评价、事项、处理任务、验证、结案类型、通知 | 撤销评价不删除原事件，回告失败不改写结案结论 |

问数八种互斥终态编码定为 `RESULT_DELIVERED`、`PERMISSION_DENIED`、`OUT_OF_SCOPE`、`KNOWLEDGE_INSUFFICIENT`、`RESOURCE_EXCEEDED`、`TECHNICAL_FAILURE`、`USER_CANCELLED`、`WAIT_EXPIRED`，对应方案已有八种含义。解释状态为 NOT_STARTED/GENERATING/COMPLETED/FAILED/STOPPED；数据库执行至少区分 NOT_SUBMITTED/ACCEPTED/RUNNING/SUCCEEDED/FAILED/CANCELLED/UNKNOWN。具体动作允许的转换由 query 模块实现设计逐项定义。

## 事务与并发

| 场景 | 必须在同一 MySQL 事务内完成 | 事务外动作及核实 |
| --- | --- | --- |
| 首批身份、角色、部门变化 | 当前权威检查、版本 CAS、必要恢复途径检查、变更、审计、权限版本和 Outbox | 注销 Redis 会话、缓存失效及任务阻断；入口继续核权，不能等事件送达才失效 |
| 独立审批通过 | 申请与子项版本、办理责任、目标状态、规则、决定、来源、权限版本、单条合并审计和 Outbox | 回告与缓存刷新；失败不暴露已批准中间态 |
| 联合最后一项通过 | 锁定申请聚合，核对全部必要项仍匹配及账号／源／规则可用，提交本次决定与整组来源生效 | 先通过的决定保留历史；整组不得部分生效，批准归属仍分别保存 |
| 部门初始访问和调岗 | 新配置或成员关系、结束对应旧来源、新增合法来源、影响版本、审计和 Outbox | 重算受影响任务；不结束其他部门及申请来源 |
| 共享输出规则修改 | 新内容修订、当前指针、权限版本、影响引用、审计和 Outbox | 当前来源立即解析新内容，历史快照保留，不要求重建知识向量 |
| 采集成功提交 | 完整成功快照、当前目录指针、差异记录及必要影响通知 | 治理复核与知识更新各自办理；失败任务不写当前目录 |
| 知识发布／回退／索引切换 | 固定完整范围、基础版本 CAS、全部绑定更新、历史与审计及 Outbox | Milvus 先准备并验证，再提交 MySQL；不假设跨存储事务，回包丢失查原操作 |
| SQL 接收与派发 | 唯一 execution_id、不可变 SQL 与参数指纹、准入依据及任务记录 | Java 受控只读执行；回包不明先核实原执行，禁止盲重跑 |
| 反馈及任务分派 | 追加事件、当前摘要／事项关联及 Outbox | 派发去重与定期对账；分派不授予业务数据权限 |

首批采用一行 `iam_security_guard` 的短事务锁串行化影响权限或恢复路径的配置写入。人员资料等不影响权限的普通编辑不占此锁。先 guard，再按稳定 ID 锁角色／部门／用户，最后业务聚合，统一锁序；这是一种便于验证的本地初期实现，实际容量通过测试判断后再优化，不先引入分布式策略服务。

执行与交付的放行和权限变更在同一 guard 上确定先后顺序：放行使用共享锁读取当前权威状态并登记许可，变更使用排他锁递增版本。变更提交后不再产生基于旧版本的新许可；已获准进入在途的调用主动取消并核实，返回内容仍重新核权。网络外发和业务数据库不是平台事务的一部分，不能承诺追回已经发出的内容，也不能将已登记许可等同于数据库已开始或停止。query 模块须进一步固定 JDBC 派发与输出交付边界并做竞争测试。

## 访问模式与索引方向

- 人员列表：生命周期与更新时间，部门当前成员反查，角色当前成员反查；姓名登录名的包含搜索由小规模后台查询承担，容量变化后按实测调整，不能声称普通 B-tree 加速任意包含匹配。
- 授权：按 user_id、source_id、有效状态查来源，按 origin_id 查规则；按规则反查全部有效来源，避免规则更新逐个猜测影响。
- 目录：source_id 与对象世代唯一定位，按 snapshot_id、object_id 查完整结构；变化以对象和前后修订定位。
- 治理与知识：主体＋revision 唯一，依赖目标＋revision 支持反查；当前绑定 source_id＋scope_id 唯一，活跃引用按产物与请求双向查找。
- 问数：对话按 user_id、最后活动时间，消息按 conversation_id＋顺序；请求按恢复／派发状态与时间，execution_id 唯一；限量结果不写普通审计。
- 反馈：user_id＋answer_id 当前评价唯一，来源事件去重，事项状态／负责人／更新时间，通知 issue_id＋completion_round＋recipient_id 唯一。
- 模型与看板：调用按 task/request、node、配置修订及时间追溯；汇总保存口径版本和覆盖水位，不能用当前余额回推历史存量。

## 存储之外的落点

Redis 登录会话不建 MySQL 登录会话镜像；MySQL 认证版本决定旧会话资格。检查点由已选 Checkpointer 管理，不复制到普通会话表。队列和事件的 Redis 命名空间、租约与保留随正式任务配置落实。

Milvus 元数据固定 sourceId、scopeId、releaseId、documentRevisionId、chunkId、indexGenerationId、embeddingIdentity；具体 Collection 与索引参数由知识模块验证后确定。不能用可重绑的 latest 别名代替 MySQL 生效清单。

附件原文件位置、备份容量及清理期限仍需实际部署输入；当前只确定 ds_attachment 保存摘要、大小、媒体类型、受控存储引用、状态和引用关系，不把机器绝对路径、公开下载 URL 或附件全文塞进资料主表。该项不阻塞首批无附件身份模块设计，阻塞真实附件上传与解析交付。
