## 分批依赖与完成条件

| 批次 | 交付范围与必要前置 | 闭环条件 |
| --- | --- | --- |
| A 公共底座及身份 | 正式三端构建与配置；会话／CSRF、人员、部门树与成员、角色使用权／授予权、恢复保护、审计与 Outbox | [首批验收](iam/验收.md)通过；页面里尚无真实服务的数据访问部分明确保留未接入状态，不能用固定授权结果冒充完成 |
| B 数据源及访问授权 | A；数据源生命周期、连接及采集、稳定目录、审批责任；部门初始配置、共享规则、本人申请、独立／联合审批、来源及撤销 | 成功采集才更新目录；本人不自批；审批与来源及审计同事务；多来源、规则变更与失权均以真实服务验证 |
| C 模型及治理 | B；18 节点配置与实际调用快照、秘密引用、表字段／关系／指标建议、人工修订确认和依赖复核 | 人工功能不依赖无关模型；AI 建议不覆盖人工内容，必要缺口未解决不能确认，来源事实核实与业务确认分开 |
| D 知识发布 | C；业务事项文档、题单审核、固定候选、构建验证／人工裁定、同版事实、索引及完整绑定、暂停回退恢复 | 题单和候选门槛全覆盖；真实 MySQL/Milvus 切换、并发、回包丢失与当前禁止检查通过 |
| E 问数 | A—D；意图澄清、同版检索、受控 SQL、结果交付／解释、SSE 和恢复 | 单源只读；八终态、预算、取消、未知执行、撤权、重启及解释失败等真实链路通过；不把固定样例当 AI 能力 |
| F 反馈与看板 | E；反馈事件／事项／治理技术任务／复验／回告，看板来源统计与对账 | 修复生效后复验，说明结案单列，通知去重；看板与各模块事实、时间及覆盖口径对账 |

审计、必要事件和统计时间从各模块首次实现时记录；看板界面可以后做，不能事后用当前状态伪造历史。前端公共样式的精修按既定[设计约定](../frontend/设计约定.md#原型基准与界面打磨)先核对“问题队列与处理”样板，和业务模块先后顺序分别安排，不因样板而提前实现全部反馈逻辑。

后续模块采用“补齐字段级设计及接口 → 实现本模块前后端和必要 AI → 真实联调 → 场景验收 → 更新事实定位”的顺序。全局先检查跨模块关系，各模块不用等全系统每个 DTO 写完才开始；进入某批实施前，该批契约与前置条件必须齐全。

B 批的数据源接入与采集涵盖首次与后续采集、快照比较、事实核实、定时、在途凭据替换和退出状态。部门初始访问及本人申请源授权使用同一权威计算；治理、知识或问数从各自批次接入真实消费。衔接见[采集设计](datasource/设计.md#结构变化与核实)及[授权设计](access/设计与接口.md)。

## 每个接口和动作的核对项

每项必须能从产品小节／页面动作追到请求类型、返回字段、状态转换、写入对象、权限、事务、错误及验收场景。查询、选项、数量、详情、执行和下载分别核权；恢复与后台任务沿用同一服务边界。用户自报 userId、角色名称或隐藏按钮都不构成权限依据。

状态修改定义前置条件及重复请求结果；长任务定义接收、派发、执行、取消、终态及恢复；引用型内容定义固定修订与当前可用状态；多对象动作定义原子范围。缺少其中任一项的接口不算详细设计完成。

## 实施前需落实的配置

| 输入 | 落实时间及影响 |
| --- | --- |
| 本机 MySQL 具体版本、空白目标库及隔离测试库 | A 建库前只读核实实例与可弃用途；当前设计使用 MySQL 8.0.16 起支持的强制 CHECK，实际部署版本须支持并在该版本验收，不改变既定 MySQL 8 系列选择 |
| 首个管理员登录名、初始密码、根部门名称编号、受控凭据文件 | 开发账号按负责人决定[随项目提供](运行与验收.md#开发配置)，真实数据库／Redis 凭据和 HMAC 密钥保留在机器配置；初始化成功关闭重复入口 |
| 登录防暴力阈值、登录名匹配及临时锁定参数 | A 编码前结合认证适配落实；账号停用与临时锁定分开。登录名匹配按首批设计，不能让库排序规则无意改变口径 |
| 正式依赖锁文件、静态检查组合、会话／代理配置 | A 工程建立时验证，版本归前后端入口，初始化不是沿用旧工程依赖 |
| 历史、审计、命令防重、事件与检查点的保留和清理 | 对应模块启用清理前确定；需业务期限的单独由负责人决定，不从审计“180 天建议起点”推导所有数据保留期 |
| 企业业务说明原件及解析 | B 保存原件与内容修订，允许类型、容量与下载见[资料契约](datasource/接口.md#企业业务说明)；治理任务取用与解析随 C 批验证 |
| 真实业务源、只读账号、适配器范围及模型信息发送边界 | B/C 真实连接和调用前核验；禁止用管理身份或模型配置绕过业务数据授权 |
| 任务容量、重试、租约、事件缓冲及保留参数 | C—E 真实工作流前按本地验证负载落实；沿用方案预算，不把测试负载变成生产容量承诺 |

表内是可定位的实施条件，不是让负责人预先决定所有技术参数。已有文件、技术验证和本机环境可提供的依据先核对；常规实现参数由实施者确定并验证。涉及新增业务限制、信息外发范围或保留政策时再提出具体决定。

## 验证状态

首批已建立正式三端构建与公共配置，Java 身份、人员、部门、角色、审计及可靠事件和 React 对应页面已实现；Python 当前提供正式公共包及存活入口。真实 MySQL／Redis、接口权限与事务，以及主要浏览器任务已有证据，准确覆盖和原生缩放等剩余项统一见[首批验收](iam/验收.md#当前验证范围)。后续 AI、受控 SQL、索引与完整工作流按所属批次实现验证，不由首批结论推定完成。界面证据放 `output/playwright`，详细结果放 `output/acceptance`。
