# F 批评价提交与入队

本页维护评价提交与入队的实现，业务规则沿用[产品方案](../../product/产品方案.docx)第 7 章和[问数页面](../../frontend/pages/query.md)。本步覆盖本人回答的评价、修改和撤销，以及点踩可靠进入统一队列。知识缺口、技术失败和巡检各有独立事项来源，按各自入口接入。分派、处理、复验、回告和看板随 F 批后续设计落实。

## E 批可复用的事实

| 核对对象 | 现有持久记录 | F 批用法 |
| --- | --- | --- |
| 回答与原提问人 | `qry_request` 记录稳定轮次、原提问人、来源、原题和补充。`RESULT_DELIVERED` 表示该轮的结果已经完成交付。当前一轮只交付一份查询结果，重查新建轮次。 | 用 `answerId = qry_request.id`、`answerRevision = 1` 定位当前实现的已交付回答。版本由服务端确定。原问题、补充和最终计划通过原轮次读取。 |
| 解释与任务代次 | `qry_explanation` 按原请求和解释修订保存文本、状态及模型配置。`qry_request.run_version` 是执行租约代次。 | 解释重试和执行恢复沿用同一评价目标，原回答与解释修订分别追溯。 |
| 实际执行 | `qry_request.execution_id` 唯一。派发许可同时写入执行号、`executed_at`、绑定、规则签名及 `reasoning`。`reasoning` 有 SQL 模板、投影、最终计划和实际生成／复核模型修订。`execution_fingerprint` 用于查重。 | 用原请求回读唯一执行与实际模板。`execution_state = SUCCEEDED` 仅证明查询已返回，达到 `RESULT_DELIVERED` 才具有评价资格。结果行仍由 E 批按现有 24 小时窗口管理。 |
| 正式知识 | `qry_request.binding_id` 和 `reasoning.evidence` 固定执行选中的绑定、文档修订及片段序号。`kn_release_binding` 指向固定候选、构建、文档及嵌入模型修订。`kn_release_build_chunk` 以 `(build_id, ordinal)` 定位片段、摘要及片段所含治理引用。 | 以原绑定和片段回查历史，发布切换后仍定位原编号。片段包含的事实和 `run_input.bindings` 中的检索范围仅说明证据覆盖，实际使用以运行记录为准。 |
| 实际表字段与治理依赖 | `reasoning.projection` 使用逻辑表列名，最终计划保存若干条件。实际 JOIN、复合键、日期、计量检查和治理修订分别在编译、目录和知识读取阶段确定。 | 已有轮次可追到选中片段、执行及已保存条件。完整的稳定表字段身份、确切治理修订和用途需在后续执行时固定。 |

### 补齐原执行的使用依据

在 `qry_request` 增加可空 `usage_refs JSON`。由问数模块在 SQL 派发许可事务中与 `execution_id`、`reasoning` 一次写定。完成结果交付后才可作为回答证据引用。恢复 `FINALIZING` 轮次直接使用原记录。结构化引用由可信的目录、知识和编译结果生成。

| JSON 字段 | 内容与采集位置 |
| --- | --- |
| `schemaVersion` | 固定为整数 `1`。 |
| `knowledge[]` | `bindingId`、`buildId`、`documentRevisionId`、`fragment`、`usages[]`。记录最终编译及独立复核所用片段，以及实际用于确定参数的名称／规格等映射片段。用途为 `QUERY_BASIS` 或 `PARAMETER_BASIS`。 |
| `objects[]` | `objectId`、`generation`、`structureRevisionId`、`columns[]`。一个源由原 `qry_request.source_id` 确定。结构修订通过原目录解析库、模式和对象名。`columns[]` 含 `columnId`、`columnRevisionId`、`usages[]`，用途取 `SELECT`、`COMPUTE`、`JOIN`、`FILTER`、`GROUP`、`ORDER`、`UNIT_CHECK`。从实际生成的 SELECT、JOIN 键、谓词、日期分组排序和单位检查取值，同一字段可有多种用途。 |
| `facts[]` | `kind` 为 `TABLE`、`COLUMN`、`RELATION` 或 `METRIC`，记录 `objectId`、`targetId`、`factRevisionId`。仅写编译、确切关联选择或参数定位实际采用的治理事实。 |
| `contextRequestIds[]` | 实际沿用日期、商品等已确认条件的原轮次编号，来自本轮实际采用的同源上下文。候选上下文仍留在原 `run_input`。 |

片段按绑定、构建和序号去重，字段按对象及字段身份去重，事实按类型、对象、目标和修订去重。问数模块提供只读证据入口，按 `answerId` 与 `answerRevision` 定位原执行及引用。反馈只保存回答引用。正文、原始结果、SQL 参数、知识正文及模型输入留在各自受控来源。

已有 E 批记录的 `usage_refs` 保持 `NULL`。执行、选中片段等可核实引用照常使用，缺失字段标为「证据不完整」。已交付且仍可见的旧回答可以提交评价。后续精确历史引用不可取时也保留已接收反馈及其事项。证据读取保留缺失状态，使用当时的编号定位。 [编译中的实际字段与连接](../../../backend/src/main/java/com/dataocean/module/query/service/QuerySql.java) · [片段与治理修订核验](../../../backend/src/main/java/com/dataocean/module/query/service/QueryCorpus.java)

## 对外接口

成功响应沿用 `Result<T>`。ID 和 UTC 时间遵循[公共接口契约](../../architecture/接口与事件契约.md)。问数详情增加 `answerRef={answerId, answerRevision}`，在结果已交付且本人可回看时返回，否则为 `null`。本人评价的路径为 `/api/v1/query/requests/{answerId}/answers/{answerRevision}/rating`，当前接受的回答修订为 `1`。

| 方法与路径 | 请求 | 返回 |
| --- | --- | --- |
| `GET` 评价路径 | 路径中的回答身份。 | `200`，`{answerId, answerRevision, rating, reason, version, updatedAt, queueState, issueId}`。`rating` 为 `NONE`、`LIKE`、`DISLIKE`。仅当前点踩且原因仍在保留范围内才返回本人原因。首次未评价的 `version`、`reason` 和 `updatedAt` 为 `null`。 |
| `POST` 评价路径 | `Idempotency-Key` 为 UUID。正文 `{action, reason?, expectedVersion}`。`action` 为 `LIKE`、`DISLIKE`、`REVOKE`。`expectedVersion` 必填，第一次为 `null`，之后传上次读到的评价版本。点踩原因去除首尾空白后须为 1–500 字符，沿用原型长度。点赞和撤销的原因缺省或为 `null`。 | 点踩用 `202` 接收，点赞和撤销用 `200`。`{commandId, eventId, answerId, answerRevision, version, acceptedAt}` 是原命令回执，`version` 为本次落盘序号。相同命令恢复原回执。 |
| `GET` 评价路径下 `/commands/{commandId}` | 原命令编号。 | `200` 返回同样的回执，表示本次评价已提交，处理进度从评价路径读取。查不到已提交的原命令时返回 `404`，保留原键可安全重试。 |
| `GET /api/v1/feedback/issues` | 沿用 `PageQuery` 的 `pageNum`、`pageSize`。本步支持 `sourceId` 和精确事项编号 `issueId`，默认按 `updatedAt DESC, id DESC`。 | `200` 返回 `PageVO<{id, sourceId, origin, status, assigneeId, createdAt, updatedAt}>`。本步生成 `USER_DISLIKE`、`PENDING_ASSIGNMENT`，负责人为空。使用 `feedback.view`，列表和总数共用过滤条件。 |

`queueState` 按原回答计算。没有已受理点踩时为 `NONE`。已有点踩事件且尚无事项关联时为 `RECEIVED`，界面显示「已收到」。完成关联时为 `QUEUED`，此时 `issueId` 有值。它表示该回答已进入处理队列。改赞和撤销后仍可回看原入队进度。后台队列基础信息由 `feedback.view` 控制，用户原因、原问、知识和业务明细的读取另核 `feedback.evidence`、当前源授权和输出规则，SQL 另核 `query.sql`。分派沿用已确认的角色和访问规则。

本人接口复用 E 批回答的实时核验，包含当前会话、本人归属、`query.view`、`query.ask`、源访问、原规则签名、固定知识可用性和结果保留窗口。服务端从已授权的原轮次取得评价主体、源、执行与知识引用。对未授权主体或未知回答修订返回 `404`，本人当前失权返回 `403`，源不可用等已定义错误沿用问数域映射。当前有访问资格但回答尚未交付或结果已过期返回 `409 STATE_CONFLICT`。重复提交和回执查询同样走当前核验。受限响应遵循 `Cache-Control: no-store`。

非法动作、未知字段及空白点踩返回 `400 VALIDATION_FAILED`，原因字段错误定位到 `reason`。相同键与不同规范化输入返回 `409 COMMAND_CONTENT_CONFLICT`。新键带旧版本返回 `409 VERSION_CONFLICT`。同一版本下重复相同评价和原因，或没有当前评价时撤销，返回 `409 STATE_CONFLICT`，不产生评价事件。修改点踩原因属于真实变更，追加新事件。业务范围内依照已批准的频率和容量限制返回 `429`，存储不可用沿用 `503`。

## 表结构

新表沿用 InnoDB。以下为持久字段及约束。UUID 用规范小写，评价和事项事件时刻按 UTC `DATETIME(3)`。表间引用采用限制删除。`answer_id` 外键与实际 `qry_request.id` 的类型、字符集和排序规则一致，迁移前核对目标库定义。人员、事项和来源编号使用 `BIGINT UNSIGNED`。 [MySQL 外键要求](https://dev.mysql.com/doc/refman/8.0/en/create-table-foreign-keys.html)

| 表 | 字段 | 主键、引用与索引 |
| --- | --- | --- |
| `fb_event` | `id CHAR(36)`、`user_id`、`answer_id VARCHAR(36)`、`answer_revision INT UNSIGNED`、`sequence INT UNSIGNED`、`previous_event_id CHAR(36) NULL`、`action VARCHAR(12)`、`reason VARCHAR(500) NULL`、`reason_purged_at DATETIME(3) NULL`、`command_id CHAR(36)`、`occurred_at`、`received_at`。 | `id` 为主键。外键指向用户、原请求及上一条事件。唯一 `(user_id, answer_id, answer_revision, sequence)` 和 `(user_id, command_id)`。索引 `(action, received_at, id)` 用于补偿扫描。检查动作枚举和正修订、正序号。点踩保存有效原因，或在保留策略处置后保存清理时刻。其他动作两者均为空。服务端校验上一事件属于同一评价键。 |
| `fb_current_rating` | `user_id`、`answer_id VARCHAR(36)`、`answer_revision INT UNSIGNED`、`last_event_id CHAR(36)`、`rating VARCHAR(12)`、`version INT UNSIGNED`、`updated_at`。 | 主键 `(user_id, answer_id, answer_revision)`。外键指向用户、原请求及最后事件。检查评价枚举及正版本。`version` 等于最后事件序号，撤销后保留 `NONE` 和当时版本。原因随事件读取，摘要可由事件重建。 |
| `fb_issue` | `id`（平台生成）、`source_id`、`origin VARCHAR(32)`、`origin_answer_id VARCHAR(36)`、`origin_answer_revision INT UNSIGNED`、`status VARCHAR(32)`、`assignee_id NULL`、`version INT UNSIGNED`、`created_at`、`updated_at`。 | `id` 为主键。本步创建时写入 `USER_DISLIKE`、`PENDING_ASSIGNMENT`、`version = 1`。唯一 `(origin, origin_answer_id, origin_answer_revision)` 使同一回答的点踩共用原事项。外键指向来源、原请求及人员。索引 `(updated_at, id)`、`(source_id, updated_at, id)` 支持队列排序和筛选。 |
| `fb_issue_evidence` | `feedback_event_id CHAR(36)`、`issue_id`、`linked_at`。 | `feedback_event_id` 为主键，外键分别指向评价事件和事项。索引 `(issue_id, linked_at, feedback_event_id)` 供核对原始线索。只关联实际点踩事件。事项与原评价保留稳定关联。 |

各表字段默认必填。在线提交的发生与接收时间共用服务端当次受理时刻，客户端不传时间。每个事实来源保留自身时间，事项创建时间独立记录实际入队。现有 `sys_command` 保存操作 `feedback.rating.submit` 的安全回执引用和输入 HMAC，`sys_outbox` 与 `sys_event_receipt` 复用现有表。 [公共命令及事件表](../../../backend/src/main/resources/db/migration/V1__identity_baseline.sql)

## 提交、派发与补偿

1. **提交评价。** 在同一 MySQL 事务内取得 IAM 安全共享锁、锁原用户和请求行，再按实时资格核验回答。读取原命令并核对请求 HMAC，指纹范围包含回答身份、动作、规范化原因和 `expectedVersion`。核验命令之前确保当前主体仍可读取该回答，先判重再校验本次修改的版本。读取使用锁后最新状态，避免旧读视图绕过并发检查。评价事件、当前摘要、最小成功审计、命令回执和 Outbox 一次提交。普通审计与失败日志只保留受控编号、动作、状态及错误码。模块复用现有命令 Mapper、HMAC 和 Outbox，资源核验和回执由评价服务负责。 [现有命令实现](../../../backend/src/main/java/com/dataocean/module/iam/service/impl/MutationServiceImpl.java) · [MySQL 锁定读](https://dev.mysql.com/doc/refman/8.0/en/innodb-locking-reads.html)
2. **可靠入队。** 每次真实变更产生 `feedback.rating.recorded`，领域事件 `eventId` 等于 `fb_event.id`，`aggregateType=feedback_rating`，`aggregateId` 为 `answerId:answerRevision`，`aggregateVersion` 等于评价序号，`occurredAt` 从原评价事件取得。Outbox 载荷仅含 `action`，消费按事件编号回读 MySQL。沿用现有 Outbox 领取、租约及重试，通过 Java 本地消费者 `FEEDBACK_ISSUE_INTAKE` 处理 `DISLIKE`，随后由共用派发器发布通道通知。消费者在一笔短事务中锁原请求，再锁 Outbox 行核对当前租约。在这笔事务内检查回执、按唯一键创建或读取事项、写证据关联、登记 `sys_event_receipt`。重投和新旧租约交接复用现有写入。每条新点踩均作为证据关联，同一原回答只创建一个事项。为已有事项关联新证据时更新事项版本和最近更新时间，保留当前处理状态。迟到的点踩仍入队，改赞和撤销只更新评价。
3. **确认与补偿。** 本地消费失败时事务整体回滚，Outbox 延时重试。业务关联提交后，即使 Redis 通道失败或派发确认丢失，`queueState` 仍从 MySQL 返回 `QUEUED`。周期核对以点踩事件为起点分批查找证据关联与消费回执。未消费的已投递记录以原事件编号补投，缺失待派发记录时按原编号和发生时间恢复。关联和回执不一致时记录受控异常并核实原事务。积压监测保留待关联数量、最早受理时刻和无正文的故障信息。事件与入队关联核对完成后再按已批准的保留策略清理，命令记录与事件的防重有效期协调。 [共用派发器](../../../backend/src/main/java/com/dataocean/module/iam/service/OutboxDispatcher.java) · [共用 Outbox 和回执](../../../backend/src/main/java/com/dataocean/module/iam/mapper/OutboxMapper.java)

后台从平台 MySQL 消费已受理事件，撤权发生在提交之后时仍保留事项和必要证据。每次用户回看和后台证据投影按当前权限裁剪。评价动作通过追加事件记录。到期的原因文本由保留策略单独清理，保留评价类型、清理时刻和归属关系。各类内容的期限沿用产品方案的批准流程，反馈保留与审计配置校验通过后启用采集。业务源只读访问及知识发布仍由各自模块处理。

新评价启用前配置 `dataocean.feedback-reason-retention` 为批准的正时长，可使用 Spring Boot 持续时间格式，如 `7d`。该例值用于合成数据验收。定期清理已入队且超过期限的原因正文，保留事件和事项关联。

## 首步验收用例

用实际 MySQL 平台库验证接口、事务和队列。库存 r1 的已交付轮次作为首个评价目标。多表、多片段和复合键使用能明确列出实际依赖的受控用例。下表是实施后的通过条件。

| 方案用例 | 操作与通过条件 |
| --- | --- |
| F01、F18 | 对照原执行号、实际 SQL 模板和已发布知识版本，核对字段、JOIN、筛选、计算、分组及治理修订。另造召回未用片段验证其不会被当作实际引用。切换发布后核对已有反馈仍指向旧版本，旧记录或历史证据缺失时显示证据不完整。 |
| F02、F05 | 并发提交同键同内容得到同一回执，异内容返回冲突。两个不同键用同一旧版本只成功一个。点赞、改点踩、修改原因、改赞和撤销后由事件重建同一评价摘要，多表和多次点踩均只建一个原事项。 |
| F03、F11 | 在提交后丢弃 HTTP 回包，按原键查回执。分别中断本地入队事务、Redis 发布和通道确认，核对「已收到」到实际入队、补偿及防重。点踩后立即改赞，迟到事件仍进入原事项，点赞单独提交不创建事项。 |
| F14 的反馈访问边界、F21、F22 | 测试原提问人、其他账号、撤权、输出规则变更、结果到期和无 SQL 查看权限。空白、缺原因、取消及伪造业务引用都没有评价写入。合法点赞与点踩按实际回答版本保存，同一回答的解释重试沿用原评价。 |
| F17、F20、F23 的队列投影边界 | 人工核对点踩文本作为受控线索。仅具备队列基础查看功能的账号仍可见事项基础信息。后台列表、审计和通道消息均不披露受限原文、SQL 或数据行。 |

## 当前实测
