# 反馈事项的处理结果、复验与回告

已分派且当前负责人已核查的技术事项可以提交处理结果。结果包括实际修正、复查方式与结果、影响范围及已生效确认。查询和安全变更同时记录相关场景并确认测试通过。当前一项技术结果沿用主负责人办理。

| 接口 | 服务端办理条件 |
| --- | --- |
| `POST /api/v1/feedback/issues/{id}/results` | 当前负责人持有 `feedback.process` 且已核查。提交成功进入待验证。 |
| `POST /api/v1/feedback/issues/{id}/technical-progress` | 当前技术负责人保存排查或等待生效，独立任务追加 `?task={task}`。改回跟进时撤回当前结果及复验。 |
| `POST /api/v1/feedback/issues/{id}/knowledge-results` | 业务知识负责人已核查，具备当前原问证据和发布查看资格。关联同源、已核实且可用的正式发布版本，提交后进入待验证。 |
| `POST /api/v1/feedback/issues/{id}/rechecks` | 复验人有当前原问证据和问数权限。使用本人的权限从原问题派发，保留原补充及业务日锚点。原问依赖其他对话历史时阻止重放。 |
| `POST /api/v1/feedback/issues/{id}/verifications` | `feedback.verify`，使用当前登录人的有效问数与来源授权，记录场景、期望、实际结果和数据依据。复验未通过退回处理中。 |
| `GET /api/v1/feedback/issues/{id}/closure-preview` | `feedback.close`。结案类型、原因和有效复验核验后返回当前版本、原提问人和固定模板。 |
| `POST /api/v1/feedback/issues/{id}/closures` | 提交事项所见版本和所确认模板与接收人。已解决仅接受当前结果的有效通过记录。说明结案保留真实类型与内部依据。 |
| `GET /api/v1/feedback/notices` | 只分页查询本人的已投递回告。 |
| `PUT /api/v1/feedback/notices/{id}/read` | 按消息和本人身份标记首次已读，返回当前授权下的定位。 |

V40 保存不可变的处理结果和复验版本，转派清除当期引用。复验授权摘要包括当前账号认证版本、使用能力、源授权来源和输出规则。已解决操作再核对当前负责人、结果修订、复验人员资格及摘要。技术处理记录、复验和结案内文按证据权限裁剪。

结案、回告接收和 `feedback.completion.recorded` Outbox 同事务写入。回告以事项、完成轮次和接收人去重。站内可见状态同本地消费回执落盘。收到、实际投递和已读独立记录。投递与回看均复核原提问人资格、源和输出规则。停用账号只保留后台不可用状态，失权账号的站内提示为通用模板。原问链接随可见资格返回，后台自由结案文本不进入回告。

结案预览和提交以记录中的复验人核对源数据复验的当前问数权限、源授权和发布状态，结案人按其结案功能办理。记录页按完成轮次回显原结案结果和具体原因。

V42 为知识办理固定正式发布引用和实际复验请求。系统在复验与解决结案时核对当期结果、当前发布资格、原问题、复验执行人及结果所用的发布绑定。复验通过必须来自本期重跑且实际交付的结果。技术复验继续登记实际核对结果。

## 同一事项的独立处理任务

V43 允许协调者在已分派的事项下添加治理、技术任务。首次添加时，既有单任务的当前负责人、核查和处理结果带入独立任务，历史记录继续保留。任务负责人核查后各自提交结果，所有在办任务提交后主事项才进入待验证。一个任务复验失败时退回该任务和主事项。至少一个任务实际修复且所有必要任务均有当前有效的通过记录时，才能按已解决结案。主事项只结案、回告一次。

| 操作 | 接口与条件 |
| --- | --- |
| 添加、转派任务 | `POST /api/v1/feedback/issues/{id}/tasks` 和 `POST /api/v1/feedback/issues/{id}/tasks/{task}/assignments`，复用分派入参和 `feedback.assign`。 |
| 退出、恢复任务 | `POST /api/v1/feedback/issues/{id}/tasks/{task}/dispositions`。协调者或主负责人填写依据，退出时说明剩余影响及安排并确认已覆盖。全部任务退出时只能凭当期核查办理其他结案。 |
| 办理、复验独立任务 | 核查、技术结果、治理结果、重跑原问和登记复验沿用原接口，追加 `?task={task}`。拆分后，结果及复验接口须指定任务。 |

添加、转派、退出、恢复和修订结果会撤销旧复验资格，旧结果和人工登记仍按事项版本保存。知识任务复验须引用任务范围变化后实际启动的问数。任务责任计入「待我处理」和「我负责的」，证据与处理正文沿用来源权限。

V47 支持技术任务保存实际跟进和等待生效，V48 扩展台账动作列以保存对应编码。原单任务首次记录进展时沿用负责人和当期核查建立技术任务。等待期间留在「我负责的」，确认修复生效并重新提交后再进入复验。任务详情始终读取当前轮次仍有效的跟进正文，事项历史的展示条数不影响回看和表单回填。复验人和结案人的待办使用当前有效复验判定，在列表计数及分页前筛选。

独立 MySQL 8.4 平台库实测了原单任务和双技术任务。复验失败只退回对应任务，重新分派后拒绝原负责人的提交，转派、修订、退出和恢复后撤销旧复验。必要任务均通过后只送达一条回告，并记录原提问人已读。[任务接口验收](../../../output/acceptance/2026-11-23-feedback-tasks/verification.json)

在独立平台库和合成库存源完成源数据、技术和治理三类任务联合复验。实测正式知识发布和同源只读问数，复验不齐时拒绝按已解决结案。通过全部必要复验后，结案命令重放仍只送达一条回告，原提问人可确认已读。[三类任务联合验收](../../../output/acceptance/2026-11-23-feedback-business/verification.json)

## 源数据修正

源系统负责人负责修正数据并确认必要同步。DataOcean 只记录跟进、修正事实和复验。事项首次直接分派为源数据时建立独立任务，也可在同一事项内追加源数据任务。V44 为旧库中已分派但还无独立任务的源数据事项保留原负责人及当期核查。

| 操作 | 已核实的办理要求 |
| --- | --- |
| 保存跟进 | `POST /api/v1/feedback/issues/{id}/tasks/{task}/source-progress`。当前已核查的跟进人填写已做工作和下一步。等待外部修正或同步期间保留在办，进入「我负责的」。 |
| 提交修正结果 | `POST /api/v1/feedback/issues/{id}/tasks/{task}/source-results`。记录实际修正人或团队、数据范围及内容、只读复查方式与结果，确认修正和必要同步已生效。工单或批次等参考可选。 |
| 只读复验 | 沿用任务复验接口，登记有权核对的场景、期望、实际结果和数据依据。可在工作台只读重跑原问，也可人工核对代表性案例。关联实际问数时核对修正后的时间、本人归属、同源、现行输出规则和实际交付。源数据复验可使用原有且仍可用的知识发布。 |

改回跟进会撤回当前修正结果和相关复验，旧版本保留。仍在等待外部修正时须先记录新的跟进结论才能申请退出。复验失败返回处理中，已解决结案仍要求全部必要任务通过有效复验。

在独立 MySQL 8.4 平台库实测 V44 升级、等待期间保留责任、拒绝未生效结果和改回跟进后撤销旧复验。合成库存修正后，使用实际模型和只读源连接重跑原问，与源库独立读数对账，再登记复验、结案并确认回告。复验接口拒绝错误轮次和未授权操作者。[源数据接口验收](../../../output/acceptance/2026-11-23-feedback-source-data/verification.json) · [模型与只读源联验](../../../output/acceptance/2026-11-23-feedback-live/verification.json)

## 用户补充、合并与重开

V45 保存原问补充、人工主从关联及事项完成轮次。主负责人核查后指定有权访问的原问题和具体缺项。原提问人从该原问卡片回复，问数知识缺口也可主动补充。回复保留在原事项中。主事项仍有关联的必要补充时显示待补充，可继续保存过程和结果，暂不接受复验或结案。最后一条等待结束后回到处理，当前复验失效，已有处理记录继续保留。补充正文沿用反馈原因的留存窗口，授权按每条原问题分别核对。

V46 允许当前主负责人逐条撤回补充请求，或记录长期未回复、账号停用、源访问撤回等无法取得补充的事实。两种处置均填写依据，保留原请求、处置人与时间。组内其他请求继续等待，两端事项版本同步推进，已处置的请求拒绝迟到回复。原提问人只可看到对外的处置状态，后台处置依据继续按原问题授权裁剪。

协调者只能把同源、经核实为同一根因与处理范围、尚未开始独立任务的重复事项归到未结主事项。确认时比较两端版本，原问和原始活动仍从各自事项回看。纠正合并恢复原事项办理状态，已形成的历史和回告快照可继续追溯。组内曾作为原问依据的知识发布版本不能作为当前治理修复。

结案人核对各原提问人的受控回告。每个接收人在每次完成轮次只收到一条回告，可分别查看自己有权访问的原问。重开由主负责人或具备协调和处理权限的人员凭新证据办理。重开进入处理中，清理当期核查、结果和复验资格，保留任务、旧结案及既往回告。后续复验和结案形成新的完成轮次。

| 操作 | 正式接口 |
| --- | --- |
| 请求补充 | `POST /api/v1/feedback/issues/{id}/supplement-requests` |
| 处置待补充请求 | `POST /api/v1/feedback/issues/{id}/supplement-requests/{supplementId}/dispositions` |
| 本人原问与回复 | `GET`、`POST /api/v1/query/requests/{id}/feedback-supplements` |
| 建立或解除主从关系 | `POST /api/v1/feedback/issues/{id}/merges`、`POST /api/v1/feedback/issues/{id}/merge-corrections` |
| 查找同源相似候选 | `POST /api/v1/feedback/issues/{id}/similarity`，返回最多五个可核查的事项编号与原问，沿用当前证据访问范围。 |
| 凭新证据重开 | `POST /api/v1/feedback/issues/{id}/reopens` |

独立 MySQL 8.4 验收库实测了 V45 升级和一主两从的合成场景。两位提问人的原问补充分别归原事项；纠正再合并仍保留待补充，全部回复后恢复办理。首轮结案对同一提问人的两条原问合发一条回告并保留两个授权定位。凭新证据重开后重新核查、提交与复验，第二轮结案保留首轮回告和历史记录。[真实接口验收](../../../output/acceptance/2026-11-23-feedback-lifecycle/verification.json)

独立 MySQL 8.4 验收库用三个旧待回复请求实测 V46 升级。主负责人撤回长期未回复的请求，并分别记录合成账号停用及源访问撤回。其余等待继续拦截结案，最后一条处置后按已有证据重新提交、复验并结案。迟到回复、非负责人处置与重复覆盖均被拒绝。[处置接口验收](../../../output/acceptance/2026-11-23-feedback-supplement-disposition/verification.json)
