# F 批事项核查与分派

以[评价与入队](评价与入队.md)已提交的 `fb_issue` 为入口。队列基础信息随 `feedback.view` 开放。待我处理包含协调者可分派的待分派事项和本人负责且有 `feedback.process` 的处理中事项。我负责的按当前主负责人筛选。分组、数据源和事项编号的筛选均先于分页计数。

| 接口 | 读写条件 |
| --- | --- |
| `GET /api/v1/feedback/issues` | `scope` 支持 `ALL`、`MINE` 和 `OWNED`，缺省 `ALL`。 |
| `GET /api/v1/feedback/issues/{id}` | 返回基础事项、当前版本、可执行动作和有权读取的原问证据。 |
| `GET /api/v1/feedback/assignees` | `feedback.assign`。按姓名或登录名搜索启用、已完成改密且具有查看和处理权限的人员。 |
| `POST /api/v1/feedback/issues/{id}/assignments` | `feedback.assign`。提交 `expectedVersion`、`assigneeId`、`direction`、`reason`。待分派进入处理中，处理中可转派。 |
| `POST /api/v1/feedback/issues/{id}/reviews` | `feedback.process` 且是当前处理中事项的负责人。提交 `expectedVersion`、`basis` 和可空 `rootCause`。 |

写入使用原命令编号、事项版本和当前分派资格。成功时在一个事务中推进事项版本、追加操作记录、写入脱敏审计及命令回执。重复提交回原回执，旧版本要求重新核对。V39 增加事项初步方向与负责人索引，并新增分派和核查记录表，保留既有事项编号与状态。

原问、点踩原因、核查与分派正文要求同时具有 `feedback.evidence`、`query.view` 和当前来源访问。回看沿用原执行的输出规则签名，并对可见字段执行当前输出规则。SQL 另核 `query.sql`、结果留存和发布可用性。原执行证据缺失时仍保留事项和能核对的历史引用。不复制结果行或提交参数。技术人员接受分派后可以记录核查，原文权限保持独立。

界面沿用[反馈专题](../../frontend/pages/feedback.md)。详情展示最近 20 条处理记录和最近 20 条关联点踩。每次核查录入独立依据，旧记录在详情回看。实际使用的查询、知识与执行事实继续从原问数读取。处理任务、复验、结案和回告另行接入。

已在独立库存反馈库复验 V38 到 V39、真实分派与核查、同版本并发拒绝、原命令重放、旧负责人转派后失去写权限，以及技术人员分派后仍无源查询和证据权限。
