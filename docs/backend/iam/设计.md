# 人员与权限首批设计

本批覆盖登录与改密、本人资料、人员、部门树与成员关系、个人角色、使用权与可授予操作、受保护管理与恢复、审计和可靠通知。字段见[建表设计](建表.sql)，动作与 DTO 见[接口](接口.md)，完成条件见[验收](验收.md)。这是正式实现输入，尚未创建新版业务源码或执行建表。

数据源授权相关的共享规则、部门初始数据配置、访问申请和联合审批属于下一批，与数据源责任和状态一起细化实现；其全局归属已在[数据模型](../数据模型设计.md)固定。首批部门操作保留下一批服务协作边界，不能用固定授权数据声称真实访问已接入。

## 身份、凭据与登录状态

`iam_user` 保存身份和生命周期，`iam_user_credential` 只保存框架编码的安全散列及修订。登录名为 trim 后 1–80 字符、大小写敏感的精确匹配，和原型一致；不转换为邮箱／手机登录，不自动折叠 Unicode 或小写。归档后不复用该登录名。姓名 1–80，角色和部门名称 1–80，备注最多 300；手机号为最多 32 字符的可空联系资料，邮箱最长 254 并校验格式，不增设短信校验或认证用途。

初始及新密码沿用 8–32 个字符，包含 ASCII 字母和数字；不 trim、标准化或记录密码。两次新密码在客户端和服务端均核对，新旧相同拒绝。采用 Spring Security PasswordEncoder 的带算法标识存储形式，初期选择框架 PBKDF2 实现并在真实机器校准工作因子；不使用原型的 SHA-256，也不采用会截断合法多字节密码的处理。算法参数随正式配置锁定并验证，未知算法标识拒绝，不能回退明文比较。参考 [Spring Security 密码存储](https://docs.spring.io/spring-security/reference/features/authentication/password-storage.html)。

| 状态或动作 | 持久事实与结果 |
| --- | --- |
| 创建账号 | lifecycle=ENABLED、must_change_password=true、first_login_at=null；必须有一个正常主部门，初始个人角色可为空 |
| 首次认证成功 | 记录真实 first_login_at；只建立待改密受限会话，普通接口和 SSE 拒绝；不能借直接 API 绕过 |
| 首次或重置后改密 | 校验当前认证凭据，更新散列与 credential_revision、清除 must_change_password、递增 authentication_version，提交审计及失效事件；注销所有旧会话后重新登录 |
| 本人正常改密 | 校验当前密码、版本与新密码，执行同一散列更新及全会话失效；不改变角色或组织 |
| 管理员重置 | 由有权管理员核实身份后设置初始密码，标记待改密并失效全部旧会话；恢复上限及数据来源均不因此变化 |
| 普通退出 | 注销当前登录会话，不改认证版本，不删除对话或取消已接收后台任务 |
| 停用 | lifecycle=DISABLED，递增认证与全局权限版本，阻断登录、访问、订阅及实际受影响任务，保留历史 |
| 复核恢复 | 选择当前合理部门与角色，确认来源复核并记录原因；重新建立登录资格，递增认证版本；旧会话、结束来源和旧任务不恢复 |
| 归档 | 先停用并处理审批责任／待办等外部阻断项；核对中列出将结束的个人角色及主兼任关系，归档事务保存当时归属快照并结束这些关系及来源；保留身份与历史，不提供普通硬删除 |

对外同时返回 lifecycle、mustChangePassword 和 displayStatus。displayStatus 为 PENDING_FIRST_LOGIN（未首次认证且待改密）、PASSWORD_CHANGE_REQUIRED（已认证过但待改密）、ENABLED、DISABLED、ARCHIVED，显示状态由前述事实推导，不建立互相矛盾的第二份状态列。停用和归档优先于待改密。

登录会话仅保存 userId、authenticationVersion、authenticatedAt、lastUserActivityAt、absoluteExpiresAt 和必要认证信息，权限每次按当前权威状态计算。空闲时限按服务端 lastUserActivityAt 判定，先检查是否到期，再由实际业务交互更新；auth/me、命令／任务状态的被动轮询和 SSE 心跳不更新该值，不能让框架默认的会话存取刷新把被动轮询当作用户活动。已有会话中的版本必须与 MySQL 当前用户一致；会话删除事件延迟、Redis 仍有旧会话或停用后重启均不能继续放行。会话中不保存整个 PO、密码散列、结果或永久权限快照。

登录验密放在短锁事务外，成功后再次核对 credential_revision、authentication_version、账号状态；若期间重置或停用，拒绝建立有效会话。会话保存后即使并发变化，每个后续入口仍核对认证版本，不能复活旧登录资格。绝对与空闲时限沿用认证专题，SSE 心跳不续期。认证服务不可用时拒绝，不降级为本地内存会话。

目标用户当前保留的角色分配（包括停用角色）中，任一角色含受保护功能或受保护授予项，即按受保护目标处理。重置、停用、恢复和归档这类目标，除原动作能力外还须 roles.protected 并核对最后恢复途径；不能由普通账号管理员通过重置其密码取得最高能力。移除受保护分配仍走专用接口，不能先停用角色再把它当普通角色处理。

CSRF 令牌接口登录前可用，认证成功和退出后重新取得；Cookie 的会话 ID 不向 JS 暴露。首次改密与普通改密均由真实会话认证，忘记密码不增加自助重置 API；原型示例账号不进入正式数据。

## 人员与组织

部门使用邻接树；列表汇总后代仅是查询行为。正常人员有一个正常主部门和零到多个兼任部门；主兼任不能重复。历史关系用 left_at 结束，重新加入创建新行。SQL 唯一约束保证最多一个当前主部门和每个用户／部门一条当前关系；“正常人员至少一个主部门”由服务事务保证，归档后允许没有当前关系。

组织写入先锁 `iam_security_guard`，再锁相关部门及用户，读取完整祖先链。两笔并发父节点调整串行核对，禁止自指和间接成环；父部门必须存在且非归档。普通编辑不顺带迁移子部门的源授权，因为部门层级不产生授权继承。

人员表单同时修改基本资料与部门时使用一个事务，资料变化核对 users.edit，归属变化另核 users.transfer；缺少某项能力时对应字段只读，不能先保存资料再让归属半失败。专用调岗接口复用相同 MembershipSelectionDTO 及服务逻辑。加入成员沿用原型的“加入兼任”，主部门迁移走完整调岗；直接移出当前主部门拒绝并引导先设置新主部门。

人员归档不能要求先单独移除主部门而又没有合法入口。归档确认本身明确包含结束该停用人员的全部当前分配及成员关系，在同一事务办理，不另增加“无主部门人员”维护状态。iam_user.archived_affiliation 只保存归档时的主兼任部门和角色展示快照，字段结构为 `{primaryDepartment:DepartmentRefVO|null,secondaryDepartments:DepartmentRefVO[],roles:RoleRefVO[]}`；当前关系表分别写 ended_at／left_at，历史和角色版本仍保留。归档人员详情从快照展示当时归属，不因组织或角色改名改变，也不把该快照当作当前访问。外部未移交责任仍须先处理，不能在归档事务中默默清空别人的待办。

批量加入兼任和迁移成员按一次请求整批提交：预览列出目标、受影响用户及源配置影响，提交携带每人的版本；任一失败整批不变。不增加逐人隐蔽半成功。正常成员不可直接加入停用或归档部门。

部门停用保留成员关系和旧配置，结束本部门派生访问，不停用成员账号或修改个人角色。恢复部门只恢复组织，access_review_required=true；下一批显式复核初始配置后才能形成新来源，不把已结束来源改回有效。归档前不得有当前直属成员、非归档子部门或未处理初始配置。账号停用与部门停用分别处理，不能以部门树级联停用全部下级账号。

## 角色、使用与授予

角色使用权取正常用户当前分配的 ENABLED 角色中启用权限的并集。页面权和动作权分开，调用动作须同时具有其显式所属页面权；不要求另配置“查询／重置／分页”。账号信息中的本人联系资料和改密由登录本人身份授权，不依赖 users.edit 或 users.password。

权限目录由版本化种子维护，来源是已确认页面与操作；企业只能给角色选择目录项，不能通过输入 permission_class、is_protected 或角色名称创建权限。`iam_permission.page_permission_code` 显式表达动作所属页面，不能用 code 前缀猜测；例如 releases 页的治理恢复动作仍按目录归属检查。角色 code 由服务端生成且稳定，is_builtin 仅标明模板来源，不等于最高能力。

角色名按 `trim → NFKC → Locale.ROOT 小写` 形成 name_key，与原型防重口径一致，数据库唯一兜底；变更姓名或角色名不改变 ID 和历史身份快照。角色至少包含一个可用页面或动作，动作所属页面必须在完整选择中。

管理角色的可授予操作取 `iam_role_grant_permission`；本人使用与可授予权不互相推导。修改角色或分配角色时核对完整最终能力集合，不只核对差集或角色名称，禁止用多个名字掩盖受保护能力。多个管理角色只能按同一动作合并其明确授予能力，不把使用权或另一动作的条件拿来补足当前授予资格。

普通新建／编辑／分配不能增删受保护能力或分配新增受保护角色；保留已存在受保护分配允许作为只读项，移除须走受保护流程。编辑共享角色先核对全部当前分配人员，保存时再次检查；包含操作者自己的角色也不能借普通修改扩大自己的管理上限。

缩小某角色授予上限只限制后续授予，不自动删除别人既有使用权；预览列出受影响的现存分配，若要收回须另做明确撤权。角色停用保留个人分配关系，但功能立即失效且不得新分配；恢复时复核当前上限及实际能力。角色归档先停用且无当前分配人员，历史分配不删除。

角色每次 version 变更同事务追加 iam_role_snapshot，明确保存当时的名称、状态、使用权限及可授予权限代码集合。当前关系仍从规范化表读取；历史快照不参与当前放行，分配记录保留 assigned_role_version。这样共享角色改动后，仍能核对当时实际分配内容，不依赖角色当前名称重建历史。

四个预设角色使用权沿用原型 role-data.js 的四个主模板，均不含业务源访问。初始可授予项单独固定：超级管理员角色显式配置整个已启用目录；管理员角色配置原型管理员模板的普通功能，以及分析师、普通用户模板中的普通功能；分析师、普通用户的可授予项为空。管理员仍须同时具有相应角色管理动作才可办理，不能仅凭上限调用接口；后续通过受保护流程调整。分析师不默认治理审核发布，管理员不默认最高管理能力；所有受保护判断都以真实权限为准。种子是显式初始配置，不用“持有权限即可再授予”的运行算法推导。

## 受保护配置与最后恢复途径

受保护操作沿用目录 `roles.protected` 与 `users.recover`。前者办理受保护能力及授予上限配置，后者办理受保护恢复；二者均不自动成为数据访问权。常规账号重置、组织编辑、角色改名和复制均不能使用恢复旁路。

受保护配置提供三类动作：调整角色的受保护使用能力、调整角色可授予操作上限、变更人员的受保护角色分配。提交必须具备 `roles.protected` 和对应被授予操作的当前授予能力，核对目标实际状态和影响；不能通过本次提案新授出的能力来证明本次操作有权。角色已分配给操作者时，禁止本次变更提高操作者自己的授予上限，需另一已有资格的人办理。

`users.recover` 允许从有审计依据的既知分配及角色快照构造新的恢复提案，预览后提交；只恢复明确列出的管理角色，不任意指定数据库行、不修改历史、不绕过目标账号状态、不授予数据源。恢复目标必须匹配可核验历史，当前角色的能力及授予集合须与历史兼容且未归档，不能凭用户自填 permissionCodes 获得新能力。共享角色本身已变化时返回 DEPENDENCY_STALE，先通过受保护角色配置核对其全部人员影响；不在恢复单人时偷偷回滚共享角色。恢复提案与普通权限配置共用权威检查和审计。

所有会影响恢复资格的操作在 guard 排他锁内计算变更后的完整有效图。有效恢复人员须：账号 ENABLED、已完成必要改密、至少一个当前 ENABLED 角色授予 `users.recover`、该操作所属页面权可用；可实际执行恢复所需的授予依据同时保留。不能只数某角色分配人数，也不能因角色名称是超级管理员而放行。并发停用、角色变更、重置密码及移除分配不能清空最后一条可用恢复途径。

受控初始化是唯一初期例外：空新库、bootstrap_completed=false 时在一个事务创建首个管理员、私有配置指定的根部门与主成员关系、受保护角色及明确授予集合；写 BOOTSTRAP 审计，不提供公网重复初始化 API，不把密码放入 SQL。首次必要改密完成后在同一受控事务设置 bootstrap_completed=true；此后不能自动回到初始化模式。初始化用户只能先改密，尚不能称为已验收的可用恢复途径。

首个管理员密码遗失且尚无可用恢复人员时属于明确的受控运维恢复，不开放匿名 HTTP 绕过。具体私有操作入口随首次部署配置落实；不能声称“保证任意情况下都可在线自助恢复”。

## 事务、审计与通知

首批 15 张表的字段与索引以 SQL 为准。数据库保证唯一及引用，服务保证完整业务状态、至少一个主部门、部门无环、授予上限及恢复资格。

| 操作组 | 事务范围 | 对外结果 |
| --- | --- | --- |
| 创建人员 | 防重、用户与凭据、主兼任、获准初始角色、审计及必要事件 | 201 返回新 ID 和版本，不返回密码 |
| 修改本人联系资料 | 用户版本 CAS、本人资料及最小审计 | 200 返回新资料；不更新他人或另建本人资料副本 |
| 修改／重置密码 | 用户与凭据版本核对、必要恢复保护、散列、待改密标记、认证版本、审计及失效事件 | 本人改密后重新登录；管理员重置返回安全操作结果 |
| 角色／部门／归属变更 | guard、聚合版本、实际影响、当前关系、security_version、审计及 Outbox | 一次提交，无一半成功；Redis 失效及后台中断可补偿 |
| 无变化保存 | 读取当前版本，不新增内容修订 | 返回当前事实，不伪造变更 |
| 被拒绝操作 | 原业务事务回滚；必要拒绝审计使用独立最小记录 | 保留原状态，按真实原因反馈；审计不可用时也不放行受保护动作 |

成功审计与业务变化一致提交；不能用异步日志替代关键管理审计。每条记录只保留必要差异，密码更新只写“已变更”及非秘密版本，不写散列或 HMAC。对权限变化提交 Outbox，重复消费幂等，当前权限不依赖投递成功才更新。

普通读取通过当前身份、页面权及对象可见性计算，审计详情里的申请、授权、业务原文链接分别按对应模块核权。没有某类查看权时不返回其对象和数量。资料更新时间、真实操作时间、首次登录与当前登录时间分别使用各自字段。

## 下一批衔接

IAM 通过 Service 提供 `CurrentIdentity`、`EffectiveCapabilities`、`GrantableCapabilities`、`CheckRecoveryInvariant`、`MembershipImpact` 和 `InvalidateAuthentication`，不向其他模块开放 Mapper 或凭据 PO。传输对象只含 ID、状态、版本和实际所需能力，禁止包含 passwordHash。

数据访问模块提供当前来源与规则合并、配置影响和来源结束能力；部门／账号状态事务由同一 Java 业务服务协调，不能把“稍后事件会处理”当作旧访问继续有效的理由。数据源提供稳定身份、当前状态与主／替代责任；审批时再次验证账号及功能，配置负责人不自动授权。

首批人员详情里的数据访问区域在 B 批完成前只能表达未接入；首批身份验收不算整个权限模块验收。B 批再补全规则、申请、来源的字段 DDL、逐接口及异常场景，复验 A 批的停用、调岗、恢复和角色变化在真实授权上的影响。
