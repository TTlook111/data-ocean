# D 批知识发布详细设计

首个业务事项为「商品分类与展示口径」。使用独立的合成商品源，从 C 批选取已确认的表说明、字段、关联和指标，形成一篇知识文档与一套标准题，验证后发布到一个业务范围。产品规则以[产品方案第 5 章](../../product/产品方案.docx)为准。页面承接[知识发布原型](../../frontend/pages/knowledge-release.md)，跨存储时序沿用[知识版本与索引一致性](../../architecture/知识版本与索引一致性.md)。

## 首个业务事项

| 内容 | 首轮范围 |
| --- | --- |
| 业务问题 | 某个分类中有展示记录的不同商品有多少种；多条展示记录如何计数 |
| 主动选择 | 商品表的表说明和分类字段、商品和展示的关联、不同商品数指标 |
| 必要依赖 | 商品稳定主键、展示表的表说明与商品外键，以及指标和关联确认时绑定的其他实际依赖。表名与字段名以合成源成功采集结果为准 |
| 使用边界 | 选择当前源的明确分类。按商品主键去重；展示记录不代表库存、销量或历史状态。只有 C 批已确认定义明确支持的含义可写入正式正文 |
| 数值题 | 在合成分类中准备两种商品，其中一种有两条展示记录。标准期望为 2，由测试数据清单独立确定。实际值由候选使用的只读查询取得 |
| 说明题 | 问同一商品有两条展示时如何计数。实际答案从候选的固定正文、索引召回片段及同版治理定义取得。人工按证据判断是否解释稳定商品身份和去重规则 |

首轮按一个单源、单文档业务范围实现。多文档引用及协同切换、合并拆分、Embedding 换代随对应场景接入现有发布流程。

## C 批交接

1. 按源和稳定条目编号读取 C 批真实确认。表和字段取最后一次确认对应的内容修订，关联和指标取实际审核修订。确认必须仍对当前定义、对象世代和必要依赖有效。待确认、移除、待复核以及失效依赖进入问题清单，逐项标明处理入口。
2. 按关联和指标确认时绑定的版本展开必要依赖，记录主动或补齐、使用方式、依赖路径。字段补所属表说明；引用表只纳入实际用到的字段。按源、对象、世代、条目和修订去重，循环或冲突阻断固定。已确认的原文及附件继续执行原有查看权限。传给规划、正文和向量模型的为获准范围内的确认内容。
3. 文档保存每节正文和对应事实引用。更换事实修订即形成新文档修订。普通采集编号变化且实际结构与定义未变时复用现有依据。治理复核未通过、已确认内容发生实质替换或目录不兼容时，旧候选停止进入新发布，已生效版本按当前使用控制实时判断。
4. 依据变化反查文档、在途候选和当前生效清单中的固定引用。历史引用保留原修订。知识流程仅在受影响范围的必要处理完成后回写 C 批办理结果。

## 状态和字段

| 存储对象 | 稳定字段与约束 |
| --- | --- |
| 文档与修订 | 文档保存源及范围、当前草稿和已确认修订指针、乐观版本。不可变修订保存标题、用途、排除项、代表性问题、按节正文、创建人和时间。确认绑定修订、操作者、时间 |
| 治理引用 | 文档修订、章节、源、对象、世代、条目类型与稳定 ID、治理修订、结构修订、主动或必要依赖、使用方式。索引支持按源和条目反查 |
| 标准题与修订 | 所属源和文档、题目、能力和边界覆盖、比较方式、预期、数据依据、经授权的执行身份、固定条件及审核人。正文或依赖变更后按实际影响复核 |
| 发布范围及候选 | 每源范围有生效指针和并发版本。候选固定基础生效绑定、本次确切文档修订、所有治理引用、已审核题单修订、执行授权上下文、模型配置修订与不可变指纹 |
| 构建与验证 | 构建尝试保存任务编号、代次、租约、技术状态和结果。验证运行绑定候选、索引代次和题单。逐题记录实际值或证据、技术结果和发生时间，人工裁定单独持久化 |
| 知识版本、索引和绑定 | 知识版本记录确切内容及发布先后，索引代次记录对应内容、片段映射、向量空间及 Collection。生效绑定同时指向内容版本和匹配索引 |
| 暂停和禁止 | 保存当前范围及治理对象的实际限制、原因、证据和审核记录。读取权威来源作实时判断，独立于候选和历史生效绑定 |

同一工作流始终使用字符串外部标识、稳定分页和统一响应。业务写使用共用命令防重和审计。读取同一源的变化需要复用 C 批权威目录、治理修订与使用控制，知识模块不写治理内容。

## 页面与事务

| 页面 | 操作与结果 |
| --- | --- |
| 知识文档 | 在当前源发起规划，核对事实和依赖，生成草稿；在正文、范围与依据、修订与发布中检查和编辑，明确保存或确认。修改语义时回到治理 |
| 标准题单 | 维护题目草稿和期望依据；事实、文档和规则齐全后审核具体题目修订。发布任务内继续当前候选的相关题和待裁定结果 |
| 发布与版本 | 准备范围并提示缺题。固定候选、构建、运行验证、处理人工裁定、预检、发布，回看当前与直接上一版；保留任务状态、失败原因和原工作位置 |

Java 在 MySQL 持久化候选及代次，并通过现有可靠任务机制调度 Python。构建先从该候选固定正文生成保留条件和限制的片段，持久化片段到治理引用的映射，再写入独立 Milvus 代次。Python 用 Java 固定的 Embedding 配置构建及查询，按 Strong 一致性实际回读预期片段及所属版本。构建和验证结果只接受当前租约及代次，完成后可回读。

自动验证与人工裁定处理不同类型的结果。数值题使用候选片段命中后的同版关系与口径，受控执行只读查询。首轮用服务端按成功目录构造的去重计数查询验证商品事项，固定字段、关联和过滤，值由参数绑定。Java 核验原执行身份的当前源授权、输出规则和对象控制。无法处理的有效输出限制阻断执行；原始业务行不保存为结果。说明题保留实际候选证据、答案、操作者和裁定理由。明确不通过、执行异常或缺题均阻断。

发布预检再核对来源可用性、治理修订、文档和题单、索引匹配、运行结果、当前使用控制和基础版本。发布时在一个 MySQL 事务以版本比较切换整个范围的绑定，留存原版和新版、操作人、审计与 Outbox。重试通过原命令回读。并发候选在基础版本变化后必须重新核对。

回退目标为当前版的直接上一版。核对完整目标的当前可用性、依赖版本兼容、可检索性和关键题校验依据，保留既有暂停和禁止。缺失或不兼容时保留当前绑定并给出原因。受限范围的原始历史可回看，正式使用仍检查当前限制。

## 实施顺序

先接入 C 批确认引用、文档草稿和修订确认，再接入标准题与候选准备，随后验证 Milvus 构建、实际题目结果、切换与回退。发布动作以真实索引和题目检查结果为前置条件。每个环节的接口、状态和验收见[接口](接口.md)及[验收](验收.md)。
