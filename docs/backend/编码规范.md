## 排版与注释

- 每个显式声明的方法都写中文多行 Javadoc，包含构造方法、接口方法、私有方法和覆写方法；说明职责，必要时补充参数、返回值、约束和异常含义。不使用单行 `/** ... */`，不以方法名直译代替用途说明。
- 注释、注解和声明分行书写，每个注解独占一行。方法、构造方法及控制语句的代码块展开书写，即使只有一条语句也不挤成一行；每行只写一条语句。
- 相邻方法之间保留一行空行，构造方法与其他方法之间同样处理。一个方法的注释、注解和声明保持连续。
- 相邻成员变量或常量的声明块之间保留一行空行，每个声明块包含该字段的注释、注解和声明；字段区与构造方法、方法区之间保留一行空行。
- 成员变量原则上都写用途注释；`entity` 下 DTO、VO、PO、Query 的每个字段必须写中文多行 Javadoc，说明业务含义，涉及单位、编码或特殊取值时一并说明，不能只重复字段名。
- 局部变量也优先注释业务用途或来源约束。相邻独立变量的声明块之间保留一行空行，并按初始化、校验、处理和返回等逻辑步骤分组；循环下标等显而易见的临时变量不机械重复注释。
- 运算符、逗号、参数列表及缩进遵守统一格式，长参数列表和调用链按可读性换行，不为减少行数压缩代码。格式化配置须保留上述注释和空行要求，不能只以格式检查通过代替人工核对。

## Java 职责分层

| 包与类型 | 职责 | 边界 |
| --- | --- | --- |
| `controller` | 接收请求、绑定及校验参数、调用业务服务、组织响应 | 不直接访问 Mapper，不承载业务规则或数据库操作 |
| `service` | 声明业务服务接口与业务能力 | 不把 HTTP 请求对象当作业务入参 |
| `service.impl` | 实现业务流程、规则检查和事务协调 | 数据访问委托 Mapper，不把业务实现放回 Controller |
| `mapper` | 数据访问、映射与必要 SQL | 不承担接口响应、业务流程或权限授予决策 |

Controller 依赖 Service 接口，ServiceImpl 通过 Mapper 完成数据库访问。分层是职责边界，不要求每个框架 CRUD 方法再增加无意义的同名转发。

## 类名与文件名后缀

Java 文件名与其中的 public 顶层类型名一致，使用大驼峰命名，并在 `.java` 前保留明确的职责后缀。

| 职责 | 后缀规则 | 文件名示例 |
| --- | --- | --- |
| 接口控制器 | `XxxController.java` | `DatasourceController.java` |
| 业务服务接口 | `XxxService.java` | `DatasourceService.java` |
| 业务服务实现 | `XxxServiceImpl.java` | `DatasourceServiceImpl.java` |
| 数据访问接口 | `XxxMapper.java` | `DatasourceMapper.java` |
| 数据传输对象 | `XxxDTO.java` | `CreateDatasourceDTO.java` |
| 返回视图对象 | `XxxVO.java` | `DatasourceDetailVO.java` |
| 持久化对象 | `XxxPO.java` | `DatasourcePO.java` |
| 查询条件对象 | `XxxQuery.java` | `DatasourceQuery.java` |

`DTO`、`VO`、`PO` 统一全大写；`Controller`、`Service`、`ServiceImpl`、`Mapper`、`Query` 保持上述拼写。包名使用小写，Service 实现位于 `service.impl`。不同业务动作需要不同 DTO 时，在职责后缀前区分动作。

## entity 对象分类

按职责使用 `entity.dto`、`entity.vo`、`entity.po`、`entity.query`，不混用一个类承载所有层。

| 分类 | 用途 |
| --- | --- |
| DTO | 创建、修改、业务操作等结构化输入及必要的跨服务传输 |
| VO | 对外返回的详情、列表行及展示结果 |
| PO | 数据库持久化对象，承载表映射字段 |
| Query | 查询条件、排序和分页输入 |

PO 不直接作为接口入参或返回值，查询条件不塞进 PO。创建与修改等字段或校验语义不同时分别定义 DTO；相同语义可复用，不机械复制。

### DTO、VO 与 Query 复用

- 每次新增或修改 DTO、VO、Query 前，必须先检索现有类型及 Controller、Service、Mapper 等使用位置，比较业务含义、字段类型、必填性、校验规则、使用边界和变化方向，由执行者判断该分还是该复用。复用的收益须大于引入的耦合及理解成本；不能因字段相同强行合并，也不能按接口、页面或动作名称机械复制。保留独立类型或新增公共结构都应有具体理由。
- DTO 的创建、修改、预览及提交输入语义相同时复用。完整资料或非秘密提案已有稳定结构时共用该结构，提交独有的版本、凭据或秘密字段仍留在对应输入中，预览不因此接纳秘密字段。
- 同时审视整个调用链的类型数量和转换层次，不能只把重复字段搬到父类后保留多余包装。包装职责一致、仅承载类型不同且能降低维护成本时，可用明确泛型或按已声明动作绑定具体提案；具体业务资料和必要类型边界仍应保留，不用无约束 Object、Map 或任意 JSON 代替明确结构。
- VO 的列表、详情及其他返回可以复用语义与可见范围一致的结构；详情只扩展实际需要的字段。不得为复用向列表、选项或低权限接口额外返回敏感字段。
- Query 还须核对搜索含义、默认值、分页、排序白名单和使用范围。相同查询直接复用，特有条件再扩展；相同人员筛选和排序规则只维护一份。业务服务继续负责各资源的权限和查询范围，不因共用 Query 放宽限制。
- 部分稳定业务结构相同时，按实际关系选择组合或浅层继承，并保持明确的接口字段结构；不为几个同名字段增加继承层级、空壳类型、大量可空字段或校验分组，也不抽象尚未出现的共用需求。
- 保留 DTO、VO、PO、Query 的职责边界。完成前主动复查本次变更及直接相关对象，统一必要调用位置，清理被替代的重复类、无用导入和残留引用；不能只看新增类本身或以编译通过代替复用检查。

### Lombok 与构造方法

DTO、VO、PO 和 Query 按已确认基础代码使用 Lombok `@Data`，按实际需要使用构造注解；分页参数沿用 `@Accessors(chain = true)`。不手写重复访问器，不机械改成另一套 record 数据类。密码、密码散列及其他秘密字段排除 `toString`；必要不可变的安全主体等内部类型按其约束实现。

Spring Bean 的依赖注入优先使用 Lombok `@RequiredArgsConstructor` 配合 `private final` 依赖字段，不使用字段 `@Autowired` 注入，不手写仅赋值的构造方法。Bean 仍通过 `@Service`、`@Component`、`@Bean` 等方式注册，构造注解不承担 Bean 注册职责。

构造过程有校验、转换或特殊注入要求时保留必要的显式构造方法，并遵守多行排版和方法注释要求。涉及多实现选择、配置值绑定时，核对生成的构造参数是否保留所需注入语义；不对所有类机械添加 `@Data`、无参或全参构造注解。构造生成规则见 [Lombok 构造注解](https://projectlombok.org/features/constructor)。

## 参数与请求体

- 同一业务动作的多项参数封装为 DTO 或 Query，避免接口方法和服务方法横向罗列大量独立参数；简单标识或少量明确参数可直接传递。
- 资源标识放路径参数；普通列表查询使用 GET，查询条件绑定 Query，分页与排序随 Query 管理。
- 创建、修改及包含结构化参数的业务动作使用 JSON Body 和对应 DTO；复杂嵌套或过长查询可使用明确的 POST 查询接口及 Query Body，不给 GET 塞请求体。
- HTTP 方法、分页响应、业务码和错误语义在接口契约中统一确定；封装参数不意味着所有接口一律使用 POST。
- 对外 DTO、VO 中可能超出 JavaScript 安全整数范围的长整型 ID 使用字符串，接收后在边界校验并转换；数量、金额等数值按自身语义建模，不全局将所有 Long 都改为字符串。
- 枚举类不直接作为外部入参类型。DTO、Query 接收契约约定的字符串或数字编码，校验合法值后转换为内部枚举；内部业务仍可使用枚举表达状态。

## 异常抛出与捕获

- 业务规则不满足时抛出明确的业务异常，普通 MVC 接口由统一异常处理器转换响应，不在每个 Controller 或 Service 重复 `try-catch`。安全过滤链的认证失败和拒绝访问由对应安全处理器处理，不能假定都能进入 MVC 异常处理器。
- 当前层能够恢复、执行有明确语义的补偿，或需要将底层异常转换为本层契约时才捕获；只捕获能处理的具体异常。资源释放优先使用 try-with-resources，必要的上下文清理由 `finally` 保证，不为清理而吞掉异常。
- 当前层不能处理且调用契约允许传播时，保留具体的 `throws`；不能为消除编译提示而随手捕获，也不能不分边界地层层添加 `throws Exception`。框架契约确有要求时按其约束处理。
- 转换异常时保留必要的原始原因，不静默忽略、不捕获后返回成功或无意义空值，也不在每层重复记录同一异常。统一响应和日志继续遵守敏感信息保护要求。
- HTTP 响应写出失败属于 I/O 故障；调用边界允许时向上传播 `IOException`。已经无法可靠写入响应时，不在同一响应中再次尝试写入错误 JSON，更不能将写出失败伪装为业务成功。

## 日志

需要日志的类统一使用 Lombok `@Slf4j` 和生成的 `log`，不手工声明重复的 Logger，不使用 `System.out` 或 `printStackTrace()` 代替日志；没有日志职责的类不为统一外观添加注解。用法见 [Lombok 日志注解](https://projectlombok.org/features/log)。

| 级别 | 使用场景 |
| --- | --- |
| `DEBUG` | 排查所需的分支判断、状态变化和必要诊断细节，控制循环与高频路径的输出 |
| `INFO` | 有排查价值的关键业务节点、任务起止及重要处理结果，不给每个方法机械记录进入和退出 |
| `WARN` | 需要关注的异常状态、重试或降级；正常参数校验失败、预期业务拒绝不机械升级为警告 |
| `ERROR` | 未预期且未能恢复的处理失败或系统故障，在负责处理的边界记录必要上下文和异常堆栈 |

- 日志说明发生了什么、关联哪个请求或业务对象、结果如何；按需要记录已有 `traceId`、业务标识、错误码和耗时，避免只有“执行失败”等无法定位的消息。
- 使用 `{}` 占位符传参，不拼接日志字符串；需要记录异常堆栈时，将异常对象作为最后一个参数，不只记录 `getMessage()`。参数化规则见 [SLF4J FAQ](https://www.slf4j.org/faq.html#paramException)。
- 同一异常在负责处理的边界记录一次，不在 Controller、Service、Mapper 层层打印堆栈，也不为打印日志额外捕获后原样抛出；已有统一请求日志时不重复记录相同内容。
- 日志内容遵守[安全执行与审计](../architecture/安全执行与审计.md)，不整包打印请求、DTO、PO 或业务结果。诊断日志不替代业务审计，不能用一次 `log.info` 代替应持久化的审计记录。

## 当前用户与线程上下文

- Java 业务代码通过 `UserContext` 统一读取 Spring Security `SecurityContextHolder` 中的当前登录用户；底层沿用框架的 ThreadLocal 机制，不再维护一套独立的用户 ThreadLocal。当前身份不由请求体、查询参数或普通请求头自报。
- 每次用户请求都先校验服务端登录会话，再建立认证上下文。登录接口设置一次上下文不能代替后续请求的恢复与认证，也不能假定同一用户始终使用同一线程。
- 请求正常结束或抛出异常后，认证上下文均由安全过滤链清理；自定义包装及异步边界使用可靠的 `finally` 清理或恢复原上下文，不能留下前一请求身份供线程池复用。缺少有效用户时按认证语义拒绝，不返回上一次用户或默认管理身份。
- 当前用户对象只保存用户 ID、登录名、姓名及必要登录会话关联和权限版本，不放密码、完整令牌或业务结果。功能、数据源、规则与资源状态按当前权威依据核验，不把登录时的权限快照当作长期通行资格。
- 请求内确需跨线程执行时，使用 Spring Security 支持的上下文委托或显式传递必要身份，执行完成后清理。不能依赖 `InheritableThreadLocal` 在线程池中自动传递用户；待异步结果返回也不能继续读取已经结束的原请求线程。
- 独立后台任务和 Java／Python 调用显式传递任务及必要业务身份，由接收方从可信任务关联验证归属与执行资格。不能持久化整个 `SecurityContext`、浏览器 Cookie 或用户实体来冒充任务身份，也不能把服务认证主体当作用户登录主体。

登录态、退出失效及服务凭据统一遵守[认证与身份上下文](../architecture/认证与身份上下文.md)。线程机制与安全委托依据见 [Spring Security 认证架构](https://docs.spring.io/spring-security/reference/servlet/authentication/architecture.html)及[并发支持](https://docs.spring.io/spring-security/reference/servlet/integrations/concurrency.html)。

## import 与类型引用

- Java 正常使用显式 `import` 后的短类名，不在业务代码中反复书写完整包名；避免通配符导入。同名类确实冲突时，才在必要位置使用全限定类名。
