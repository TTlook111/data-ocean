## Java 职责分层

| 包与类型 | 职责 | 边界 |
| --- | --- | --- |
| `controller` | 接收请求、绑定及校验参数、调用业务服务、组织响应 | 不直接访问 Mapper，不承载业务规则或数据库操作 |
| `service` | 声明业务服务接口与业务能力 | 不把 HTTP 请求对象当作业务入参 |
| `service.impl` | 实现业务流程、规则检查和事务协调 | 数据访问委托 Mapper，不把业务实现放回 Controller |
| `mapper` | 数据访问、映射与必要 SQL | 不承担接口响应、业务流程或权限授予决策 |

Controller 依赖 Service 接口，ServiceImpl 通过 Mapper 完成数据库访问。分层是职责边界，不要求每个框架 CRUD 方法再增加无意义的同名转发。

## 类名与文件名后缀

Java 文件名与其中的 public 顶层类型名一致，使用大驼峰命名，并在 `.java` 前保留明确的职责后缀。

| 职责 | 后缀规则 | 文件名示例 |
| --- | --- | --- |
| 接口控制器 | `XxxController.java` | `DatasourceController.java` |
| 业务服务接口 | `XxxService.java` | `DatasourceService.java` |
| 业务服务实现 | `XxxServiceImpl.java` | `DatasourceServiceImpl.java` |
| 数据访问接口 | `XxxMapper.java` | `DatasourceMapper.java` |
| 数据传输对象 | `XxxDTO.java` | `CreateDatasourceDTO.java` |
| 返回视图对象 | `XxxVO.java` | `DatasourceDetailVO.java` |
| 持久化对象 | `XxxPO.java` | `DatasourcePO.java` |
| 查询条件对象 | `XxxQuery.java` | `DatasourceQuery.java` |

`DTO`、`VO`、`PO` 统一全大写；`Controller`、`Service`、`ServiceImpl`、`Mapper`、`Query` 保持上述拼写。包名使用小写，Service 实现位于 `service.impl`。不同业务动作需要不同 DTO 时，在职责后缀前区分动作。

## entity 对象分类

按职责使用 `entity.dto`、`entity.vo`、`entity.po`、`entity.query`，不混用一个类承载所有层。

| 分类 | 用途 |
| --- | --- |
| DTO | 创建、修改、业务操作等结构化输入及必要的跨服务传输 |
| VO | 对外返回的详情、列表行及展示结果 |
| PO | 数据库持久化对象，承载表映射字段 |
| Query | 查询条件、排序和分页输入 |

PO 不直接作为接口入参或返回值，查询条件不塞进 PO。创建与修改等字段或校验语义不同时分别定义 DTO；相同语义可复用，不机械复制。

DTO、VO、PO 和 Query 按已确认基础代码使用 Lombok `@Data`，按实际需要使用构造注解；分页参数沿用 `@Accessors(chain = true)`。不手写重复访问器，不机械改成另一套 record 数据类。密码、密码散列及其他秘密字段排除 `toString`；必要不可变的安全主体等内部类型按其约束实现。关键业务逻辑的中文注释继续遵守共用总则。

## 参数与请求体

- 同一业务动作的多项参数封装为 DTO 或 Query，避免接口方法和服务方法横向罗列大量独立参数；简单标识或少量明确参数可直接传递。
- 资源标识放路径参数；普通列表查询使用 GET，查询条件绑定 Query，分页与排序随 Query 管理。
- 创建、修改及包含结构化参数的业务动作使用 JSON Body 和对应 DTO；复杂嵌套或过长查询可使用明确的 POST 查询接口及 Query Body，不给 GET 塞请求体。
- HTTP 方法、分页响应、业务码和错误语义在接口契约中统一确定；封装参数不意味着所有接口一律使用 POST。
- 对外 DTO、VO 中可能超出 JavaScript 安全整数范围的长整型 ID 使用字符串，接收后在边界校验并转换；数量、金额等数值按自身语义建模，不全局将所有 Long 都改为字符串。
- 枚举类不直接作为外部入参类型。DTO、Query 接收契约约定的字符串或数字编码，校验合法值后转换为内部枚举；内部业务仍可使用枚举表达状态。

## 当前用户与线程上下文

- Java 业务代码通过 `UserContext` 统一读取 Spring Security `SecurityContextHolder` 中的当前登录用户；底层沿用框架的 ThreadLocal 机制，不再维护一套独立的用户 ThreadLocal。当前身份不由请求体、查询参数或普通请求头自报。
- 每次用户请求都先校验服务端登录会话，再建立认证上下文。登录接口设置一次上下文不能代替后续请求的恢复与认证，也不能假定同一用户始终使用同一线程。
- 请求正常结束或抛出异常后，认证上下文均由安全过滤链清理；自定义包装及异步边界使用可靠的 `finally` 清理或恢复原上下文，不能留下前一请求身份供线程池复用。缺少有效用户时按认证语义拒绝，不返回上一次用户或默认管理身份。
- 当前用户对象只保存用户 ID、登录名、姓名及必要登录会话关联和权限版本，不放密码、完整令牌或业务结果。功能、数据源、规则与资源状态按当前权威依据核验，不把登录时的权限快照当作长期通行资格。
- 请求内确需跨线程执行时，使用 Spring Security 支持的上下文委托或显式传递必要身份，执行完成后清理。不能依赖 `InheritableThreadLocal` 在线程池中自动传递用户；待异步结果返回也不能继续读取已经结束的原请求线程。
- 独立后台任务和 Java／Python 调用显式传递任务及必要业务身份，由接收方从可信任务关联验证归属与执行资格。不能持久化整个 `SecurityContext`、浏览器 Cookie 或用户实体来冒充任务身份，也不能把服务认证主体当作用户登录主体。

登录态、退出失效及服务凭据统一遵守[认证与身份上下文](../architecture/认证与身份上下文.md)。线程机制与安全委托依据见 [Spring Security 认证架构](https://docs.spring.io/spring-security/reference/servlet/authentication/architecture.html)及[并发支持](https://docs.spring.io/spring-security/reference/servlet/integrations/concurrency.html)。

## import 与类型引用

- Java 正常使用显式 `import` 后的短类名，不在业务代码中反复书写完整包名；避免通配符导入。同名类确实冲突时，才在必要位置使用全限定类名。
