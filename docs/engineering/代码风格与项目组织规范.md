# DataOcean 代码风格与项目组织规范

本页是 React 前端、Java 后端和 Python AI 服务共用的代码与项目组织总则，适用于正式实现、原型及相关维护。每次开始新增或修改代码前必须阅读本页及相关端细则，完成开发前按本次变更逐项自查。各端细则补充语言和工程特有约定，通用原则只在本页维护。已确认的目标目录、模块及工具职责见[工程组织与版本基线](工程组织与版本基线.md)，实际实现定位和兼容工具组合随工程验证落实，不据此提前生成代码骨架。

## 命名清楚且统一

变量、函数、类、文件和目录准确表达用途，同一业务概念尽量使用一致名称。三端遵循各自语言的命名惯例，保持业务术语与接口字段含义一致；具体类型及文件后缀由各端细则明确。

导入集中放在文件约定区域，保持统一排序与分组，清理未使用和重复导入。Java 的显式导入、短类名及同名冲突处理见[Java 导入细则](../backend/编码规范.md#import-与类型引用)。

## 职责单一

页面、接口、业务逻辑、任务编排和数据访问各司其职，避免把过多职责集中在一个组件、类或方法中。围绕真实职责组织代码，不为拆分增加只转发调用、没有独立意义的层次。

## 合理复用与封装

优先复用已有业务能力、标准库、已选框架和适用工具，提取真正重复且稳定的公共能力，避免复制相同实现。单次使用不机械抽象，不为追求通用增加无实际需求的框架、配置入口或复杂度。

每次新增或修改接口模型、组件或业务能力前，先检索已有定义与使用位置，核对职责、业务含义、契约、约束及变化方向，由执行者判断拆分或复用是否值得。复用带来的维护收益高于耦合和理解成本时复用；职责、边界或独立变化需要分开时保留独立定义。接口、页面、动作名称不同本身不构成复制理由，字段相同也不构成强行合并的理由。

跨语言共享业务术语和接口契约，各端按自身类型和职责实现；公共组件不隐式增加业务规则或权限。Java 已确认的复用代码与适配要求见[公共代码复用](../backend/编码规范.md#公共代码复用)。

## 目录结构清晰

按业务模块组织代码，模块内部按职责分层，每个模块有明确位置。公共代码与模块专属代码分开，端内模块遵守同一套目录规则；前端、Java 和 Python 保留各自语言及工程惯例，不强行使用完全相同的目录层级。

目标目录遵循[工程基线](工程组织与版本基线.md)，实际实现定位随真实重构补充。Java 的 Controller、Service、Impl、Mapper 和 entity 分类沿用[Java 职责分层](../backend/编码规范.md#java-职责分层)及[对象分类](../backend/编码规范.md#entity-对象分类)。

## 工具类分类管理

跨模块使用的稳定通用工具集中管理，模块专用工具留在对应模块。工具目录不承载完整业务流程或不相关代码，不把尚未形成共用需求的能力提前搬入公共目录。

## 文件职责明确

一个文件或类围绕相对独立的职责组织。拆分依据职责、理解成本和依赖关系判断，避免文件持续膨胀，也避免按统一行数硬拆或过度拆分导致查找困难。

## 依赖方向清楚

模块之间通过明确接口协作，避免直接依赖其他模块内部实现和形成循环依赖。公共底层能力不反向依赖具体业务模块；专属实现不因被其他模块临时调用就自动成为公共能力。

Java 与 Python 按[服务职责与数据流](../architecture/服务职责与数据流.md)及[调用与任务协议](../architecture/调用与任务协议.md)协作，不通过跨端直接写业务表或复制授权逻辑绕过既定边界。

## 统一契约与规则归属

普通 JSON 返回、分页、错误码、日期及其时区语义、权限判断和日志遵循统一契约，模块通过所属规范引用，不各自定义一套。SSE 和文件响应遵循各自协议，不强塞普通 JSON 返回包装。

普通返回、分页、错误码和日期格式统一见[接口与事件契约](../architecture/接口与事件契约.md)，Java 复用细则见[公共代码复用](../backend/编码规范.md#公共代码复用)，任务和流式交付见[调用与任务协议](../architecture/调用与任务协议.md)，权限、凭据和日志见[安全执行与审计](../architecture/安全执行与审计.md)。后续模块在所属接口设计中补齐专属字段和错误码，沿用共用契约，不各自另定格式。

## 类型和边界明确

明确接口和数据的类型、字段及组合约束。前端校验提供及时反馈，服务端在可信边界校验实际输入和业务条件，不能只依赖前端。身份、权限和系统管理字段从可信上下文取得。

输入、返回、持久化和查询对象按职责区分，不用无约束的 Map 或 JSON 绕过本应明确的类型。Java 的 DTO、VO、PO、Query 和参数封装见[Java 编码细则](../backend/编码规范.md)。

## 完整状态与异常

按实际任务覆盖正常、加载、空数据、失败、无权限及重复操作等状态，清楚表达当前进度和实际结果。错误信息可理解且不泄露敏感信息，保留必要的受控诊断关联。

异步任务的接收、执行、取消、交付和恢复遵循任务协议，不能把请求成功当作业务完成，也不能用空结果掩盖异常。界面表达沿用[前端交互规则](../frontend/交互规则.md)，不在通用代码中另创状态含义。

## 配置与代码分离

按环境集中读取配置，环境差异通过配置表达，避免写死机器路径、地址及环境相关参数。真实连接密码、密钥等敏感信息不提交到仓库，保护与轮换按[凭据规范](../architecture/安全执行与审计.md#凭据保护与轮换)落实。负责人明确指定的开发示例账号按[开发配置](../backend/运行与验收.md#开发配置)随项目提供，不能据此将真实环境秘密入库。

构建与配置文件同样按可读性排版。XML（含 `pom.xml`）的父子节点分行并逐级缩进，不把完整嵌套结构或多个配置项挤在一行；长属性列表按属性换行。项目坐标、属性、依赖管理、依赖和构建等区块之间保留空行，相邻依赖、插件块之间也保留空行。

JSON/JSONC 的多字段对象和嵌套配置、YAML 的命令参数列表同样展开；TOML 按配置节分组，数组缩进保持一致。简短标量列表和空集合可保留单行。配置含义与顺序不因排版调整改变，锁文件及其他工具生成内容保留生成工具的格式。

## 注释覆盖与写法

前端、Java 和 Python 的每个手写代码块都必须写中文注释，说明该块的职责、业务用途或约束。覆盖类、函数、方法、组件、Hook、回调，以及条件分支、循环、异常处理、资源管理等逻辑块；嵌套代码块同样覆盖。模板或 JSX 的界面区块、样式规则块也要说明对应的界面职责或状态。正式代码、原型、测试与手写脚本遵守同一覆盖要求。

| 代码类型 | 注释写法 |
| --- | --- |
| Java | 方法和字段使用多行 Javadoc，块内逻辑使用独立行注释；具体排版及字段要求见[Java 编码细则](../backend/编码规范.md#排版与注释) |
| 前端 JavaScript / TypeScript | 类、函数、组件、Hook 和独立回调使用多行 JSDoc / TSDoc；内部逻辑块使用独立行注释，界面区块和样式规则块使用对应语法的注释 |
| Python | 模块、类、函数及方法使用中文多行 docstring；内部逻辑块使用独立行注释，异步函数和上下文管理代码同样覆盖 |

数据模型、接口类型和配置对象的每个手写字段都要说明业务含义，必要时注明单位、编码、取值及敏感性约束。其他成员变量和局部变量也尽量说明用途或来源，保持变量声明和逻辑步骤之间的清楚分组。

注释与代码分行，紧邻对应声明或代码块；说明职责、业务规则、设计取舍和约束，避免逐语句翻译语法。改动逻辑时同步修改相关注释，保持命名、实现和注释一致。工具生成内容由生成源维护，第三方源码沿用其自身约定。

## 自动检查与有效测试

使用统一的格式化和静态检查工具保持基础风格一致，选用与职责见工程基线，具体兼容版本和配置在各端工程验证时固定。提交前运行本次变更相关检查，如实说明未通过项及验证范围，不把静态检查通过当作真实接口或业务验收完成。

完成开发前，人工核对本次变更是否满足代码块和字段的注释覆盖、注释准确性、排版与空行、合理复用、异常边界及日志要求；Java 同时核对 Lombok 和 Bean 注入。格式化、静态检查或测试通过不能代替上述核对。

测试优先覆盖会改变业务结果的行为、安全边界、并发和异常恢复。低影响的格式调整以静态检查为主，避免只镜像实现而无法验证行为的测试；检查范围与变更影响相匹配。

## 测试与代码对应

各端统一测试目录和命名规则，按业务模块建立与被测代码的可定位关系，便于查找和维护。模块专属测试与共用测试辅助代码分开，测试数据和凭据使用受控样例。

测试目录及后缀按[工程基线](工程组织与版本基线.md#构建检查与测试定位)和各端细则维护，不要求三种语言使用相同布局。共用总则维护对应关系与验证原则，不复制具体路径和工具用法。

## 及时清理无用内容

在当前任务范围内清理已确认失效的代码、文件、无用导入和重复实现。删除前检查引用与影响，完成相应验证，保留用户并行修改，并利用版本管理追溯历史。无关清理另行处理，不在普通修改中顺手扩大重构范围。
