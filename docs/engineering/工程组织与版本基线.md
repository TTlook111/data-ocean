# 工程组织与版本基线

正式工程采用一个 Git 仓库、三端独立构建，Java 使用一个 Maven 应用按业务分包，Python 使用一个工程并分 API 与 Worker 进程运行。代码原则见[三端共用总则](代码风格与项目组织规范.md)，Java 专属规则见[Java 编码细则](../backend/编码规范.md)。

本页维护已确认的工程组织目标；React 与 Java 首批模块已进入实现，实际目录与覆盖见[源码定位](../source-map/README.md#首批正式实现)。下列完整目录包含尚未落地的目标，不能据此预建骨架或推定全部迁移完成。被替代代码的处理边界见[原型基准](../frontend/设计约定.md#原型基准与界面打磨)，具体迁移或删除仍按实施任务执行。前端和后端版本分别由所属入口维护，本页不复制版本数字表。

## 仓库与文档边界

```text
data-ocean/
├─ frontend/          React 正式工程
├─ backend/           Java 正式工程
├─ python-service/    Python AI 工程
├─ deploy/            基础依赖的 Docker Compose 与配置模板
├─ docs/              方案、架构、工程和接口文档
├─ prototypes/        离线交互原型
└─ tools/             实际需要的开发和维护脚本
```

三端分别使用 npm、Maven Wrapper 和 uv 构建。根目录只提供确有需要的开发辅助入口，不引入另一套重复构建逻辑。已有实现目录随真实代码维护定位，尚未落地的目录只在对应模块实施时建立。

接口文档纳入 `docs` 的渐进式体系，不另设根级 `contracts`。模块入口提供索引，接口专题按需记录路径、请求与返回字段、校验、事件及错误语义，公共约定只维护一份并引用。

设计阶段以已确认文档为依据；实现后由所属 Java/Python 服务生成 OpenAPI 等结构化描述，用于类型生成及一致性检查。生成内容不再手工维护，不以实现偏差反向修改已确认规则。接口描述生成与业务数据导出分别处理，业务数据导出仍由 Java 受控提供。

`tools` 仅保存真实需要的检查、文档生成或维护脚本。已有 npm、Maven、uv 命令能直接完成的工作沿用其原生命令；需要统一执行多个检查时只编排调用，不再实现一套检查规则。

## 本地运行与依赖环境

当前以本地启动和联调为主要运行方式。开发者自行在宿主机安装 JDK、Python、Node 及相应构建工具，Java、Python API／Worker 和前端开发服务在本机启动；基础依赖通过 Docker 容器运行。

宿主机工具按项目依赖的兼容要求选择，不要求本机安装的所有版本统一。JDK 遵循已定主版本，Python 与 Node 选用兼容范围内已验证的运行时，Maven 构建版本由项目 Wrapper 固定。允许多版本共存并仅为项目选择运行时，实际补丁和配套工具版本由工程配置及本机环境说明记录。

| 范围 | 已确认方式 |
| --- | --- |
| Java、Python、前端 | 在宿主机安装环境并使用各端原生命令启动；Python API 与 Worker 仍按既定职责分进程 |
| MySQL、Redis、Milvus 及必要配套依赖 | 通过 Docker 运行；现用[根 Compose 模板](../../docker-compose.yml)，正式交付目标为 `deploy/`，由使用者按所属项目及服务启动 |
| Compose 交付内容 | 固定兼容镜像版本，说明端口、持久化数据卷、配置项、启动停止及健康检查方法；模板不含真实凭据 |
| 版本与机器配置 | 版本分别引用[前端基线](../frontend/README.md#前端技术选型)与[后端基线](../backend/README.md#版本基线与验证边界)；本机路径、端口及凭据放私有配置 |

数据库及需要保留的 Redis、Milvus 数据使用持久化数据卷，具体参数按[存储边界](../architecture/存储与会话状态.md)落实。应用从本机外部配置读取依赖地址及受控凭据；现有机器的实际状态按 `.dataocean/local-environment.md` 核对，不将旧环境事实当作新版配置已完成。

本地共享基础设施保持独立的 Docker 项目归属：Redis 与检查点 Redis 归 `redis`，Milvus 及其 etcd、MinIO 归 `milvus`，MySQL 单独管理，不放入 DataOcean 应用分组。启动 Compose 时显式指定所属项目及服务；本机私有文件路径只维护在本机配置中。

基础依赖配置和[独立验证入口](../../tools/technical-validation/README.md)已可用，正式业务配置随各模块实现逐步落实。当前不预设生产规格、并发规模、集群副本或灾备时限，也不为未实施模块提前生成工程骨架。

## Java 业务模块

一个 Spring Boot 启动入口、一个 Maven 应用，业务模块先按包组织，不拆成独立服务或为每层建立一个 Maven 子模块。模块内部保留 Controller、Service、ServiceImpl、Mapper 和 entity 分类；根据实际业务创建所需文件，不为目录齐全建立空层次。

| 模块 | 职责 |
| --- | --- |
| `iam` | 人员、部门、角色、申请审批、授权来源与输出规则 |
| `datasource` | 连接、采集、元数据、结构变化和企业业务说明 |
| `governance` | 表字段、关联、指标及治理修订 |
| `knowledge` | 文档、题单、候选、发布、索引任务及生效清单 |
| `query` | 会话、请求、执行准入、结果交付和恢复协调 |
| `feedback` | 问题分派、处理、复验和结案 |
| `model` | 模型配置、节点分配和调用记录 |
| `audit` | 审计写入、查询及保护 |
| `dashboard` | 运营统计及看板查询 |

```text
backend/
├─ pom.xml
├─ src/main/java/com/dataocean/
│  ├─ DataOceanApplication.java
│  ├─ common/
│  ├─ infrastructure/
│  └─ module/<业务模块>/
│     ├─ controller/
│     ├─ service/impl/
│     ├─ mapper/
│     └─ entity/{dto,vo,po,query}/
└─ src/test/java/com/dataocean/
```

`common` 保存稳定通用的返回、异常、分页及工具能力；`infrastructure` 保存 JDBC、Redis、HTTP、加密等技术适配。权限来源合并、发布门槛和任务判定等业务规则仍在业务模块，不集中堆入公共目录。

模块通过明确的 Service 接口和传输类型协作，不依赖其他模块的 Impl、Mapper 或 PO。跨模块流程由明确的业务服务协调；需要双向通知时沿用任务与事件机制，避免互相注入实现形成循环依赖，不在 Java 重建 LangGraph 的 AI 节点编排。

审计记录使用引用和必要快照，不将完整业务原文复制成另一份事实；看板通过明确的统计查询能力聚合，不让其他业务模块反向依赖看板。实际接口依赖随详细设计检查，不能仅凭文件夹分开就宣称已实现模块隔离。

## Python API 与执行器

```text
python-service/
├─ pyproject.toml
├─ uv.lock
├─ src/dataocean_ai/
│  ├─ api/
│  ├─ worker/
│  ├─ workflows/
│  ├─ adapters/
│  ├─ schemas/
│  └─ core/
└─ tests/
```

| 位置 | 职责 |
| --- | --- |
| `api` | 命令接收与校验、登记入队、状态查询及 SSE，不在 HTTP 生命周期中运行整个图 |
| `worker` | 队列消费、执行资格、租约、取消和接管，驱动 LangGraph |
| `workflows` | 问数、治理、知识和反馈等实际 AI 工作流，各自维护节点、图状态、工具组合及提示词 |
| `adapters` | Java 受控接口、模型提供方、Milvus 和 Redis 的技术适配 |
| `schemas` | API 与 Worker 共用的稳定任务、命令和事件类型；工作流专属状态留在所属工作流 |
| `core` | 配置、日志、必要共用上下文等底层能力，不承载业务流程或另一套授权规则 |

API 与 Worker 使用同一代码包、同一 `uv.lock` 和同一发布版本，按本地运行方式在宿主机独立启动并配置并发。进程分离用于独立生命周期和执行容量，不增加一套独立业务系统。

任务协议版本、图及状态结构版本明确记录。API/Worker 升级前验证旧检查点兼容性，或先排空相关任务并按已定任务协议处理不兼容状态。`runVersion` 继续表示一次请求的执行代次，不能充当软件版本或状态结构版本。

## 前端工程

一个 React 工程包含后台与问数两个布局，保持问数独立界面，同时共享登录、请求和稳定基础组件。正式工程与当前离线 Vue 原型分开识别，不以正式选型推定原型已迁移。

```text
frontend/src/
├─ app/          路由装配、Provider 和布局
├─ modules/      各业务模块的页面、组件、接口和类型
├─ shared/       稳定共用组件、请求、SSE、hooks 和工具
└─ assets/
```

模块类型、hooks 和组件先随所属业务维护，形成稳定跨模块用途后再提取到 `shared`。前端不机械复制 Java 类文件组织方式，业务术语及接口含义保持一致。组件库、路由、状态管理及其他配套库已确认，职责与版本边界集中维护在[前端选型](../frontend/README.md#前端技术选型)。

## 构建检查与测试定位

| 端 | 构建与依赖 | 检查及测试定位 |
| --- | --- | --- |
| 前端 | npm，提交 `package-lock.json`，CI 按锁文件安装 | ESLint 检查代码质量，Prettier 负责格式；Vitest 与 React Testing Library 验证行为，组件测试相邻并使用 `*.test.tsx` |
| Java | Maven Wrapper 固定构建工具，BOM 管理配套依赖 | Spotless 负责格式和导入整理；命名等非格式检查使用经 JDK 17 兼容验证的检查配置；测试包对应源码包，单元测试 `*Test.java`、集成测试 `*IT.java` |
| Python | uv，提交 `uv.lock`，API 与 Worker 使用同一锁文件 | Ruff 统一格式与静态检查，pytest 按被测模块组织 `tests`，使用 `test_*.py` |

格式化与代码质量检查各司其职，关闭重复或互相冲突的格式规则。Java 插件、格式引擎和静态检查器分别核对 JDK 要求，不能只锁插件却让引擎自动升级。Checkstyle 及格式引擎的具体兼容版本见[后端版本与验证](../backend/README.md#版本基线与验证边界)，不将要求更高 JDK 的最新版直接加入基线。

本地与 CI 使用同一检查命令；按变更目录运行对应检查，跨端协议变化同时检查相关端的契约与事件兼容性。浏览器验收继续使用项目规定的 ego-lite，测试样例不代替真实 API 与业务验收。

## 版本维护与验证边界

前端具体版本只维护在[前端技术选型](../frontend/README.md#前端技术选型)，Java、Python、数据库及后端工具只维护在[后端版本基线](../backend/README.md#版本基线与验证边界)。本页与各端细则链接引用，不再保存另一份版本表。

三端独立构建，发布清单关联代码提交、协议及产物版本。需要更新时显式调整依赖并重新生成锁文件，验证后统一记录；不以浮动 `latest` 作为可重复发布依据。如使用镜像发布，版本与镜像摘要随发布物固定。

已认可的版本数字是工程验证基线，实际覆盖与验证边界分别见[前端实现状态](../frontend/README.md#当前实现与验证边界)和[后端版本验证](../backend/README.md#版本基线与验证边界)。独立最小链路的构建和运行通过不表示正式三端工程、全部精确版本或业务服务已经验收。依赖配置、持久化与保留参数继续按[架构待定项](../architecture/README.md#需要继续讨论的架构问题)落实。
