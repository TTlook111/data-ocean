# DataOcean 项目面试讲稿

> 适用场景：飞致云 / SQLBot 相关岗位面试  
> 项目角色：核心开发  
> 项目时间：2026.05 - 2026.06  
> 使用方法：不要逐字背诵。先记住“问题 - 方案 - 取舍 - 结果”四段式，再根据面试官追问展开。

## 一、先给项目一句话定位

DataOcean 是一个面向企业业务人员的 NL2SQL 智能问数与元数据治理平台。用户选择一个 MySQL 数据源后，可以直接用自然语言提问；系统基于经过治理和审核的元数据及业务知识生成 SQL，经过 AST 安全校验、行列级权限改写和只读沙箱执行后，返回表格、图表、SQL 与解释。

这个项目不是单纯的 Text-to-SQL Demo。它重点解决的是：

> 如何让大模型只基于可信知识，在明确权限内，生成可校验、可执行、可追溯的 SQL。

## 二、30 秒自我介绍版

我做的项目叫 DataOcean，是一个企业级智能问数与元数据治理平台。它的产品形态和飞致云 SQLBot 有相似之处，都是让业务人员通过自然语言完成数据查询；同时我也参考了 OpenMetadata 在元数据目录、术语、标签、血缘和治理方面的设计思想。

我没有把它只做成“把表结构塞给大模型生成 SQL”的 Demo，而是把可信问数作为核心：Java 负责用户权限、数据源、元数据治理、知识发布、审计和结果脱敏；Python 使用 LangGraph 编排 Query Rewrite、Schema RAG、SQL 生成、AST 校验、沙箱执行和图表生成。核心链路已经完成端到端联调。

我重点参与了 Agent 工作流、Schema RAG 与 `skills.md` 知识生命周期、sqlglot SQL 安全沙箱，以及 Java 与 Python 之间的查询链路。

## 三、3 分钟完整介绍版

### 1. 为什么做

企业数据库里通常有大量表和字段，业务人员不熟悉 SQL；即使使用大模型直接生成 SQL，也有三个明显问题：

1. 大模型不了解企业内部的指标口径、表关联关系和字段陷阱。
2. 原始元数据可能缺失、过期或本身就是错的，RAG 命中错误知识只会让错误更稳定。
3. Prompt 约束不是安全边界，生成的 SQL 仍可能越权、查询敏感字段或执行危险操作。

因此我把问题从“如何生成 SQL”重新定义为：

> 如何建设一条从元数据治理、可信知识发布、上下文召回、SQL 生成，到安全执行和审计反馈的完整链路。

### 2. 系统怎么分层

系统分为三层：

```text
Vue 3 前端
  查询端 + 治理管理端
          |
          v
Spring Boot Java 网关
  鉴权、权限、数据源、元数据治理
  skills.md 生命周期、任务持久化、审计、脱敏
          |
          | RestClient + SSE
          v
FastAPI Python AI 服务
  Query Rewrite、Schema RAG、SQL 生成
  sqlglot AST 校验与改写、沙箱执行、图表生成
          |
          v
Milvus / MySQL / Redis / Qwen
```

前端只调用 Java。Java 是企业管理和安全入口，Python 专注 AI、RAG 和 SQL 执行能力。这样不会让 Python 再维护一套用户、审批和持久化逻辑，也避免前端同时对接两套认证体系。

### 3. 一次查询怎样执行

```text
用户选择数据源并提问
  -> Java 校验身份、数据源权限和数据源就绪状态
  -> Java 创建并持久化查询任务
  -> Java 将权限上下文、最近对话和业务术语传给 Python
  -> Query Rewrite 消解指代、提取指标/维度/筛选条件
  -> Schema RAG 从当前数据源召回相关 Schema 和 skills.md 切片
  -> SQL Generator 生成候选 SQL
  -> sqlglot 做 AST 解析、白名单校验和权限改写
  -> 只读沙箱执行，失败时在受控次数内回到生成节点修正
  -> 根据结果生成 ECharts 配置
  -> Java 持久化任务、记录审计并执行最终脱敏
  -> 前端展示表格、图表、SQL 和解释
```

整个过程通过 SSE 返回节点进度，并支持超时和任务取消。

### 4. 我认为最有价值的设计

第一，RAG 的输入不是未经处理的原始 Schema，而是经过治理和审核的知识。

第二，`skills.md` 不是磁盘上的普通文件，而是有草稿、审核、索引和发布状态的业务语义资产。

第三，SQL 安全不依赖 Prompt，而是在 sqlglot AST 层做确定性校验和改写。

第四，查询产生的血缘、使用频率和用户反馈会回流到字段可信度与治理侧，形成闭环。

## 四、与 SQLBot、OpenMetadata 到底是什么关系

可以坦率地说“有借鉴”，但不要说“就是照着它们做的”。

### 1. 与 SQLBot 的关系

SQLBot 给我的主要启发是智能问数的产品闭环：

- 选择数据源后自然语言提问；
- 结合表结构、术语、SQL 示例和上下文提高生成准确率；
- 返回 SQL、数据明细和可视化图表；
- 支持多轮会话、历史记录和权限控制。

DataOcean 与它的共同点是都在解决企业智能问数问题，也都使用 LLM 和 RAG。

DataOcean 的侧重点更偏向毕业设计中的“可信治理链路”：

- 把元数据治理作为 RAG 的前置准入条件；
- 为知识文档设计审核、版本、索引、发布和失败回退状态；
- 把字段治理状态、可信度、权限和脱敏信息带入查询链路；
- 使用 LangGraph 显式编排可重试、可超时、可取消的执行流程；
- 使用 sqlglot AST 做 SQL 白名单、危险函数、LIMIT 和行列级权限改写。

推荐表述：

> SQLBot 是我在产品形态和智能问数流程上的重要参照。我重点研究了它如何把数据源、表关系、业务术语和 SQL 示例用于问数。DataOcean 没有复刻其代码，而是在相同问题域下，把 OpenMetadata 风格的元数据治理进一步前置到 RAG 和 SQL 执行链路中。

### 2. 与 OpenMetadata 的关系

OpenMetadata 给我的主要启发不是 NL2SQL，而是元数据治理模型：

- 数据资产目录与 FQN；
- 表级、字段级实体关系；
- 业务术语、同义词、分类和标签；
- 数据质量、血缘和下游影响分析；
- 审核、版本、状态和可追溯性。

DataOcean 没有试图实现一个完整的 OpenMetadata。OpenMetadata 面向多种数据资产和连接器生态，而本项目为了控制毕业设计范围，只做多数据源接入、单次查询限定一个 MySQL 数据源，并围绕 NL2SQL 保留必要的治理能力。

推荐表述：

> OpenMetadata 帮我建立了“元数据不只是表结构，而是带有语义、质量、关系、责任和生命周期的数据资产”这个认识。DataOcean 只抽取了对可信问数最关键的治理能力，并把这些信息直接用于 RAG 准入、上下文重排和 SQL 权限校验。

| 维度 | SQLBot | OpenMetadata | DataOcean |
| --- | --- | --- | --- |
| 核心定位 | 智能问数产品 | 元数据管理与治理平台 | 元数据治理驱动的可信智能问数 |
| 主要用户价值 | 自然语言查数与分析 | 数据发现、治理、质量、血缘 | 在可信知识和明确权限内完成问数 |

| 元数据治理 | 服务于问数配置 | 核心能力且覆盖面广 | 聚焦 NL2SQL 所需治理闭环 |

| 安全策略 | 产品级资源和数据权限 | 元数据操作权限 | AST 校验、行列权限、只读执行、Java 最终脱敏 |
| 项目范围 | 成熟开源产品 | 成熟开源平台 | 毕业设计，当前为 MySQL 单库多表 MVP |

## 五、四个最值得展开的技术难点

## 难点一：为什么不能把全库 Schema 直接塞给模型

### 问题

单库可能有几百张表。全量放进 Prompt 会造成 token 成本上升和注意力稀释，模型容易选错同名字段；只做向量相似度又可能漏掉 Join Path、指标口径等关键知识。

### 方案

我把知识分成 Schema 与 `skills.md` 两类：

- Schema 提供表、字段、类型、注释和治理状态；
- `skills.md` 提供 Join Path、指标 SQL 表达式、字段防坑和典型查询场景；
- Python 按二级标题、三级标题切成细粒度 chunk；
- 检索后根据查询意图、表名命中、字段可信度和知识类型进行重排；
- `JOIN_PATH`、`METRIC`、`FIELD_NOTE`、`QUERY_SCENE` 等类型有不同权重；
- Prompt 总预算固定，优先保留与生成 SQL 最相关的上下文。

### 取舍

只用向量相似度实现简单，但难以表达治理状态和知识类型；全量 Prompt 信息完整但成本和准确率不可控。因此采用“向量召回 + 规则重排 + token 预算”的混合策略。

### 可以继续追问的点

- 为什么 Join Path 要独立成 chunk？
- 表名或业务术语的精确命中如何与向量分数结合？
- RAG 不可用时如何降级？
- 如何评估召回质量？当前还缺系统化离线评测集，这是后续重点。

## 难点二：`skills.md` 为什么需要生命周期

### 问题

如果一点击发布就先删除旧向量，再写入新向量，那么 embedding 或 Milvus 写入失败会导致线上没有可用知识。另外 Java 和 Python 都做分块，会产生规则漂移。

### 方案

```text
DRAFT -> PENDING_REVIEW -> APPROVED -> INDEXING -> PUBLISHED
                                           |
                                           v
                                        APPROVED
                                     索引失败回退
```

- Java 管理文档、版本、审核、任务状态和 MySQL chunk 快照；
- Python 是唯一的分块与向量操作实现；
- 新版本先分块并写入带文档 ID 和版本号的向量；
- 校验 Milvus 实际向量数与 chunk 数一致；
- 验证成功后 Java 才切换活动版本；
- 最后再清理上一版本向量；
- 失败时恢复到 `APPROVED`，旧活动向量继续提供服务。

### 取舍

这相当于知识索引的“先写后切换”，多占用短时间的存储，但避免发布失败造成服务空窗。Java 保存 chunk 快照也增加了一份数据，但换来了预览、审计、重建和故障排查能力。

### 一句话总结

> 我把向量索引当成可重建的派生数据，把 MySQL 中的文档、版本和 chunk 快照当成可审计的事实记录。

## 难点三：为什么 SQL 安全不能只靠 Prompt

### 问题

LLM 输出不具备确定性。即使 Prompt 要求“只能 SELECT”，模型仍可能生成多语句、危险函数、越权表字段或超大结果集。

### 方案

使用 sqlglot 解析 MySQL AST，并建立确定性规则：

- 只允许单条安全 SELECT；
- 拦截 DDL、DML、多语句和危险函数；
- 限制子查询深度；
- 校验表白名单和不可用治理状态；
- 检查列级拒绝权限；
- 在 AST 上注入行级过滤条件；
- 没有 LIMIT 时强制加入 `LIMIT 10000`；
- 使用只读账号、只读事务、查询超时和连接池限制；
- 敏感列由 Python 标记，Java 返回前做最终脱敏。

### 取舍

SQL 字符串拼接实现快，但容易破坏括号、别名、JOIN 和子查询语义，所以权限过滤和 LIMIT 必须基于 AST 改写。Prompt 仍然用于减少错误生成，但它只是第一层引导，不是安全边界。

### 防守式回答

如果面试官问“这样就绝对安全吗”，不要回答“是”：

> 不能说绝对安全。当前是纵深防御：只读数据库账号是底线，AST 规则和权限改写是应用层控制，超时、行数和连接池是资源保护，Java 脱敏和审计是最后一层。项目仍需要持续补充 SQL 对抗用例和真实数据库权限配置验证。

## 难点四：Java 与 Python 为什么这样分工

### 问题

项目同时包含大量企业管理 CRUD 和 AI 工作流。如果所有功能都放在 Python，Java 项目的价值会被削弱，用户、审批、事务和持久化也会与 AI 代码耦合；如果全部放在 Java，RAG、LangGraph、模型 SDK 和 SQL AST 生态又不合适。

### 方案

- Java 负责确定性、强事务、长期状态：鉴权、权限、数据源、治理、审批、版本、任务、审计、脱敏；
- Python 负责模型相关和请求级执行：改写、检索、重排、生成、校验、执行、图表；
- 前端只调用 Java；
- Java 使用 RestClient 调用 Python，并消费 Python SSE；
- 会话由 Java 持久化，Python 每次接收请求范围内的最近对话，避免双写。

### 取舍

Java 代理会增加一次内网转发，但换来了统一认证、统一 API、明确的数据所有权和更容易审计的调用链。

## 六、可以重点讲的 Agent 设计

Agent 不是为了“用了 LangGraph”而使用 LangGraph，而是因为流程中确实存在状态、条件路由、重试、超时和取消：

```text
Query Rewrite
      |
Schema Retriever
      |
SQL Generator <-----------+
      |                    |
SQL Validator              | 执行失败且仍有预算
      |                    |
SQL Executor --------------+
      |
Data Visualizer
```

关键设计：

- `AgentState` 保存改写问题、检索上下文、候选 SQL、错误、重试次数和剩余时间预算；
- Validator 拒绝的是安全问题，不应盲目重试；
- Executor 的数据库错误可以带回 Generator 做有限次数修正；
- 每个节点都检查取消信号和剩余预算；
- 图表生成失败只降级为表格，不应让已成功的数据查询整体失败；
- Milvus 异常时可使用 Java 提供的 MySQL chunk 快照降级，并向用户标记结果处于降级状态。

## 七、STAR 项目故事

### 故事一：打通完整智能问数链路

**S - 背景：** 各模块分别完成后，端到端查询仍失败，问题横跨 Milvus、SQL 解析、序列化和 SSE。

**T - 任务：** 让 RAG 检索、SQL 生成、校验、执行和图表生成真正串起来，而不是只通过单元测试。

**A - 行动：**

- 定位 LangChain Milvus 旧接口与 `MilvusClient` 连接方式不兼容的问题；
- 统一检索结果 metadata 字段，修复写入和读取字段名不一致；
- 处理 SQL 尾部分号造成的校验误判；
- 修复 Decimal 查询结果无法 JSON 序列化；
- 在 SSE 断开时补充资源清理，避免任务残留。

**R - 结果：** 完整链路成功跑通，能够从自然语言问题得到真实 SQL、执行结果和图表配置。

### 故事二：修复知识发布的可用性风险

**S - 背景：** 强制向量化如果先删旧版本，再写新版本，一旦 embedding 或 Milvus 写入失败，线上检索会立即失去知识。

**T - 任务：** 保证知识更新失败时旧版本仍可用。

**A - 行动：**

- 将向量写入限定为 `doc_id + version_no`；
- 新版本写入后校验向量数量；
- Java 事务中切换文档和 chunk 状态；
- 切换成功后才清理旧版本；
- 失败时回退文档状态并保留旧向量。

**R - 结果：** 发布过程具备失败回退和版本级隔离，不再出现“更新失败导致线上知识被清空”的风险。

### 故事三：把权限从 Prompt 约束下沉到 AST

**S - 背景：** 只在 Prompt 中告诉模型“不能查某些表和字段”无法形成可靠权限边界。

**T - 任务：** 让权限对模型输出具有强制性。

**A - 行动：**

- Java 计算当前用户的数据源、表、列和行级权限；
- 将明确的权限协议传给 Python；
- Python 在 sqlglot AST 上检查表列并注入行过滤；
- 敏感字段随结果返回标记，Java 执行最终脱敏；
- 修正 allowlist 为空和 unrestricted 两种语义容易混淆的问题。

**R - 结果：** 权限从“希望模型遵守”变成“生成后必须通过的确定性规则”。

## 八、面试官高概率追问

### 1. 为什么 MVP 只做 MySQL 单库多表？

系统可以接入多个 MySQL 数据源，但用户每次必须明确选择一个数据源，查询只在该库内进行多表关联。

这是主动收缩，不是没考虑跨库。跨库会引入 SQL 方言、同名字段语义冲突、分布式执行、跨源权限和事务边界。毕业设计阶段先把治理、RAG、安全和查询闭环做深，比表面支持很多数据库更有价值。

### 2. 字段可信度怎么用？

可信度不是直接决定 SQL 正确与否，而是作为字段选择和 RAG 重排的辅助信号。初始值来自注释、治理状态和知识文档；后续根据成功查询、字段使用和用户反馈调整。它不能替代审核，也不能让低可信字段自动变成禁止使用，禁止状态由 `BLOCKED`、`DEPRECATED` 和权限规则控制。

### 3. 为什么 Java 最后还要脱敏？

Python 负责根据权限标记敏感列，但 Java 是用户身份和权限的最终所有者。把最终脱敏放在 Java，可以避免 AI 服务或执行链路的遗漏直接把敏感数据返回给前端，符合纵深防御。

### 4. 为什么不用数据库原生 RLS？

原生 RLS 安全性更强，但不同数据库实现差异较大，而且项目需要支持由平台动态计算的用户、角色、部门和临时审批策略。当前 MVP 使用 AST 改写，同时要求业务库账号只读。生产环境中可以将高价值固定策略进一步下沉到数据库原生权限。

### 5. 为什么用 Milvus？

项目从一开始就把 Schema 和业务知识作为独立向量资产管理，需要按数据源、文档和版本过滤，也需要后续支持混合检索和规模增长。Milvus 比轻量内存向量库增加了部署成本，但更符合项目的服务化和版本化目标。

### 6. 为什么不用 Elasticsearch 做向量检索？

当前项目已有明确的向量检索需求，Milvus 更专注于向量存储和 ANN 检索。元数据目录的关键词搜索与 RAG 是两类问题。MVP 不为了“技术栈丰富”再引入一套搜索基础设施；后续如果目录搜索规模和过滤需求上升，可以评估 Elasticsearch 或 Milvus Hybrid Search。

### 7. 你怎样证明 SQL 是正确的？

AST 校验只能证明 SQL 在语法和安全规则上可接受，不能证明业务语义一定正确。业务正确性依赖：

- 治理后的 Schema 与业务术语；
- 审核过的指标口径和 Join Path；
- 执行错误反馈重试；
- 返回 SQL 和引用上下文供用户解释；
- 用户反馈和离线评测集。

目前项目已经验证完整链路，但系统化准确率评测仍是明确的后续工作，不能把“链路跑通”等同于“准确率达到生产标准”。

### 8. 这个项目里 AI 帮你做了多少？

推荐诚实回答：

> 我使用 AI 辅助需求拆解、方案比较、样板代码和代码审查，但架构边界、数据模型、状态机、安全规则、模块集成和问题定位需要我理解后决策。我能解释代码为什么这样写、哪里有风险，以及如果重新设计会怎么改。对我来说，AI 是提高实现速度的工具，不是替代工程判断。

### 9. 如果重新做一次，你会先改什么？

我会更早建立一套可重复的 NL2SQL 评测集，覆盖：

- 单表、多表 Join、聚合、时间范围、排序和 TopN；
- 术语同义词、错误字段、歧义问题和多轮追问；
- 越权表列、SQL 注入、危险函数和超大查询；
- RAG 召回率、SQL 执行正确率、回答正确率和 P95 延迟。

当前实现先把平台链路和治理能力做全，测试数量不等于智能问数质量，缺少评测集会让 Prompt 和检索策略的优化缺乏统一基准。

## 九、项目不足与诚实边界

主动承认边界反而更像真正做过项目：

- 已完成端到端链路，但真实企业数据集上的准确率评测还不充分；

- OpenMetadata 的连接器生态、资产范围和成熟度远超本项目，DataOcean 只实现了服务 NL2SQL 的治理子集。

## 十六、RAG 分块优化：标题切割的局限与改进

> 如果面试官追问"按标题切分有什么问题"或"怎么处理其他格式文档"，用这一节回答。

### 1. 当前方案的问题：按标题切割为什么不够好

项目中 `skills.md` 的切割方式是 Python `chunker.py` 按 `##` / `###` 标题层级分割。这个方案简单可控，但确实存在几个明显局限：

**问题一：层级语义断裂。** `##` 和其下的 `###` 是父子关系，切割后变成孤立的 chunk，父子之间的上下文依赖被切断。

**问题二：跨章节引用丢失。** 第三章可能引用第一章定义的概念或指标口径，但两个章节的 chunk 在向量空间中没有任何关联——模型检索到第三章的 chunk 时，看不到第一章的定义。

**问题三：短小节信息密度不足。** 某些 `###` 小节内容很短（一两句话），单独作为 chunk 缺乏足够语义信息，检索时分数不稳定。

**可以这样对面试官说：**

> 目前我们用的是最简单的按标题切分，好处是规则明确、可复现。但标题和标题之间存在层级关系和跨章节引用，单纯切开会丢失这些语义连接。我在项目里做了一部分补偿——比如 reranker 里按 chunk type 加权、检索时带相邻 chunk 做上下文扩充——但要根本解决这个问题，后续有几个方向值得考虑。

### 2. 改进方向（面试时可以挑两三个讲）

| 方法 | 核心思路 | 适合场景 |
|---|---|---|
| **语义分块 (Semantic Chunking)** | 基于 embedding 相似度判断断点：相邻句段语义相近则合并，出现语义跳变时切断。LangChain 有 `SemanticChunker` 实现 | 对话、长文等自然段落 |
| **递归字符分割 + 滑动窗口** | 按 `\n\n` → `\n` → `。` 逐级尝试分割，保留 10-20% overlap。相邻 chunk 共享上下文，弥补边界损失 | 通用文本，工程成熟 |
| **Small-to-Big / 父子检索** | 索引时用小块做精确匹配，检索时返回包含该小块的大块（父 chunk），保证返回结果有完整上下文 | 需要精确检索 + 完整上下文的场景 |
| **图结构索引 (Graph RAG)** | 把 chunk 之间的关系建成图（如同一个 `##` 下的小节互连、术语与定义关联），检索时做邻居扩展或子图遍历 | 知识之间有显式关系的场景 |
| **上下文扩充 (Context Expansion)** | 检索到匹配 chunk 后，自动把前后相邻 chunk 一并捞回，拼成完整上下文送入 LLM | 最简单有效的补偿方案，当前项目已采用 |
| **命题化重写 (Proposition Chunking)** | 先把文档拆成独立、自包含的原子命题，每个命题不依赖上下文就能理解，再对命题建索引 | 学术前沿方向，适合高质量文档 |

### 3. 多格式文档处理：Unstructured

**面试官可能会问："除了 Markdown，PDF、Word 这些文档怎么处理？"**

业界有一个非常成熟的开源方案：**[Unstructured](https://github.com/Unstructured-IO/unstructured)**（GitHub 10k+ star）。

**核心能力：**

- **格式覆盖广**：支持 30+ 文档格式——PDF、HTML、DOCX、PPTX、Markdown、CSV、图片（OCR）、邮件（.eml）、Epub、Notion 等，一套 API 全部搞定。
- **版面分析 (Layout Detection)**：自动识别标题、正文、表格、图片、列表、页眉页脚，对 PDF 这种无结构文档尤为重要。
- **多种分块策略**：
  - `basic` — 规则分块
  - `by_title` — 按标题层级分块（和我们的思路一致）
  - `by_page` — 按页分块
  - `by_similarity` — 语义相似度分块
- **表格提取**：自动将文档中的表格提取为 HTML/CSV 结构化数据，这在企业文档处理中特别有用。
- **标准流水线**：Partitioning（分区）→ Cleaning（清洗）→ Staging（暂存）→ Chunking（分块），每个阶段可插拔。

**推荐的面试表述：**

> 目前我们的项目以 Markdown 为主，按标题分块足够了。但如果要接入 PDF 手册、Word 需求文档、Confluence 页面这类多样化数据源，按标题分块就行不通了——这些格式本身没有可靠的标题结构。业界有一个很成熟的开源项目叫 **Unstructured**，GitHub 上 10k+ star，它支持 30 多种文档格式的自动解析和智能分块，底层用到了版面分析模型来识别文档结构，能处理表格、图片、多栏排版这些复杂场景。它的流水线设计也很好——分区、清洗、分块各自解耦，可以按需替换其中任意一环。如果后续 DataOcean 要扩展数据源类型，Unstructured 是首选的文档解析前端。

### 4. 精排 (Reranker) 模型选型

**面试官可能会问："精排你们用了什么模型？还有哪些可选？"**

精排的作用：粗召回（向量检索 Top-N）→ 精排模型逐对打分 → 按相关性重排。这是 RAG 检索质量提升最显著的一环。

**主流模型/服务一览：**

| 模型 | 类型 | 特点 | 适用场景 |
|---|---|---|---|
| **BGE-Reranker-v2-m3** (BAAI) | 开源 Cross-Encoder | 多语言（中英），轻量高效，C-MTEB 榜单前列 | 中文场景首选 |
| **BGE-Reranker-v2-gemma** (BAAI) | 开源 Cross-Encoder | 基于 Gemma，效果更强但模型更重 | 追求极限精度 |
| **bge-reranker-large** (BAAI) | 开源 Cross-Encoder | 经典版，中英双语，存量项目广泛使用 | 稳定可靠选择 |
| **Jina Reranker v2** | 开源/API | 多语言，支持 8K token 上下文 | 长文档重排 |
| **Cohere Rerank v3** | 商业 API | 效果好，免部署，按量付费 | 不想自建精排服务 |
| **mxbai-rerank** (MixedBread) | 开源 Cross-Encoder | 基于 DeBERTa，英文为主 | 英文场景轻量选择 |
| **ColBERT** 类 (late interaction) | 开源 | 延迟交互范式，预先计算 token 级 embedding，检索时做细粒度匹配 | 不是严格精排但思路相近 |

**选型建议（对面试官可以这样说）：**

> 精排模型的选型我建议分两条线考虑：
>
> **开源自部署线**：首选 **BGE-Reranker-v2-m3**，中英文多语言，HuggingFace 直接下载，Cross-Encoder 跑在 GPU 上推理延迟很低（单条几十毫秒），在中文场景效果在 C-MTEB 榜单上排名靠前，BAAI 团队也持续维护。
>
> **商业 API 线**：如果不想维护模型服务，**Cohere Rerank v3** 或 **Jina Reranker API** 都很成熟，按调用量付费，集成成本低。
>
> 在我们项目里，除了模型精排之外，还加了一层**业务规则重排**——不同类型的知识 chunk（JOIN_PATH、METRIC、FIELD_NOTE、QUERY_SCENE）根据查询意图获得差异化权重。这种"规则 + 模型"的混合策略在垂直领域往往比纯模型重排更可控、更可解释。

**现有项目的 reranker 实现（可以翻代码验证）：**

项目 `python-service/dataocean/rag/reranker.py` 已实现：
- 按 chunk type 权重加成（JOIN_PATH、METRIC、FIELD_NOTE、QUERY_SCENE 等）
- 按表名命中、字段可信度、查询意图进行结果重排
- 配合 Prompt token 预算做上下文截断
