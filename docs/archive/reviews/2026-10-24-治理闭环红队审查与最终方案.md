# 治理闭环红队审查与最终方案

> 历史参考／非现行合同；现行依据见文档导航。


> 2026-10-24；对象为[用户确认的治理目标](../../development/字段语义治理与问数反馈闭环改造目标.md)及当前工作树。结论来自代码静态路径核对和失败场景推演，未实施接口攻击、写库或新的运行验收。本文件是修正后的实施合同；下列修正尚未因此自动实现。原轮次测试与真实 AI 记录继续保留各自边界。

## 用户授权后的实施更新

用户随后明确要求实施修改，已将下列反例补为失败回归并修复：业务公式完整依赖、整组业务事实遗漏、AI 覆盖原始依据、新修订提前结案、过期执行回写、同 SQL 换措辞/换用户重复贡献，以及字段审核缺少明确原始资料确认。实施证据与边界见[红队补强记录](../../acceptance/治理闭环TDD实施记录.md#2026-10-24-红队补强)。下文审查表保留发现当时的依据，不再将已补强项笼统理解为全部仍未实现。

当前落地选择保持简单：公式采用现有解析器的受限语法白名单，不猜测别名或未限定字段；发布/构建按当前全量有效业务事实严格比对，不新增任意省略清单；修复结果采用绑定原情景与预期值的明确人工验收，不宣称已有自动业务回放引擎；旧评分政策留档，规范化 SQL 样例用于新政策参考分；大快照超过预算时明确拒绝一键治理并提供单对象工作面，尚未实现任意规模的分片调度。知识复查与 RAG 生效继续分别显示，失效知识保持阻断，不增加旧口径降级。

## 审查结论

产品方向成立：平台内治理知识，由 AI 整理候选、人工确认、程序复核，生成多篇可追溯文档，RAG 消费稳定知识，查询期读取独立档案，反馈驱动再治理。业务源始终只读。

当前最危险的假设是：流程走通就说明知识正确、SQL 使用字段就说明该字段应承担差评、出现新修订就说明原问题已修复。现有测试和 14 个 AI 候选只能证明特定路径可执行，不能证明上述假设成立。当前版本应按“核心实现与有限接口验证”定位，不能称为全链路业务正确性验收通过。

## 对抗性发现

P1 表示会影响知识可信性、反馈关闭或关键使用链路，需优先修正；P2 表示在特定运行规模或使用方式下暴露。下表区分直接可见的实现缺口与尚待复现的运行边界。

| 发现 | 对抗场景与后果 | 当前依据与判定 | 修正要求 |
| --- | --- | --- | --- |
| P1：AI 可以同时写结论和“依据” | 模型猜测“金额单位为元”，再生成一段貌似可信的 evidence；人工只看流畅文字就批准 | `BusinessKnowledgeServiceImpl.generate` 将模型返回 evidence 写入修订；提交主要检查依据非空。静态确认缺少结构化外部证据强绑定，不等于已证明某个候选伪造 | 输入依据与 AI 推断分开；依据引用固定文档/术语/人工确认记录及版本，AI 不得自创权威来源；缺单位或基数依据保留待确认 |

| P1：计分去重易被绕开且无场景区分 | 同一人改问题措辞/SQL 格式或换账号反复赞踩；支付场景好评掩盖退款场景错误 | `evidenceKey` 使用 userId、问题原文、SQL 原文、definition/revision；分数按该修订整体聚合。只保证精确重复不多计，未证明独立证据或业务场景有效 | 区分去重与独立性，使用规范化 SQL/任务根来源及场景证据；限制同源贡献，异常意见隔离待审；展示样本量和来源集中度，不把反馈比例称为正确概率 |
| P1：新知识有效与 RAG 生效之间有空窗 | 新版本复查使旧事实失效，新 build 尚未确认，新问数可能停止；若偷偷回退则使用旧口径 | 当前系统有严格 membership 和独立显式 build 确认，应保持阻断；此为状态衔接与可用性边界，未做真实切换复现 | 展示“待发布/待构建/已生效”；普通替换预先准备并验证整组，再经明确确认切换；撤权/封禁/撤销即时阻断，绝不靠旧知识降级绕过 |
| P2：租约过期后旧 worker 仍可能回写 | 多实例或进程暂停超过租约，新 worker 已领取，旧 worker 恢复后看见 AI_RUNNING 又写入 | `processQueued` 用状态 CAS 和固定租约，回写未匹配本次领取令牌。单实例正常运行不等于故障恢复安全；尚未复现 | 每次领取唯一 executionToken 或递增 fence，候选落库和任务完成均核对；过期结果保留审计但不能改变当前任务 |
| P2：任务行被复用会丢轮次语义 | 同一字段多次反馈覆盖任务 origin/baseRevision，几条未解决反馈与某次修订混在一起 | 当前按快照/字段唯一，queueFeedback 更新已有任务；审计存在不等于轮次/反馈对应已完整建模 | 保留稳定对象入口，增加明确轮次或关联事件，不要求重复建工作区；每条反馈有独立修复关联，旧轮次不可覆盖 |
| P2：大范围治理消耗失控 | 大库一次扫描大量字段，N+1 读取及事务变长，随后生成大量付费候选；重复人工重试持续消耗 | discover 遍历整快照，worker 每次两个对象但未见按本轮总预算限制。吞吐限制不等于费用或事务上界；未压测 | 先预览数量/适用前提，按页扫描及短事务，设置本轮任务/调用/时间上限和暂停；超限保留已完成结果，不新建基础设施 |

## 修正后的最终方案

### 1. 以知识对象为主线，规则只负责发现与验证

治理对象为数据源、表、关系、指标与字段。字段档案包含业务定义、独立角色标签、使用条件、单位/枚举、来源修订及使用证据。关系包含完整条件、基数、时间适用性和聚合风险；指标包含粒度、公式、过滤、去重、单位及时间口径。无需强迫不适用字段填写所有内容。

来源质量规则继续检查原始结构及合规只读数据；知识治理规则检查资料缺口、冲突、适用条件与证据。检查项是可执行能力，规则是对它的配置。规则不能从“名称像金额”直接推导单位，更不能把未知变成错误或默认事实。

### 2. AI 整理候选，人工确认业务事实，程序核验合同

链路固定为：发现缺口 → 资料整理/AI 候选 → 人工补充与确认 → 精确修订复查 → 本轮形成可追溯结论。

将源注释、外部/平台业务资料、人工确认和 AI 推断明确区分。来源记录包含标识、版本/摘要、适用时间、必要片段与确认人；AI 可引用、不能捏造来源或把自己的解释当证据。只有元数据无法确定的内容保留未知并提供平台内补录。输入注释、文档及反馈属于不可信数据，不能改变系统指令或模型权限；输出仍经 schema、依赖、权限与来源校验，不能只依赖提示词防注入。

复查报告分别显示“程序可验证条件”“人工确认的业务口径”和“尚无法验证项”。合同有效和人工确认不能包装成数学意义上的业务正确证明。沿用现有审核权限，不擅自增加强制双人流程；同一人/同一资料的确认也不能冒充多份独立证据。

### 3. 反馈必须绑定具体修复，才能结束再治理

固定关联：原反馈 → 原任务最终受保护 attempt/SQL hash → 实际资源和知识修订 → 归因对象/原因 → 修复任务 → 新修订差异 → 对应验收证据。

修复前先确定判定方式：如“退款订单不得参与实付统计”“明细连接后订单总额不能重复”“分转元只做一次”。优先使用合成数据或人工确认的业务样例作确定性回归；需要读取业务数据时只能复用已授权的平台只读能力，不扩大样本权限，也不要求用户操作数据库。

当前规则复查通过只完成知识合同核验。原反例未消除、修订只变文案或没有可核验修复目标，反馈继续待验证；证据足够后才结束该问题。撤回反馈、认定非问题、无法归因、业务修复通过和系统失败分别有原因，不能靠“新 revisionId”统一关闭。

### 4. 文档是稳定知识的投影，发布以完整清单为准

保留多篇：数据源概览、表用途/粒度、关系与连接注意事项、指标专题、字段说明。每篇引用确切知识对象与修订，文案编辑保留；改变单位、关系或公式必须回到知识修订，不能在正文中另立口径。

每个发布组冻结 scope、预期事实/修订集合、文档版本集合、完整依赖与明确排除项。逐篇验证真实性与权限，整组验证无遗漏/错版/冲突；不能仅统计字段覆盖。允许按业务范围明确排除，但展示部分覆盖，不能声称原范围全部治理完成。

审核发布和显式 RAG 构建继续独立。新集合经验证后再切活动指针，保留在途引用；普通知识替换可预先准备，状态必须明确。安全撤销/撤权即时生效，若没有合规版本则提示不可用或澄清，不使用过期事实继续运行。

### 5. 置信度只表达版本和场景下的使用证据

保留独立证据账本，不在正文内存放动态分数。身份为对象 + 来源/语义修订，场景证据至少记录指标/问题类别与原因；初期不建立复杂的任意多维加权体系。

用户只需评价结果，可选原因。归因可以涉及多个字段、关系或指标，未知保持未知；没有反馈不加分。实际使用是候选责任范围，不是根因证明。与目标无关的字段不能因为低分被替换，也不能因高分获得权限。

当前 `(正向+1)/(总数+2)*100` 降为带版本的试行参考分，界面同时展示有效证据量、独立来源及负向问题。未经业务样例校准，禁止作为自动批准、禁用或语义选择的硬阈值。先补齐证据独立性、场景和归因，再决定是否需要更复杂的评分模型。单纯分数变化不生成新文档或重建向量。

### 6. 运行恢复、范围和产品呈现形成一致合同

任务按对象和明确轮次留痕，AI 执行有领取令牌、幂等结果和预算，超时/失败可恢复且不覆盖人工修改。重试是当前版本上的新执行，不复活过期结果。治理资料不足、部分完成、不适用和执行失败分别呈现。

全程使用同一公共数据源/快照范围，显式范围不一致时停请求。用户看到对象、缺什么、依据、下一步与待验证问题；审核细节/来源对比/历史按需展开。分别显示知识已确认、文档已发布、RAG 已生效及反馈已验证，不用一个“完成”覆盖四种不同结果。

## 必须补齐的 TDD 验收门槛

| 反例 | 预期结果 |
| --- | --- |
| AI 生成漂亮解释及自行声称的依据，无可核来源 | 仍是候选/待确认，不能单靠非空 evidence 取得确认资格 |
| 未限定字段、别名、子查询或公式引用未声明资源 | 完整解析并绑定依赖；解析不支持则禁止成为可执行口径 |
| 删除唯一关系/指标文档，但表字段仍全部覆盖 | 发布组/构建确认与执行均报告缺少具体事实，不切活动指针 |
| 差评后仅改标点得到新修订并通过形式校验 | 原反馈仍待验证，不显示已修复 |
| 一对多连接导致金额重复 | 定位关系/粒度问题，不自动扣正确金额字段的语义分 |
| 同一来源改写提问或 SQL、多账号集中意见 | 不被当成多份独立验证；来源集中/异常可见，可隔离审核 |
| 新知识准备期间、构建失败、旧版本被安全撤销 | 状态可解释，安全失效立即阻断；不混用新解释/旧 build |
| worker A 过期，B 领取，A 随后返回 | A 无权改变当前候选与任务结论，B 结果不被覆盖 |
| 大快照、预算用尽、部分模型失败或撤权 | 有限工作量、部分结果保留，未执行对象和下一步清晰可见 |

上表是原审查提出的验收门槛。后续实际补强及红绿结果以实施记录为准，未实现的自动回放等扩展不能借用已通过计数。原建议实施顺序：先证据可信/依赖解析/业务发布清单/反馈验收绑定，再完善场景归因和证据防重复，最后补任务故障恢复与大范围限制；保留已有安全边界与不相关工作树修改。

完成标准是：一条错误知识可被发现，一次错误结果可被归因，一次修订能用原问题验证，一次发布能证明完整且合规；无法判定时，系统诚实地保留未知。
