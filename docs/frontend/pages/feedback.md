# 用户反馈与持续改进页面

模块首项为独立的反馈概览 Dashboard，图表、时间范围及统计口径见[看板页面](dashboard.md#模块-dashboard)。具体核查、分派和验收仍从问题队列与处理进入。

正式队列可按问题摘要或编号、数据源和状态搜索。来源和负责人放在更多筛选中，收起后显示已应用条件数。四个队列分组保留在结果面板内，每条事项同时显示问题摘要、编号、下一步与最近更新时间。原问、反馈原因和查询证据在详情中按权限展示。

详情继续使用核查与处理、原问题与证据、记录与回告三页签，页签正文滚动，底栏保留实际可用动作。操作记录先呈现动作和时间，操作者、负责人和对应依据在下方按字段对齐。业务知识负责人记录核查后，从原数据源的知识文档、标准题单和发布与版本办理，回事项提交已发布版本和覆盖依据。复验人用原问题发起真实问数，回看答案后登记结论。结案人核对接收人与固定模板，原提问人从问数工作台右上角的铃铛定位原问。详情返回沿用原筛选、页码和事项焦点。

协调者可在已分派事项的「处理任务」新增治理、技术或源数据任务。任务行显示负责人、当前状态和实际可用的动作，当前「已做工作」和「下一步安排」并列展示。已有跟进记录时，任务使用「更新进展」打开并回填当前可见内容。已提交的处理结果和复验可展开回看。任务操作记录带事项内编号，结案和回告继续从主事项办理。源数据复验可人工只读核对或使用原问题只读问数。任务规则见[处理、复验与回告](../../backend/feedback/处理结果复验与回告.md#同一事项的独立处理任务)。

正式事项详情展示用户补充和原事项关联。后台选定原问后请求补充，提问人从该问数卡片回复。主负责人可在待回复记录上选择「撤回补充请求」或「无法取得补充」，填写处置原因后结束该条等待。原问卡片显示对外结果，已打开的旧回复表单随之失效。合并表单可主动查找同源相似事项，也可按编号或摘要搜索。选择候选后，继续核对主事项和合并依据并确认。合并记录可进入主事项或凭依据纠正。已结案事项可凭新证据重开，「记录与回告」保留各轮历史。回告收件箱为同一人本轮各条仍可访问的原问提供定位。[办理接口与权限](../../backend/feedback/处理结果复验与回告.md#用户补充合并与重开)

业务含义见[模块解说](../../product/modules/07-feedback.md)及方案第 7 章。下表只负责前端页面、动作和状态表达；当前进度见[原型状态](../原型状态.md)，共用控件与布局见[设计约定](../设计约定.md)。

提问人的反馈入口、进度和回告就近放在独立问数工作台；后台负责问题队列及处理流程，不能用后台办理入口取代员工侧进度。

| 页面或区域 | 使用者职责 | 必要动作与流转 | 权限与状态边界 |
| --- | --- | --- | --- |
| 反馈与问题队列 | 具备对应任务处理或分流权限者 | 搜索、筛选与查看线索 → 核对归属并分流 → 进入获派的治理或技术处理 | 点踩、知识缺口、技术失败和巡检区分来源，分派不扩权 |
| 核查、处理与验证详情 | 对应业务或技术处理者、验证者 | 查看有权证据 → 记录核查与处理 → 关联治理修订或技术修复 → 复验 → 结案并回告可公开结论 | 反馈是线索，先核实再修改；解释结案不冒充修复，未验证不能声称完成 |

当前原型覆盖问题队列与办理主链，复用后台表格、分页、核对表单和任务页。默认展示摘要或编号、数据源、状态；来源、负责人和日期收在更多筛选中，已用条件保持展开，各字段匹配取交集。待我处理、我负责的、全部事项与结案回看保留适用条件，状态选项随分组联动。待我处理按当前可执行动作计算；等待用户补充或其他任务负责人提交的事项保留在我负责的，必要任务已提交或退出后不再冒充本人待办。必要补充未齐时，新增、提交或退出任务不解除等待，也不能登记验收为通过；目标用户补充后回到处理。下一步核对核查、任务和当前验收条件，时间明确显示最近更新，详情返回保留查询、有效页码、焦点和滚动。PC 小窗口保留常驻菜单、桌面表格及表内横向滚动。

反馈功能统一复用角色权限，页面不配置人员或数据源处理范围。查看角色允许查看队列基础信息；主负责人记录核查，当前任务负责人提交处理结果。建立、调整处理任务须有分派功能，协调者通过重新分派调整责任，不代交他人结果。技术人员无需业务查询权即可办理获派任务；业务原文、用户原因及内部明细仍沿已有数据访问和证据功能核对，SQL 另行核权。受限标题、补充问题、验收明细、处理结果、历史、跨页上下文和预填使用同一可见内容投影；分派不增加查询访问。数据源仅作为问题所属来源和列表筛选条件。

单事项详情分为核查与处理、原问题与证据、记录与回告。用户原话、评价变更、核实根因与核查依据分别表达，原因未明可留空。请求补充明确原提问人和具体缺项，用户在原问卡片补充后回写同一事项。说明并结案直接可见，不能将解释或未复现计为解决。

处理任务分治理、技术、源数据三条路径。误建或无需变更任务由主负责人或分派协调者填写依据、核对剩余影响后退出，保留范围记录与恢复入口；仍有未覆盖影响不能退出。所有任务均退出时仅可说明结案。退出、恢复、重新分派、结果修订或范围变化均使旧验收失效。已提交任务的详细结果收起回看，待办原因在固定底栏可见，可定位到对应任务。

治理任务继续链接既有治理、文档、题单与发布页面；选择器同时展示业务解释、对象路径、修订与确认状态。可复用任务创建前已发布的有效修复，核对原回答实际引用、覆盖范围、对象身份与当前有效发布，不强制制造新治理修订。相同原引用且没有实际修复不能冒充解决。

技术和源数据任务以独立的阶段框展示排查跟进、等待生效和已处理生效。箭头位于框间留白，当前阶段指向下一阶段的箭头使用主色。初次办理默认为排查跟进。排查和等待阶段只显示已做工作及下一步，使用「保存进展」，等待记录留在「我负责的」。已生效阶段显示修正说明、复查方式与实际结果及生效确认，使用「提交处理结果」。源数据还记录实际修正人或团队。已有工单、发布、批次或链接可填入相关处理记录。关联问题只读显示，复验依据由办理人另行填写。切换阶段保留本次输入，提交只采用当前阶段的字段。

验收继续按影响分级：治理任务沿用既有发布关联表单、候选回归及生效后复验；技术区分展示、连接及查询安全，后者必须有相关场景测试记录与通过确认。完成记录提交后进入待验证，独立人工验收仍需实际结果和范围；跟进记录不能验收为解决。改回跟进会撤回待验证结果，历史结果、跟进、转派和重开记录均保留。受限跟进与结果明细使用同一证据权限，实际源系统修改及外部测试仍未对接。

已解决、其他结案、已合并分别表达。其他结案记录真实原因与依据；同源重复事项合并保留原反馈和回答，可凭依据纠正。各原事项的必要补充仍在主事项展示并阻止提前验收，用户分别补齐；补充归回原事项，纠正合并后继续保留。知识修复核对全部关联原回答的确切版本，不能把其中仍被质疑的同一版本作为修复。合并详情保留返回队列与原记录焦点。新证据重开保留任务结果、退出记录、结案、验收及回告轮次。事项版本变化拒绝旧表单覆盖。

点踩、知识缺口和技术失败从问数进入统一队列；点赞只追加评价，不单独建事项。结案预览展示受控模板和接收人，内部自由结论不进入回告；按结案类型和真实原因形成模板，发送与历史回看重新核对当前问数及源访问。账号停用不发送，失权只显示受限提示。确认结案后演示产品内回告投递；失败、结果待核查、账号不可用及受限内容单独保留，重试不重复处理或发布。同一人同一完成轮次合并一条回告，关联的各条原问可单独定位；无原问记录时明确不可用。问数展示后台统一进度，已关联事项不再使用旧的快速模拟办理入口。回答引用独立于界面序号，重置问数后不误关联旧回答。

问题队列与处理页直接展示查询与事项列表，不再设置模块内导航页签；待我处理、我负责的、全部事项和结案回看继续作为列表分组。事项详情保留核查与处理、原问题与证据、记录与回告三个页签，完整承接问题办理。

反馈评审快照限当前标签页；后台与问数往返交接已保存的治理、知识及发布状态，返回后继续办理原任务，刷新后台仍重置上述演示状态。浏览器后退复用旧页面时同步较新的反馈与已读状态，保留原回答和后台工作上下文。后台交接不作为问数知识依据，检索仍只取正式可用内容。跨模块衔接不代表跨标签页实时同步、真实认证、通知投递或服务端事务已实现。验证范围见[原型状态](../原型状态.md)。
