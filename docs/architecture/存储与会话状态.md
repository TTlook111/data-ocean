# 存储与会话状态

MySQL 保存业务数据和会话历史，Redis 保存 LangGraph 检查点并承担缓存与临时协调，Milvus 保存向量及检索所需元数据。Java/Python 的应用职责见[服务职责与数据流](服务职责与数据流.md)，技术栈见[后端设计](../backend/README.md#已确认的技术栈)。本页维护已确认的存储边界与身份层级，不定义物理表或具体部署参数。

## 存储分工与写入归属

| 存储 | 保存内容 | 管理与写入归属 |
| --- | --- | --- |
| MySQL | 人员、角色、部门、申请与授权、数据源配置、元数据快照、治理修订、业务说明、知识正文及片段、题单、发布记录、反馈、模型配置及必要调用记录 | Java；Python 通过 Java 接口读取业务依据、提交生成成果，不直接写业务表 |
| MySQL | 会话与消息、历史摘要、问数请求及待派发状态、SQL 候选与检查记录、数据库执行任务、限量结果快照、答案及审计 | Java；作为会话历史、业务任务和执行事实的持久记录 |
| Redis | 用户登录会话、必要认证关联及按用户定位会话的索引 | Java 通过 Spring Session Redis 管理；与业务对话、Python 检查点及其他用途分开命名和授权 |
| Redis | LangGraph 状态快照、通道数据、待完成节点写入、暂停位置及恢复所需状态 | Python 通过 Redis Checkpointer 管理 |
| Redis | Redis Streams 任务队列、缓存、限流、临时锁、并发协调、任务心跳及短期进度与文字事件 | 按用途划分命名空间和访问职责；关键结论与执行事实仍由 MySQL 保存 |
| Milvus | 知识片段向量、反馈问题向量，以及数据源、文档、片段、修订、索引代次和 Embedding 配置等检索元数据 | Python；正式发布与当前使用控制由 Java 管理 |

MySQL 是 DataOcean 平台库，不复制企业业务库作为平台事实库。企业业务数据仍经 Java 使用只读账号受控读取。原始凭据通过受控秘密引用管理，不进入会话消息、图状态、向量元数据或普通日志。

秘密的加密、引用与轮换，以及查询执行事实和管理审计的可靠提交，统一见[安全执行与审计](安全执行与审计.md)。审计不复制完整业务结果，具体保留与清理沿所属业务政策执行。

会话历史、业务任务和 SQL 执行去重记录不依赖 Redis 检查点保留。检查点清理或缓存失效不删除 MySQL 中的业务事实与历史，也不能据此重新执行已完成任务。具体保留期限、容量及清理机制仍待确定。

知识正文、片段和修订由 MySQL 保留，Milvus 中的向量及检索数据可由确切来源与匹配模型配置重建。MySQL 生效清单、检索代次、Embedding 匹配、当前使用控制及产物清理统一见[知识版本与索引一致性](知识版本与索引一致性.md)，向量命中不构成发布或读取许可。

## 用户会话与请求层级

本节“会话”指业务对话。浏览器登录会话由 Spring Session Redis 管理，退出、失效及时限统一见[认证方案](认证与身份上下文.md#用户登录与服务端会话)，不以登录会话 ID 代替 `conversationId` 或 `requestId`。

业务归属和访问校验顺序为：`userId → conversationId → requestId`。

| 标识 | 含义 | 归属与约束 |
| --- | --- | --- |
| `userId` | 当前登录用户 | 由 Java 从可信认证上下文取得，不使用请求体自报的用户编号作为当前身份 |
| `conversationId` | 一段连续业务对话 | 每个会话归属于一个用户，一个用户可以有多个会话；会话保存消息和摘要 |
| `requestId` | 一次独立问数请求 | 每个请求归属于一个会话，记录本次意图、数据源、预算、执行和结果；请求编号全局唯一 |

Java 在查看历史、提交补充、取消、重新查询或恢复时，核对当前用户、会话归属及请求与会话的关系，再核验当前账号、数据源授权和输出限制。内部工具调用也通过可信任务关联取得上述身份，不能仅凭传入编号读取任意会话或检查点。层级表达归属关系，不要求将三个编号拼成一个字符串；编号全局唯一也不能替代归属校验。

## LangGraph 线程与多轮关系

每个问数请求对应一个可恢复的 LangGraph 线程，`thread_id` 复用全局唯一的 `requestId`。Python 使用 Java 验证后传入的任务身份和请求上下文，不能把 LangGraph 的线程编号当作用户认证。

- 补充原请求的缺项或恢复尚未终结的流程时，沿用原 `requestId` 和 `thread_id`；用户补充可以新增消息，不因此新建执行请求。
- 同一会话中的新一轮问数创建新的 `requestId` 和 `thread_id`。重新查询或等待到期后的继续查询也创建新请求，并保留与原请求的关联，不覆盖原答案或复用旧执行许可。
- 多轮上下文由该用户会话的历史、最近五轮完整对话及更早摘要组装，并按当前权限和数据源过滤；跨请求记忆不依赖重复使用同一 `thread_id`。
- 单次请求只使用一个数据源。同会话切换数据源时隔离相关上下文，不能混用前一数据源的对象、证据或执行资格。

会话历史属于 MySQL 业务记录，Redis 检查点记录一次请求的图运行状态；两者通过用户、会话和请求的可信关系关联，保留与清理策略分别管理。

## Redis 检查点的持久化与恢复边界

复用与正式 LangGraph 版本兼容的 `langgraph-checkpoint-redis`，不另行实现 MySQL Checkpointer。按适配器要求具备 RedisJSON、RediSearch 能力，具体 Redis、LangGraph 与适配器版本在工程选型时核对；参考 [Redis Checkpointer](https://github.com/redis-developer/langgraph-redis)及 [LangGraph 检查点](https://docs.langchain.com/oss/python/langgraph/checkpointers)。

检查点由适配器保存状态快照、通道数据及 pending writes，不能仅保存一段聊天文本。图状态保留必要的意图与时间锚点、依据及模型修订、剩余预算、候选及执行任务引用；大结果保存在 Java 管理的结果记录中，检查点保存必要引用。

检查点存储须满足进程重启与故障恢复要求，并防止被普通缓存淘汰。Redis 的持久化、备份、可接受的数据丢失窗口，以及检查点与可淘汰缓存的隔离方式在部署设计时确定；Key 前缀或逻辑库划分不等同于独立的持久化和淘汰策略。未设置 TTL 只表示不自动过期，不代表已经配置可靠持久化，参见 [Redis 持久化](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)。

当前本地验证将登录会话、队列与检查点分到两个 Redis 实例及独立数据卷；Checkpointer 使用其独立实例的 DB 0。两实例启用 AOF、每次写入同步落盘、禁止自动淘汰，并拒绝静默加载截断 AOF；具体参数由根 Compose 配置维护。共享基础设施按 `redis` / `milvus` 等独立 Docker 项目组织，不归入应用项目；机器路径、私有环境文件和容器名覆盖配置只留在本机配置中。

冷备在 Redis 停止后复制完整数据目录，包括 AOF 清单及各文件，记录 SHA-256；恢复先校验摘要，使用匹配版本和模块在隔离卷中验证检查点，再按 MySQL 任务事实判断恢复资格。还原出来的历史检查点不能重跑已经完成的任务。本地 SIGKILL 与隔离备份还原的运行依据由[本机环境说明](../../.dataocean/local-environment.md#验证入口与依据)定位，AOF 增量验证程序见[验证说明](../../tools/technical-validation/README.md)，不等同于整机断电、磁盘损坏、跨机灾备、容量或性能验收。

检查点过期和清理须与任务生命周期协调，不能提前清除仍具恢复资格的请求。Java 中的请求终态、等待到期时间和当前权限决定是否允许恢复，Redis 中仍有快照不代表可重新运行终结请求。

恢复时，Java 先核对用户、会话与请求归属，以及请求状态、当前权限、数据源、知识有效性、既定时间条件和剩余预算。Python 再继续相应未完成节点；已启动的数据库任务通过 Java 核实实际状态，已完成时复用原结果，未知状态不盲目重发。Redis 检查点不代替 MySQL 执行记录、幂等和权限核验。接管执行代次、事件重放、取消与故障分类遵守[调用与任务协议](调用与任务协议.md)，事件游标过期不等于图检查点丢失。

## 待细化与验证

存储落点、身份层级和上述本地 Redis 持久化与隔离配置已落实。仍需确定保留清理策略、附件原文件存储、物理模型和容量要求，并补充真实业务及主机级故障验证；本地合成验证的结果不扩展为正式业务验收。

实现时须验证追问暂停后重启恢复、SQL 已完成但回调中断、多用户及多会话隔离、同会话多请求互不覆盖、撤权或到期后拒绝恢复，以及检查点写入失败时不错误推进任务。
