# 系统架构

系统职责与主要机制已确定，正在细化正式实现，前后端业务重构尚未开始。技术栈与工程组织见各端入口；当前采用宿主机应用与独立 Docker 基础依赖，本地持久化和最小故障恢复已有验证。待落实项为物理数据模型、逐接口契约、正式工程配置、容量与保留策略。

## 已定选择与待定事项

- 正式前端框架、组件库、路由、状态管理、表格表单、图表、SSE 客户端及样式方案已确认，统一见[前端设计](../frontend/README.md#前端技术选型)；原型继续使用现有依赖，真实重构尚未开始。
- 后端采用 Java 与 Python，具体框架与存储选型见[后端技术栈](../backend/README.md#已确认的技术栈)，版本及验证边界只维护在[后端基线](../backend/README.md#版本基线与验证边界)。三端代码原则见[共用总则](../engineering/代码风格与项目组织规范.md)，Java 特有约定见[编码细则](../backend/编码规范.md)。
- 已确认[工程组织与版本基线](../engineering/工程组织与版本基线.md)：单仓库、三端独立构建、Java 单 Maven 应用按业务分包、Python 同包 API/Worker 分进程、前端后台与问数共用工程。接口契约归入渐进式 docs，工具脚本按需维护；正式工程组合仍待验收。
- 已确认[本地运行与依赖环境](../engineering/工程组织与版本基线.md#本地运行与依赖环境)：应用在宿主机运行，基础依赖已有 Compose 模板，按独立 Docker 项目管理。容量与灾备指标按实际部署需要确定。
- 已确认[服务职责与数据流](服务职责与数据流.md)：前端统一访问 Java；Java 负责业务、权限和受控数据访问，Python 负责 Agent、模型调用和 AI 编排。
- 已确认[存储与会话状态](存储与会话状态.md)：MySQL 保存业务数据和会话历史，Redis 保存 LangGraph 检查点并承担缓存与临时协调，Milvus 保存向量；身份按用户、会话、请求逐层校验，问数 `thread_id` 复用全局唯一的 `requestId`。本地独立检查点 Redis、AOF 及故障恢复已有验证证据；保留、容量和正式运行参数仍需细化。
- 已确认[认证与身份上下文](认证与身份上下文.md)：Spring Security 与 Spring Session Redis 管理 Cookie 登录会话，Java 通过 UserContext 读取请求线程用户；明确退出失效、SSE 认证、Java／Python 服务 JWT 及受限只读文件凭据注入，具体接口和配置仍待实现验证。
- 已确认[调用与任务协议](调用与任务协议.md)：HTTP JSON 命令、独立后台任务与 SSE 事件流；关键结果和状态写入 MySQL，短期事件保存在 Redis。明确命令幂等、执行代次、重放与快照、取消确认、分层超时和失败恢复；连接断开不重新执行任务，SQL 状态未知时先核实。
- 已确认[知识版本与索引一致性](知识版本与索引一致性.md)：知识与索引分别版本化，MySQL 管理唯一生效清单；完整范围事务切换、Embedding 配套变更、独立暂停禁止、直接上一版回退及在途固定绑定。初期知识检索采用 Strong 一致性，具体布局和容量仍需验证。
- 已确认[安全执行与审计](安全执行与审计.md)：Java 统一执行与交付检查，多层只读校验、真实输出含义追溯、权威权限版本与主动撤权、秘密加密及引用、关键变更与审计一致提交。方言、中文规则能力和具体保护实现仍需验证，不以模型结论代替授权。
- 方案里的逻辑对象、字段和技术参考用于说明设计输入，不是物理建表、框架选型或服务拓扑。正式架构应明确选用什么、用途、必要理由和约束；不沿用旧系统技术作为默认答案。
- 架构评估时需明确代表性数据规模、并发与响应目标、模型部署及信息发送边界、任务和历史保留、故障恢复要求。已确认业务约束直接沿用；尚无依据的具体数值列为待确认输入，不把示例预算或旧系统实测当作新系统承诺。

## 需要继续讨论的架构问题

| 优先顺序 | 需要确定的内容 | 影响 |
| --- | --- | --- |
| 1. 本地运行约束 | 实际样例数据量、任务并发配置、模型服务连接与信息发送边界，以及本机端口和可用资源 | 为本地联调和验证提供依据，不将示例负载扩展为生产容量要求 |
| 2. 存储实现与保留 | 基于已验证本地 Redis / Checkpointer 组合，继续细化保留清理策略、备份保留与容量、主机级故障恢复；附件原文件落点及数据容量 | 沿用独立实例与已验证 AOF 配置，补齐真实业务和主机故障边界，不把进程故障结果扩展为完整灾备验收 |
| 3. 接口与任务实现细化 | 按已定协议及认证方案定义逐接口路径、DTO、事件结构和错误码；认证过滤链与会话配置、执行代次与租约、具体重试时限和事件保留参数 | 将已定方案落实为可核验契约，验证接管、幂等和并发竞争，不重选已确认通信与认证方式 |
| 4. 知识索引实现细化 | 生效清单字段、代次与 Embedding 身份判定、Milvus 布局、构建校验、并发切换、活跃引用与清理参数、Strong 检索性能 | 落实已确认发布与回退机制，验证可见性、兼容性和保留边界 |
| 5. 安全实现细化 | 解析器与驱动覆盖、视图函数依赖、中文规则核验能力、资源取消能力、权限并发控制、密钥托管轮换、审计结构及保护清理实现 | 落实已确认执行和审计边界，用真实受控场景验证拒绝、撤权与失败处理 |
| 6. 本地启动与工程验证 | 在最小链路基础上完成正式三端依赖、工具及应用配置，验证真实界面与业务服务 | 已有基础依赖配置继续复用，按正式实现验证可重复构建与运行，不将合成程序结果扩展为业务验收 |

下一步细化物理模型与逐接口契约，补齐正式工程配置、容量、保留及故障恢复边界。已确认的应用职责、存储落点、认证、任务、知识一致性及安全审计机制继续沿用；实际部署服务器时再确定资源与运维要求。
