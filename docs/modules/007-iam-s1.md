## 管理员需要理解的模型

角色管功能；部门默认数据与个人/角色数据授权管可查数据；后台角色绑定的负责源管管理范围。后台管理操作必须在同一个角色绑定上同时满足功能与负责源，不能把不同绑定的功能与源做并集相乘。普通问数用户不要求拥有后台负责源，其可查询数据由独立数据授权决定。

系统管理员负责后台管理，不自动获得业务查询数据。查询、查看 SQL 和导出功能在角色配置，数据授权不重复这些开关。记录条件、有效期与禁止规则按需展开，不重新引入旧策略数字优先级或复杂委派。

## 必须保留的决定

- 授权只读独立 S1 事实；不读取、映射、回填旧角色、旧 JWT 权限或旧缓存。没有双读双写或拒绝后的旧权限回退。
- B6 已退休旧权限专用链，不能按历史 RBAC/Policy 方案恢复。账号、部门、资产、会话、审计等业务数据继续保留。
- 54 项固定功能目录是消费边界，前端不能自造权限码。
- 注解切面 `IamS1AuthorizationAspect`必须同时保留 `@Aspect`与 `@Component`；显式 Guard 的专用 S1 接口仍需保留。
- 当前仍使用 JWT 黑名单与令牌版本。没有替代机制的执行证据前，不删 tokenVersion；历史冻结清单里的目标名不是已实现事实。
- 跨环境迁移、bootstrap、授权初始化和 B6 删除必须独立核对；旧手册中的准备轮授权不延续到今天。

## 旧权限退役与保留边界

旧 `sys_permission`、`sys_role`、`sys_user_role`、`sys_role_permission`、`datasource_access`、`datasource_access_policy` 及其专用 Controller、Mapper、Resolver 已退役。S1 不读取旧 JWT 权限数组，不从旧授权映射或回填新授权，禁止新旧权限双读兜底。其他环境的删除仍需核对真实引用、替代链路和独立授权，不能照历史对象清单直接执行。

保留账号及密码安全、真实部门、数据源及密钥生命周期、元数据与知识版本/chunk/Milvus、会话/查询结果、业务审计与通知，以及全部已执行的 Flyway migration 和 schema history。通用 AST、只读 SQL、连接池和内部服务令牌基础设施继续保留。`permission_change_log`、`access_approval_request` 仅保留只读历史，不参与 S1 授权或产生新临时授权。保留记录不等于保留访问权，新角色绑定、负责源与数据授权通过 S1 正常建立。

JWT 黑名单和 `tokenVersion` 当前仍承担会话失效，替代机制未实现并验收前不得删除。如有实际迁移或恢复需要，安全条件见[跨环境变更与恢复边界](../development/本地开发与验证.md#跨环境变更与恢复边界)。

## 执行和读取

执行 wire 的行谓词使用 columnId，管理/候选 DTO 仍使用 columnMetaId。未在投影中的策略依赖单独放入 policyColumns，Java 验证实际元数据归属、快照、表/列身份与治理可用性。它不加入模型 schema 或用户 SQL 可见列；原 SQL 仍按原权限验证，只有服务端行条件注入及注入后结构复测消费该依赖。实际使用与来源保持原用户 SQL，不能把策略字段或 COUNT 授权锚点拿来计分。共享 AST 拒绝 FOR UPDATE/FOR SHARE 等锁子句。实际行列组合见[扩展联调](../acceptance/2026-10-29-扩展联调.md)。

Java 在提交、每次候选 SQL 执行前、最终结果保护以及任务/历史/SQL/CSV/反馈/SSE 读取时按相应动作检查当前权限。Python 消费请求级绑定快照，执行检索过滤、SQL AST 和参数化行条件；不维护第二套权限事实。

前端通过能力摘要控制可见性和提示，能力摘要失败要显示错误。管理 `/api/iam-s1/datasources`与业务 `/api/iam-s1/query-resources/datasources`用途不同，不混用来扩大查询范围。

账号登录或退出时，前端使已验证的数据源、快照与 S1 能力缓存失效，选择偏好只在当前账号 API 重验后恢复；旧初始化、历史详情和能力响应不能回填新会话。401 按请求所属会话处理：旧账号及匿名请求迟到不清除新会话，当前会话的真实 401 仍使登录失效。这只保护前端显示和会话归属，不替代后台 S1 鉴权、独立数据授权，也不构成真实多角色验收通过的证据。

字段解释继续使用现有功能码：查看 `governance:field:view`，创建/编辑/AI/采纳/提交/撤回需要同一数据源上的 `governance:field:manage` 与 `knowledge:manage`，审核需要 `governance:field:view` 与 `knowledge:approve`，撤销需要 `governance:field:manage` 与 `knowledge:approve`。引用已审核术语另需 `glossary:view`；语义复查用 `governance:check`，问题处理用 `governance:issue:manage`。没有为系统联调新增功能码；隔离合成账号/绑定的实际范围在当轮记录列示。前端显隐不取代 Java 每项实际源校验。

治理任务、业务知识、档案与反馈入口同时保留功能级准入和实际源服务守卫。业务知识动态 actions 逐动作区分维护与审核，不要求维护者同时拥有审核权。本人反馈/目标读取使用 query:use 的范围入口，再核对任务归属及当前权限。

已审核术语条件需按布尔逻辑和每次物理表扫描证明必然成立，不能以 OR/NOT 分支中出现同一条件作为通过。完整全量授权与条件授权按 OR 合并，部分字段的全量授权不扩大其他字段；标量子查询须继承外层 FILTER/JOIN 用途，不能借投影绕过脱敏字段用途限制。

### 资源归属与接口动作

- 术语范围区分 `UNBOUND`（确无关联）、`BOUND`（关联源可核验）和 `BROKEN`（有关联但归属损坏）。`BROKEN` 不能当空关联全局放行；多源术语的写入和审核逐源全量校验，目标实体以真实归属为准。
- HTTP 方法不直接决定权限语义。只读 POST 仅按完整方法与路径逐项白名单核对：`POST /api/admin/knowledge-docs/{id}/preview-chunks`、`POST /api/admin/business-knowledge/{id}/source-status`；不得把所有 POST 视为只读，也不得从查看权推导其他写入权。真实映射、注解和列表范围由 `IamS1EndpointCoverageTest` 核对。
- 知识文档的历史版本、关联任务与来源快照统一通过 `KnowledgeOwnershipValidator` 校验；缺失或错属不能借请求中的源 ID 放行。生成请求先核对 datasourceId 与 snapshotId 的真实归属，再读取元数据或调用 Python。
- 访问审批锁定 `PENDING` 申请，拒绝本人审批；批准范围只能是申请子集，必须有期限且不超过申请期限或 30 天上限。审批时重新核对当前权限，显式 DENY、隐藏及禁止/废弃对象不能借临时授权绕过。具体实现见[临时访问审批](iam/临时访问审批.md)。
