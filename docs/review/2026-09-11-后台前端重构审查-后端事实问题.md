## 1. P0：知识文档回滚可绕过审核直接入库

### 现象

`KnowledgeVersionServiceImpl.rollback()` **完全不校验文档状态**，也不校验目标版本是否曾经通过审核或被发布过。任何调用方都可以对一份 `DRAFT` 文档执行回滚，把任意历史版本的内容直接置为「索引中」并触发向量化任务，跳过「提交审核 → 审核通过 → 发布」全流程。

### 证据

`backend/DataOcean/src/main/java/com/dataocean/module/knowledge/service/impl/KnowledgeVersionServiceImpl.java:132`

```java
public Integer rollback(Long docId, Integer targetVersionNo) {
    log.info("开始回滚文档版本 docId={} targetVersionNo={}", docId, targetVersionNo);
    // 查询目标版本
    KnowledgeDocVersion targetVersion = getVersion(docId, targetVersionNo);
    Integer previousVersionNo = findCurrentIndexedVersionNo(docId);

    // 以 ROLLBACK 来源创建新版本
    Integer newVersionNo = createVersion(
            docId,
            targetVersion.getContent(),
            GenerationSource.ROLLBACK.name(),
            targetVersion.getMetadataSnapshotId(),
            "回滚到版本 " + targetVersionNo);

    // 查询文档获取数据源 ID，创建向量化任务
    KnowledgeDoc doc = knowledgeDocMapper.selectById(docId);
    doc.setStatus(DocStatus.INDEXING.name());      // ← 无前置状态校验
    knowledgeDocMapper.updateById(doc);
    vectorIndexTaskService.createTask(             // ← 直接触发向量化，无审核
            doc.getDatasourceId(),
            "DOC",
            docId,
            targetVersion.getMetadataSnapshotId(),
            newVersionNo,
            previousVersionNo);
    ...
}
```

### 对比：同模块其他动作都有状态校验

| 动作 | 位置 | 前置校验 |
| --- | --- | --- |
| `submitReview` | `KnowledgeDocLifecycleService.java:54` | `只有草稿状态的文档才能提交审核` |
| `approve` | `KnowledgeDocLifecycleService.java:74` | `只有待审核状态的文档才能审核` |
| `reject` | `KnowledgeDocLifecycleService.java:98` | `只有待审核状态的文档才能审核` |
| `publish` | `KnowledgeDocLifecycleService.java:128` | `只有审核通过的文档才能发布` |
| **`rollback`** | **`KnowledgeVersionServiceImpl.java:132`** | **无** |

五个入口里只有 rollback 没有校验，因此这属于遗漏，而非有意的设计选择。

### 影响

- 任何人（含前端被绕过的直接 API 调用）可以把未经审核的内容写入 Milvus，污染 RAG 检索结果。
- 与项目核心设计「metadata-governance-driven trustworthy querying」直接冲突：RAG 准入应只接受已审核发布的内容。
- 前端在阶段 5 只对 `PUBLISHED` 开放回滚按钮，但**前端限制不构成安全边界**。

### 建议

在 `rollback()` 入口补齐校验，至少要求目标版本 `reviewStatus` 为已通过、且当前文档处于允许回滚的状态（建议 `PUBLISHED` 或存在已索引版本）。是否允许对 `APPROVED` 文档回滚需要产品确认，但**不应允许 `DRAFT` 文档通过回滚进入索引**。

## 2. P1：审核意见已落库但无查询接口，驳回原因不可见

### 现象

`approve` / `reject` 会把审核意见写入 `knowledge_review_task` 表，但**全项目没有任何 Controller 暴露该表**。作者被驳回后看不到原因。

### 证据

写入侧 `KnowledgeDocLifecycleService.java:197`：

```java
private void createReviewTask(KnowledgeDoc doc, String reviewStatus, String comment) {
    KnowledgeDocVersion currentVersion = knowledgeDocVersionMapper.selectOne(...);
    Long docVersionId = currentVersion != null ? currentVersion.getId() : null;

    KnowledgeReviewTask reviewTask = KnowledgeReviewTask.builder()
            .docVersionId(docVersionId)
            .reviewerId(UserContext.currentUserId())
            .reviewStatus(reviewStatus)
            .reviewComment(comment)          // ← 审核意见确实落库
            .submittedAt(LocalDateTime.now())
            .reviewedAt(LocalDateTime.now())
            .build();
    knowledgeReviewTaskMapper.insert(reviewTask);
}
```

调用点仅两处：`:87`（approve）、`:111`（reject）。`submitReview` 不写审核任务。

读取侧：全项目检索 `KnowledgeReviewTask` / `knowledge_review_task`，仅命中实体、Mapper 与该 ServiceImpl，**无任何 Controller 引用**。

### 影响

《DataOcean-后台前端整体重构开发指导》第 16.3 节「生命周期」验收场景明确要求：

> 审核拒绝后能够返回编辑并看到原因。

当前后端无法支撑该验收项。这是本轮重构中**唯一一条被后端能力卡住的验收标准**，前端只能标注缺口，不能伪造。

### 建议

该缺口修复成本很低：数据已按 `docVersionId` 关联存好，只需增加一个查询接口（例如 `GET /api/admin/knowledge-docs/{id}/review-tasks`）。建议纳入 P1，与本轮重构的验收收口一起处理。

## 3. P2：业务术语模块的状态机与删除清理

### 3.1 已通过术语无合法修改路径，但存在越权修改路径

**现象**：状态机只有 `DRAFT | REJECTED → PENDING_REVIEW → APPROVED | REJECTED`，从 `APPROVED` 没有出边，已通过术语无法退回草稿修改；但 `updateTerm` 又完全不校验状态，可以直接静默改写已通过术语。

**证据**：

`module/glossary/service/impl/GlossaryTermServiceImpl.java:74`（合法路径被限制）

```java
if (!GlossaryTerm.STATUS_DRAFT.equals(term.getStatus())
        && !GlossaryTerm.STATUS_REJECTED.equals(term.getStatus())) {
    throw new BusinessException("只有 DRAFT 或 REJECTED 状态的术语才能提交审核");
}
```

`module/glossary/controller/GlossaryController.java:110`（越权路径无限制）

```java
@PutMapping("/terms/{termId}")
public Result<Void> updateTerm(@PathVariable Long termId, @RequestBody GlossaryTerm term) {
    GlossaryTerm existing = termService.getById(termId);
    if (existing == null) {
        return Result.error(404, "术语不存在");
    }
    term.setId(termId);
    termService.updateById(term);        // ← 无状态校验，APPROVED 术语可被静默改写
    return Result.success("术语更新成功", null);
}
```

**影响**：状态机在语义上失效——受限制的是「合规流程」，不受限制的是「绕过审核的改动」。术语定义会被改写并进入 RAG 查询改写，而审核记录 `reviewerId` / `reviewedAt` 不会更新，无法追溯。

**建议**：二选一，不要维持现状。
- 方案 A（推荐）：补充 `APPROVED → DRAFT` 的退回接口，`updateTerm` 增加状态校验，使「修改已通过术语必须重走审核」。
- 方案 B：保留直接修改，但必须清空 `reviewerId` / `reviewedAt` 并把状态置回 `DRAFT`，避免已审核标记失效。

前端当前按方案 A 的语义实现：`APPROVED` 术语只读，并明示后端缺少回退接口。若后端选择方案 B，前端需同步调整。

### 3.2 删除术语 / 术语表不清理关联数据

**现象**：删除只做单表 `removeById`，不清理关联关系，而相关表**没有任何外键约束**，因此静默产生孤儿数据。

**证据**：

`module/glossary/controller/GlossaryController.java:76`

```java
@DeleteMapping("/{id}")
public Result<Void> deleteGlossary(@PathVariable Long id) {
    Glossary existing = glossaryService.getById(id);
    if (existing == null) {
        return Result.error(404, "术语表不存在");
    }
    glossaryService.removeById(id);      // ← 其下 glossary_term 全部成为孤儿
    return Result.success("术语表已删除", null);
}
```

`module/glossary/controller/GlossaryController.java:123`

```java
@DeleteMapping("/terms/{termId}")
public Result<Void> deleteTerm(@PathVariable Long termId) {
    termService.removeById(termId);      // ← metadata_relationship 中 GLOSSARY_OF 关系成为孤儿
    return Result.success("术语已删除", null);
}
```

`GlossaryServiceImpl` / `GlossaryTermServiceImpl` 均未覆盖删除方法，无级联逻辑。

**外键约束缺失的核实**：`db/migration/` 下全部 50 个 Flyway 脚本中检索 `FOREIGN KEY` 与 `REFERENCES`，**结果为空**。`glossary_term.glossary_id`、`glossary_term.parent_id`、`metadata_relationship.source_id/target_id` 全部只有普通索引，无约束。

```sql
-- V38__glossary_tables.sql
    glossary_id     BIGINT NOT NULL COMMENT '所属术语表 ID',
    parent_id       BIGINT COMMENT '父术语 ID（NULL 表示顶级术语）',
    INDEX idx_term_glossary (glossary_id),
    INDEX idx_term_parent (parent_id),

-- V37__metadata_entity_graph.sql
    source_id       BIGINT NOT NULL COMMENT '源实体 ID',
    target_id       BIGINT NOT NULL COMMENT '目标实体 ID',
    INDEX idx_rel_source (source_id, relation_type),
```

**这不属于一致的设计选择**：同一 Controller 的 `unlinkTermFromColumn`（`:176`）就明确清理了 `GLOSSARY_OF` 关系，说明作者清楚需要维护关系表，只是删除路径漏了。

**影响**：
- `metadata_relationship` 中的 `GLOSSARY_OF` 孤儿关系会指向已删除的术语，实体图谱与血缘查询可能返回悬空节点。
- 删除术语表后，其下术语的 `fqn` 仍占用 `uk_term_fqn` 唯一键，重建同名术语表会因 FQN 冲突而失败。

**建议**：删除术语时清理 `metadata_relationship`（`source_id = termId AND source_type = 'GLOSSARY_TERM'`）；删除术语表时级联删除其下术语并清理对应关系，或至少阻止删除非空术语表。

## 4. P3：能力缺口（有表、有数据写入，无对外接口）

以下四项均不属于行为错误，而是「数据已在库中，但前端拿不到」。阶段 5 前端已在页面文案中如实标注，未使用假数据补齐。

| 编号 | 缺口 | 证据 | 前端影响 |
| --- | --- | --- | --- |
| G1 | 向量化任务不可查询 | 引用 `VectorIndexTask` 的 10 个文件全部位于 `module/knowledge/` 内部（client / entity / mapper / scheduler / service），无任何 Controller 引用 | 文档处于 `INDEXING` 时无法显示进度与失败原因，只能显示状态；重复发布需靠后端报错拦截 |
| G2 | 无「按文档查来源快照」的聚合接口 | 来源快照分散在 `knowledge_doc_version.metadata_snapshot_id`，需先取版本列表再逐个解析 | 可用，但需组合两次请求；前端已按此实现，非阻塞 |
| G3 | 术语无 `APPROVED → DRAFT` 退回落口 | 见 3.1 | 已通过术语在本轮前端保持只读 |
| G4 | Prompt 模板不能停用 | `enabled` 有列、`getActiveContent`（`PromptTemplateServiceImpl.java:301`）按它过滤，但无修改接口；`setEnabled(true)` 仅在 approve 时调用（`:169`） | `enabled` 只能展示，无法在前端停用模板 |

### 补充：`knowledge_doc_version.review_status` 是一列死数据

**现象**：该列建表定义为 `NOT NULL DEFAULT 'PENDING'`，但 `createVersion` 从不写入它，`approve` / `reject` 也只更新 `knowledge_doc` 表。因此该列**恒为 `PENDING`**，`reviewer_id` 恒为 `NULL`。

**证据**：

```sql
-- V13__create_knowledge_tables.sql:35
    review_status        VARCHAR(30)  NOT NULL DEFAULT 'PENDING' COMMENT '审核状态: PENDING/APPROVED/REJECTED',
    reviewer_id          BIGINT                COMMENT '审核人 ID',
```

`KnowledgeVersionServiceImpl.java:95` 的 `createVersion` builder 未设置 `reviewStatus`：

```java
KnowledgeDocVersion version = KnowledgeDocVersion.builder()
        .docId(docId)
        .datasourceId(doc.getDatasourceId())
        .metadataSnapshotId(snapshotId)
        .dependencySnapshot(...)
        .versionNo(newVersionNo)
        .content(content)
        .generationSource(generationSource)
        .changeSummary(changeSummary)
        .createdBy(UserContext.currentUserId())
        .build();                        // ← 无 reviewStatus
```

**影响**：这是一列会**主动误导读取方**的数据——任何按 `review_status` 展示审核状态的前端都会得到「恒为待审核」的错误结论。

**本轮实际踩坑**：阶段 5 的「审核记录」Tab 最初用该列渲染审核轨迹，会产生错误显示（已发布版本显示为「待审核」）。已改为只呈现真实可信的版本流转信息（生成来源 / 变更摘要 / 操作人 / 时间），并在页面明示审核意见查不到的原因；「版本」Tab 中该列也已移除。

**建议**：要么在 `approve` / `reject` 时同步写入版本行（语义更完整，且能天然支撑 P1 的审核记录查询），要么删除该列与 `reviewer_id`，避免继续误导。不推荐维持现状。

## 6. 阶段 5 前端的对应规避动作

供后续修复后端时对照，避免修完后端前端仍是旧的规避逻辑。

| 后端问题 | 阶段 5 前端的处理 | 后端修复后前端应做的调整 |
| --- | --- | --- |
| 回滚无状态校验（P0） | 仅对 `PUBLISHED` 文档显示回滚按钮，确认框写明「创建 ROLLBACK 版本 + 置为索引中 + 触发向量化 + 不经过审核」 | 校验补齐后，可评估是否对 `APPROVED` 也开放 |
| 审核意见不可见（P1） | 「审核记录」Tab 明示后端无查询接口，不展示审核意见 | 接入新接口，展示审核人、审核时间、审核意见 |
| 术语越权修改（P2-3.1） | `APPROVED` 术语只读，页面说明缺少回退接口 | 若采用方案 B，需开放编辑并提示「修改后状态回到草稿」 |
| 版本 `review_status` 死列 | 不使用该列渲染任何审核结论 | 若后端补齐写入，可恢复「按版本展示审核状态」 |
| 向量化任务不可见（G1） | `INDEXING` 状态只显示状态与「禁止重复发布」，不显示进度 | 接入任务查询接口，补充进度与失败原因 |
| Prompt 不能停用（G4） | `enabled` 仅展示 | 接入启停接口后补充操作入口 |

## 7. 建议的处理顺序

| 顺序 | 项目 | 理由 |

## 8. 跨端项：前端已发现、后端建议优化

以下两项的**根因在前端**（已计入前端缺陷清单 F1、F3，前端修复即可解决用户可见问题），但后端存在可优化之处。列出以便两端修复时互相参照，**不要**把它们当作后端的阻塞缺陷。

### C1 `batchHandle` 静默跳过，只返回成功计数

**位置**：`module/governance/service/impl/QualityIssueServiceImpl.java:139`

```java
public int batchHandle(List<Long> issueIds, String targetStatus, Long operatorId) {
    int updated = 0;
    for (Long issueId : issueIds) {
        try {
            handleIssue(issueId, targetStatus, null, operatorId);
            updated++;
        } catch (BusinessException e) {
            log.warn("批量处理跳过 issueId={}: {}", issueId, e.getMessage());
        }
    }
    return updated;
}
```

状态不允许的条目被静默跳过，接口只返回 `updated`。前端因此只能显示「已处理 N 条」，无法告知用户有多少条被跳过、原因是什么（前端缺陷清单 F3）。

**影响**：中等。当前可从服务端日志追溯，但用户侧完全没有反馈。

**建议**：返回结构改为 `{ updated, skipped, skipReasons }`，或在响应中带 `skippedIssueIds`。前端即可如实呈现“N 条成功、M 条因状态不允许被跳过”。这是**接口增强**，不改变现有语义，向后兼容。

### C2 `DATASOURCE_DISABLED` 的 actionPath 指向列表页

**位置**：`module/datasource/service/impl/DatasourceReadinessServiceImpl.java:206`

```java
addReason(vo, "DATASOURCE_DISABLED", "数据源已禁用，暂不可查询", "数据管理员", "启用数据源", "/admin/datasources");
```

`actionText` 是「启用数据源」，但 `actionPath` 指向数据源**列表**，用户还需自己在列表里再定位一次。而 readiness 本身就绑定了具体数据源 ID。

**影响**：低。前端可从上下文补出详情链接，但会与后端的显式 actionPath 语义脱节。

**建议**：`actionPath` 指向该数据源详情，或由前端统一按 `datasourceId` 补全（本项目前端已有的 `resolveReadinessActionPath` 会附加 `datasourceId`，可在其中处理此类情况）。
