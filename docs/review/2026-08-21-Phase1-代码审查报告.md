## 2. 🔴 Critical Issues

### 2.1 SQL 注入风险 — `DataQualityChecker`

**文件**: `governance/checker/DataQualityChecker.java`  
**位置**: `checkNullRate()`, `checkUniqueness()`, `checkForeignKeyOrphans()`, `checkDataStaleness()`

```java
// 问题代码 — 直接拼接用户可控的表名/列名到 SQL
String sql = String.format(
    "SELECT COUNT(*) AS total, SUM(CASE WHEN `%s` IS NULL THEN 1 ELSE 0 END) AS nulls FROM `%s` LIMIT %d",
    column.getColumnName(), column.getTableName(), MAX_SAMPLE_ROWS);
```

**风险**：虽然 `columnName`/`tableName` 来自元数据采集，但如果用户能创建含有恶意字符的表名/列名（如 `` `; DROP TABLE -- ``），就可以实现 SQL 注入。另外 `StatisticsCollector` 中也有相同模式。

**建议修复**：
1. 对标识符做严格白名单校验（仅允许 `[a-zA-Z0-9_]`）
2. 使用已有的 `escapeIdentifier()` 方法（`StatisticsCollector` 中已实现）统一到公共工具类
3. 设置 Statement 为只读 + 超时

```java
// 推荐：统一使用标识符转义工具
private static String escapeIdentifier(String id) {
    // 拒绝超长/非法字符
    if (!id.matches("[a-zA-Z0-9_]{1,64}")) {
        throw new BusinessException("非法标识符: " + id);
    }
    return id.replace("`", "``");
}
```

### 2.2 密码解密逻辑重复且不一致 — `DataQualityChecker`

**文件**: `governance/checker/DataQualityChecker.java` → `decryptPassword()`  
**对比**: `datasource/service/impl/DatasourceSecretServiceImpl.java`

```java
// DataQualityChecker 中自行实现了解密，使用了不同的环境变量
String aesKey = System.getenv("DATASOURCE_AES_KEY");  // ← 与 DatasourceSecretService 使用的 DATAOCEAN_ENCRYPT_KEY 不同！
```

**风险**：
1. **密钥不一致** — 两处使用不同的环境变量名，极可能导致解密失败
2. **降级行为危险** — 解密失败时直接返回原始密文作为密码使用（`return encrypted;`），可能导致连接失败日志泄露密文
3. **违反 DRY** — 加密逻辑散布在多处，升级算法时遗漏某处就是安全漏洞

**建议修复**：  
删除 `DataQualityChecker.decryptPassword()`，改为注入 `DatasourceSecretService` 复用已有解密逻辑：

```java
@RequiredArgsConstructor
public class DataQualityChecker implements QualityChecker {
    private final DatasourceSecretService secretService;  // 注入而非自行解密
    
    private Connection getConnection(Long datasourceId) {
        // ...
        String password = secretService.decrypt(secret.getEncryptedPassword());
        // ...
    }
}
```

### 2.3 Redis 权限缓存可序列化泄露 — `PythonAgentClientImpl`

**文件**: `query/client/impl/PythonAgentClientImpl.java`

```java
redisTemplate.opsForValue().set("perm:" + taskId, permContext, Duration.ofSeconds(60));
```

**风险**：
1. `PermissionContextVO` 包含 `deniedColumns`、`deniedTables`、`maskColumns` 等敏感权限信息，直接序列化到 Redis
2. 使用 `RedisTemplate<String, Object>` — 序列化方式取决于全局配置，若用 JDK 序列化则存在反序列化漏洞；若用 JSON 则泄露完整权限结构
3. TTL 仅 60s 但无加密保护，Redis 若被攻破则所有用户权限泄露

**建议修复**：
1. 权限数据建议通过 taskId 直接从数据库/计算器获取，避免存入 Redis
2. 如必须缓存，使用独立的 `StringRedisTemplate` + JSON 序列化，并对 value 加密
3. 考虑内存级缓存（Caffeine）替代 Redis 缓存敏感数据

## 3. 🟠 High Priority Issues

### 3.1 `listVersionHistory` N+1 查询 + 全表扫描

**文件**: `versioning/service/impl/SnapshotLifecycleServiceImpl.java`

```java
// 问题：每次分页查询都加载所有数据源名称
Map<Long, String> datasourceNames = datasourceMapper.selectList(
    new LambdaQueryWrapper<Datasource>().eq(Datasource::getDeleted, 0L))
    .stream()
    .collect(Collectors.toMap(Datasource::getId, Datasource::getName));
```

**影响**：当数据源数量增长到数百/数千时，每次分页查询都会全表加载。

**建议修复**：
```java
// 仅查询本页涉及的数据源 ID
Set<Long> dsIds = snapshotPage.getRecords().stream()
    .map(MetadataSnapshot::getDatasourceId)
    .collect(Collectors.toSet());
Map<Long, String> datasourceNames = datasourceMapper.selectList(
    new LambdaQueryWrapper<Datasource>()
        .in(Datasource::getId, dsIds)
        .select(Datasource::getId, Datasource::getName))
    .stream()
    .collect(Collectors.toMap(Datasource::getId, Datasource::getName));
```

### 3.2 `traceDerivedFromChain` 无环检测 + 无限递归风险

**文件**: `metadata/controller/MetadataCatalogController.java`

```java
private List<Map<String, Object>> traceDerivedFromChain(Long columnId, int depth, boolean upstream) {
    // ...
    node.put("children", traceDerivedFromChain(relatedColId, depth - 1, upstream));
    // ...
}
```

**风险**：如果血缘关系中存在环（A → B → C → A），递归会在 depth 内反复访问相同节点，造成指数级 DB 查询放大。

**建议修复**：
```java
private List<Map<String, Object>> traceDerivedFromChain(
        Long columnId, int depth, boolean upstream, Set<Long> visited) {
    if (depth <= 0 || visited.contains(columnId)) return Collections.emptyList();
    visited.add(columnId);
    // ... 递归时传入 visited
}
```

### 3.3 SSE 流消费缺少优雅中断机制

**文件**: `query/client/impl/PythonAgentClientImpl.java`

`consumeSseStream()` 使用 `MAX_SSE_DURATION_MS = 180_000` 超时保护，但在异步线程中长时间阻塞 `BufferedReader.readLine()` 期间：
- 无法响应 Spring 应用关闭（graceful shutdown）
- 无法响应用户取消（`cancelTask` 只通知了 Python 侧）
- 线程池 `queryExecutor` 资源被长时间占用

**建议**：
1. 使用 `Thread.currentThread().isInterrupted()` 检查中断
2. 配合 `Future` 使主线程可取消异步任务
3. 将 Socket 读超时设置为较短值（如 30s），SSE 心跳间隔内无数据则主动断开

### 3.4 `QueryController.ask()` 无幂等性保护

**文件**: `query/controller/QueryController.java`

```java
@PostMapping("/ask")
public Result<Map<String, Object>> ask(@Valid @RequestBody QueryAskDTO request) {
    // 限流 → 权限 → 创建会话 → 保存消息 → 提交任务 → 触发 Agent
}
```

**风险**：前端网络抖动可能导致重复提交，产生重复任务和费用消耗。

**建议**：
1. 在 `QueryAskDTO` 中增加可选的 `requestId`（客户端 UUID）
2. 利用 Redis SETNX 实现幂等窗口（5s 内相同 requestId 返回已有 taskId）

## 4. 🟡 Medium Issues

### 4.1 `StatisticsCollector` SQL 注入防护不完整

虽然有 `escapeIdentifier()` 方法，但仅转义了反引号。建议增加长度限制和字符白名单校验（见 2.1 建议）。

### 4.2 `SnapshotLifecycleServiceImpl.changeStatus()` 缺少并发控制

```java
@Transactional
public void changeStatus(Long snapshotId, String targetStatus, ...) {
    MetadataSnapshot snapshot = snapshotMapper.selectById(snapshotId);
    // ... 校验状态 ...
    snapshot.setStatus(targetStatus);
    snapshotMapper.updateById(snapshot);
}
```

在并发场景下，两个请求可能同时读到相同的旧状态，导致非法状态转换。

**建议**：使用乐观锁（`@Version`）或 `UPDATE ... WHERE status = ?` 进行 CAS 更新。

### 4.3 `MetadataCatalogController` 中 Controller 包含业务逻辑

`traceDerivedFromChain()` 方法是递归 BFS 图遍历逻辑，不应放在 Controller 中。建议抽取到 `MetadataRelationshipService` 或专门的 `ColumnLineageService`。

### 4.4 `PythonAgentClientImpl` 职责过重

该类承担了：
- 构建连接配置
- 计算权限上下文
- 加载知识库 chunks
- 加载术语表
- SSE 流解析
- 任务结果回写
- 会话消息保存

建议拆分为：
- `AgentRequestBuilder` — 负责请求体构建
- `SseStreamConsumer` — 负责 SSE 流解析
- `PythonAgentClient` — 仅负责 HTTP 调用编排

### 4.5 异常处理中的信息泄露

```java
// QueryController
throw new BusinessException("该数据源尚未发布元数据快照，请先完成元数据治理");
```

部分错误信息暴露了内部实现细节（"元数据快照"、"治理"）。面向终端用户的 API 应返回脱敏后的友好提示。
