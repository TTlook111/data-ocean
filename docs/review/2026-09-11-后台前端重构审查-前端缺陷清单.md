## 0. 文档定位与结论

本文档记录审查中发现的**前端代码缺陷**。判断标准是**缺陷根因在哪一端**：修复只需改前端代码即可解决的，归入本文档；必须改 Java/Python/数据库才能解决的，归入后端文档。

本文档不取代 `docs/development/后续开发.md`。待办排期需在确认后并入该清单。

### 结论概览

| 级别 | 数量 | 说明 |
| --- | --- | --- |
| 高 | 3 | 引导用户执行错误操作，或把失败呈现为成功 |
| 中 | 3 | 导航状态错误、后端已有能力未承载、URL 不可恢复 |
| 低 | 3 | 潜在缺陷与死代码 |
| 已修正 | 2 | 阶段 5 实施中自我发现并已修复 |

**高严重度三项的共同点**：后端返回的数据是正确的，前端把它用错了或没有用。

## 1. 高严重度缺陷

### F1 数据源详情的主操作指向错误的下一步

**位置**：`frontend/src/views/admin/datasource/DataSourceDetailView.vue:42-52`

**证据**：该页面自行推导“下一步”，没有使用后端 readiness 已经返回的 `blockReasons`：

```js
const primaryAction = computed(() => {
  if (!readiness.value) return { key: 'reload', label: '刷新状态' }
  if (!readiness.value.connectionReady) return { key: 'test', label: '测试连接', icon: PlugZap }   // 第 44 行
  if (datasource.value?.status !== 1) return { key: 'enable', label: '启用数据源', icon: Database }  // 第 45 行
  ...
})
```

而后端 `DatasourceReadinessServiceImpl.java:114` 的定义是：

```java
private boolean isConnectionReady(Datasource datasource) {
    return Integer.valueOf(Datasource.STATUS_ENABLED).equals(datasource.getStatus())
            && Datasource.HEALTH_HEALTHY.equals(datasource.getHealthStatus());
}
```

`connectionReady` 已经包含 `status == ENABLED` 的判断，因此**被禁用的数据源必然在第 44 行就返回**。

**后果**：

| 场景 | 后端认为的首要动作 | 前端驾驶舱主操作 |
| --- | --- | --- |
| 数据源被禁用 | 「启用数据源」（`DATASOURCE_DISABLED`） | **「测试连接」** |

1. 用户对一个已禁用的数据源点“测试连接”，测完数据源仍是禁用的，页面不告诉他需要启用。
2. 第 45 行的「启用数据源」分支**永远不会执行**，是死代码。

**违反条款**：开发指导 §3.1「新前端必须复用这些事实，不能在前端重新拼装另一套就绪状态」；任务清单 §4「必须建立唯一的集中转换函数，不允许各页面分别写判断」。

**修复方向**：`primaryAction` 改为消费 `readiness.blockReasons[0]` 的 `actionText` / `actionPath`（即改用 `NextActionCard` 的同一套映射），或至少在顺序上把 `status !== 1` 提到 `connectionReady` 之前并与后端 `appendBlockReasons` 的判定顺序保持一致。

**附注**：同一文件 `lifecycleSteps`（`:54-72`）用 `current.includes('CONNECTION')` 这类字符串匹配自行推导当前步骤，未复用后端已有的 `stage` / `stageLabel`。目前后端 7 个 stage 取值恰好都能落位，但 `current.includes('METADATA')` 是对一个不存在的 stage 值的猜测，属脆弱耦合。见 F7。

### F2 快照 `ISSUE_FOUND` 的主操作引导跳过问题处理

**位置**：`frontend/src/views/admin/releases/ReleasesView.vue` 快照列表行级操作

**证据**：

```html
<el-button v-if="row.status === 'ISSUE_FOUND'" link @click="changeStatus(row, 'APPROVED')">批准</el-button>
```

**后果**：开发指导 §7.6 的状态-主操作表规定：

| 状态 | 规定的主操作 |
| --- | --- |
| `ISSUE_FOUND` | **进入问题中心** |

前端在该状态下给出的主操作是「批准」，等于**引导用户绕过问题处理**，直接放行一个质量检查未通过的快照。后端虽然允许 `ISSUE_FOUND → APPROVED`，但该状态存在的意义正是先处理问题。

「问题中心」的入口只存在于“选中快照后的详情区”，且指向的是治理总览（`/admin/governance`）而非问题中心（`/admin/governance/issues`）。

**违反条款**：开发指导 §7.6；§2「完成当前操作后，下一步去哪里」；§9 门禁表「快照｜存在阻断治理问题｜进入问题中心｜不得显示为发布」。

**修复方向**：`ISSUE_FOUND` 行同时给出「进入问题中心」（主）与「批准」（次），问题中心链接携带 `datasourceId` 与 `snapshotId`。不需要新接口。

### F3 批量处理把部分成功呈现为完全成功

**位置**：`frontend/src/views/admin/governance/IssueList.vue:157`

**证据**：

```js
const res = await batchHandleIssues({ issueIds: selectedIds.value, status })
ElMessage.success(`已处理 ${res.data?.updated ?? 0} 条`)
```

后端 `QualityIssueServiceImpl.batchHandle`（`:139`）对状态不允许的条目**静默跳过**，只返回成功计数：

```java
for (Long issueId : issueIds) {
    try {
        handleIssue(issueId, targetStatus, null, operatorId);
        updated++;
    } catch (BusinessException e) {
        log.warn("批量处理跳过 issueId={}: {}", issueId, e.getMessage());
    }
}
return updated;
```

**后果**：用户勾选 10 条问题点“批量确认”，其中若干条因状态不允许被跳过 → 前端显示「已处理 7 条」，且使用 `success` 样式。用户无法知道另外 3 条是被跳过了还是失败了，也不知道原因。若全部被跳过，显示「已处理 0 条」仍是绿色成功提示。

**违反条款**：开发指导 §9「所有写操作必须以服务端当前状态为准……接口失败时仍展示后端错误」；§11.3「状态表达」；§16.5「异常体验」。

**修复方向**：前端比较 `selectedIds.length` 与 `res.data.updated`，数量不一致时改用 `warning` 提示并说明「N 条因当前状态不允许流转被跳过，请刷新后重试」。**根治需要后端返回明细**（见后端文档 §5 边界项）。

## 2. 中等严重度缺陷

### F4 工作区导航在 `/admin/access/*` 下同时高亮两个入口

**位置**：`frontend/src/components/admin/AdminWorkspaceNav.vue:9-11`

**证据**：

```js
function isActive(path: string) {
  return route.path === path || route.path.startsWith('/' + path.replace(/^\//, '') + '/')
}
```

「授权管理」的路径 `/admin/access` 同时是另两个工作区路径的前缀。脚本验证结果：

```text
/admin/access                  -> 高亮: 授权管理
/admin/access/approvals        -> 高亮: 授权管理 + 访问审批      ❌
/admin/access/organization     -> 高亮: 授权管理 + 组织与角色   ❌
```

其余六个业务域无前缀冲突，因此只有 access 域受影响。

**违反条款**：开发指导 §5.4「二级工作区导航」；§11.3「状态表达」（当前项必须唯一可辨）。

**修复方向**：改为最长匹配优先——先取所有匹配项，仅激活路径最长的一个；或对 `/admin/access` 使用精确匹配（`route.path === path`），仅对确实有子页面的工作区使用前缀匹配。

**勘误（2026-09-12 修复时发现）**：本节结论低估了影响范围，且给出的修复方向不够。

1. **受影响路由是 7 条，不是 2 条。** 「其余六个业务域无前缀冲突」这句不成立——`governance` 域有同样的前缀结构（`/admin/governance` 是 `issues`/`rules`/`fields` 三条路径的前缀）。按原 `isActive` 逻辑对全部 28 条非重定向 admin 路由跑脚本，异常如下：

   ```text
   /admin/governance/issues      -> 治理总览 + 问题中心        ❌ 双高亮
   /admin/governance/rules       -> 治理总览 + 规则与状态      ❌ 双高亮
   /admin/governance/fields      -> 治理总览 + 字段治理        ❌ 双高亮
   /admin/access/approvals       -> 授权管理 + 访问审批        ❌ 双高亮
   /admin/access/organization    -> 授权管理 + 组织与角色      ❌ 双高亮
   /admin/metadata/tables        -> 无高亮                     ❌ 本节未发现
   /admin/permission/policies    -> 无高亮                     ❌ 本节未发现
   ```

2. **存在第二种失效模式：完全不高亮。** `/admin/metadata/tables`（`TableExplorer`）与 `/admin/permission/policies`（`PolicyEditor`）都是**真实路由而非重定向**，但路径与所属工作区（`/admin/assets`、`/admin/access`）不同前缀，因此当前不点亮任何二级入口。

3. **最终采用的修法不是最长匹配。** 改为用路由显式声明的 `route.meta.workspaceKey` 做等值判定，与 `AdminDomainNav.vue:28` 对 `domainKey` 的既有做法一致：

   ```ts
   const activeKey = computed(() => String(route.meta.workspaceKey || ''))
   function isActive(key: string) { return activeKey.value === key }
   ```

   验证结果：**旧实现 7 条异常 → 新实现 0 条异常**。28 条路由的 `workspaceKey` 全部命中 `ADMIN_WORKSPACES` 的 19 个 key，19 个 key 也全部被引用（`workbench` 除外——该域无二级工作区，导航整体不渲染）。

   选定该方案而非最长匹配的理由：高亮从此依赖**显式声明**而不是路径猜测。最长匹配能修好 5 条双高亮，但修不了 2 条零高亮（它们的问题是路径与工作区不同前缀，与匹配长度无关），而且会打断 `/admin/releases/snapshots/5` 这类详情页的归属高亮。

4. **`/admin/metadata/tables` 与 `/admin/permission/policies` 从零高亮变为有高亮，属有意修正**，依据是这两条路由自己的 `meta` 声明了工作区归属（`assets` / `access`）。验收时应作为预期行为，不要当作回归。

### F5 问题分派能力未承载

**位置**：`frontend/src/views/admin/governance/IssueList.vue` 全文

**证据**：

- 后端接口存在：`MetadataGovernanceController.java:174` `POST /api/admin/quality-issues/{issueId}/assign`
- 前端 API 层已封装：`api/admin/governance.ts:78` `assignIssue(issueId, assigneeId)`
- **但没有任何页面调用它**。问题详情只读取展示：

```html
<dt>责任人</dt><dd>{{ selectedIssue.assigneeName || '未分派' }}</dd>
```

页面显示“未分派”，却不提供分派操作。连带「责任人」筛选也缺失（筛选只有维度 / 级别 / 状态三个）。

**违反条款**：任务清单 §7.2 要求问题中心包含「问题列表、处理、批处理、**分配**」；开发指导 §17 完成定义第 2 条「后端已实现的管理能力全部具有合理前端归属」；§7.7 要求默认优先展示「分配给当前用户的问题」，该能力依赖分派。

**修复方向**：在问题详情加入分派操作（用户选择器复用组织与角色的用户列表接口），并在筛选栏加入责任人筛选。

**勘误与实施结果（2026-09-12）**：本节归入「前端缺陷」只对了一半——分派**操作**是纯前端改动，但**责任人筛选**卡在后端。

- 后端 `listIssues` 没有 `assigneeId` 参数（`QualityIssueService.java:23`），`MetadataGovernanceController.java:103` 与 `:128` 两个列表端点也都没有该入参。因此「支持责任人筛选」和 §7.7 的「默认优先展示分配给当前用户的问题」都不是前端能独立完成的。
- 成本其实很低：加过滤只需 3 个文件、核心 1 行 `.eq(assigneeId != null, MetadataQualityIssue::getAssigneeId, assigneeId)`，且 `V11__create_governance_tables.sql:45` 已有 `idx_assignee (assignee_id, status)` 索引，无需迁移。
- 但受《开发指导》§1「本轮不修改 Java、Python、数据库」的硬约束，本轮**只实现前端分派操作**，上述两项已并入 `docs/development/后续开发.md` 的待办。

**本轮实施**：`IssueList.vue` 详情抽屉加入「分派责任人」区块（`listUsers` + `assignIssue`）。用户选择器就地内联，未抽公共组件——`实施任务清单` §5 的组件清单中没有该任务，且 §8 才规划「合并重复 API 封装」。

### F6 切换工作区时 URL 丢失上下文

**位置**：`frontend/src/components/admin/AdminWorkspaceNav.vue:19`

**证据**：

```html
<RouterLink :to="workspace.path" ...>
```

只传路径，不携带当前查询参数。从 `/admin/governance/issues?datasourceId=3&snapshotId=7` 点击「治理总览」会跳成 `/admin/governance`。

**后果**：功能上仍连贯（`adminContext` 有 localStorage 兜底，页面显示的还是同一数据源），但 **URL 不再包含完整上下文**——把它发给同事，对方打开会使用**他自己**的 localStorage 值，可能看到另一个数据源的数据。

**违反条款**：任务清单 §3「稳定子任务用查询参数恢复，例如 `tab`、`datasourceId`、`snapshotId`、`page` 和筛选条件」；开发指导 §6.2 规则 4；§15 交付要求「URL 刷新、前进和后退恢复」。

**修复方向**：`RouterLink` 的 `:to` 带上可继承的上下文参数——至少 `datasourceId`，当目标工作区的 `contextMode` 含 snapshot 时再带 `snapshotId`。`ADMIN_WORKSPACES` 已有 `contextMode` 字段可用于判断。

**实施说明（2026-09-12）**：两处补充。

1. **严重性表述需收敛。** `adminContext` 持久化到 localStorage，且 `ScopeBar.syncFromUrl` 只在 query 参数**存在时**才覆盖 store——所以常见路径下用户**看不到**范围丢失。真正丢的是「URL 不再自描述」：分享、刷新、前进后退恢复（§17.6、§6.2 规则 4）。修复的价值依据是这一条，不是「用户会看到错误数据」。
2. **来源不能只读 URL。** 页面 URL 通常不带这两个参数，只读 `route.query` 会让继承失效（点击导航后目标 URL 依然没有参数）。实际实现按「合法 URL 参数优先于本地持久化状态」，URL 缺失时回落到 store，这样目标 URL 才真正自描述。
3. **一级导航 `AdminDomainNav.vue:37-48` 的 `:to="domain.path"` 有同一问题**，且更显眼（7 个一级入口任意页面单击即达）。本轮一并修复，两级导航共用 `utils/adminNavigation.ts` 的 `buildContextQuery`。白名单构造（只输出 `datasourceId` / `snapshotId`），不复制来源 query，避免 `tab`、`page`、筛选项泄漏到不认识它们的页面。

## 5. 阶段 5 实施中自我发现并已修正的问题

记录于此，因为两处都与后端文档中的 `review_status` 死列相关，可作为“死列会主动误导读取方”的实证。

| 问题 | 原实现 | 修正 |
| --- | --- | --- |
| 审核轨迹误用死列 | 「审核记录」Tab 用 `knowledge_doc_version.review_status` 渲染轨迹。该列建表 `DEFAULT 'PENDING'` 但后端从不写入，会**恒显示“待审核”**，包括已发布的版本 | 改为只呈现真实可信的版本流转（生成来源 / 变更摘要 / 操作人 / 时间），并在页面说明审核意见查不到的原因 |
| 来源快照误报为缺口 | 曾判断“后端没有按文档查询来源快照的接口”，页面因此不展示来源快照 | 实际 `KnowledgeVersionItem.metadataSnapshotId` 就是真实数据。已改为列出各版本来源快照并链接到快照详情 |

## 6. 验证通过的项目（正面结论）

以下项目经脚本或逐项比对确认无问题：

| 检查项 | 方法 | 结果 |
| --- | --- | --- |
