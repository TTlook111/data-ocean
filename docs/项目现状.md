## 已知限制

- 文档整理静态核对发现：Java 查询 chunk 准入统一排除空 columns，Python 对部分仅表依赖的业务事实允许空列。纯表级用途/粒度/计数口径的查询消费需先补准入一致性验证；类型/生成支持不等于该路径已完成，详见后续开发第 6 项。本轮未复现真实 RAG 或修改业务代码。

- 当前修复验收是绑定原情景/预期结果的明确人工核验；没有自动业务回放引擎，也不把程序合同检查称为业务真值证明。
- 评分政策 2 合并规范化 SQL 样例，仍需业务校准；旧政策事件保留追溯，不自动转为新证据。未实施复杂跨场景评分或独立性证明。
- 一键治理限制为 200 字段、100 表、100 关系，单次最多新增 200 项任务；超预算转单对象工作面。未实施任意规模分片调度。
- 历史业务知识缺少人工依据确认时需重新核对；知识复查、文档发布、RAG 生效和原问题验证是不同阶段。
- 完整新链路、多角色、撤权/失效、在途替换、大范围及页面视觉仍需独立验收；没有生产验收结论。
- Redis 默认开发加密密钥告警及一项历史静态测试对缺失脚本的引用仍需处理。Browser 早期 iframe 报错和默认 Milvus 集合归属仅保留为历史待复核问题，不宣称已复现或是当前主链阻断。

剩余动作只在[后续开发](development/后续开发.md)维护，不在历史方案里重开任务。
