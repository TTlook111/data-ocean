## 当前阶段

方案与交互原型已形成基准，当前推进[详细设计与分批实施](backend/详细设计与验收.md)。A 批已接入身份、组织、功能权限与审计，实际覆盖见[首批验收](backend/iam/验收.md#当前验证范围)。原型覆盖见[原型状态](frontend/原型状态.md)。

B 批数据源接入、采集、目录、企业业务说明和访问授权在已确认范围内具备正式验收条件。业务源范围为 MySQL 8.4.9 和 PostgreSQL 16.16 的[已验证对象](backend/datasource/验收.md#本次支持的源对象)，界面范围为 PC 桌面浏览器。真实接口、界面及故障恢复证据见[B 批验收结论](backend/access/验收.md#验收结论)。

C 批已接入表说明、字段、关联及指标治理，支持批量生成、字段受控采样、资料待定位和来源复核。模型后台支持 18 个节点独立配置，实际治理调用可回看当次配置修订。双库、两种生成协议、附件和 PC 实测范围见[治理验收](backend/governance/验收.md#当前验证)。

D 批已接入知识文档修订、发布准备任务、标准题审核、索引构建、逐题验证、裁定和正式切换。合成商品事项已实测首版发布、r1 切到 r2、当前与上一版回看及旧基础阻断。各阶段范围见[首个事项验收](backend/knowledge/验收.md)。

工程组织见[工程基线](engineering/工程组织与版本基线.md)，选型与版本分别由[前端设计](frontend/README.md#前端技术选型)和[后端设计](backend/README.md#版本基线与验证边界)维护，跨端职责与协议见[系统架构](architecture/README.md)。界面承接现有原型，布局与打磨边界见[设计约定](frontend/设计约定.md#原型基准与界面打磨)。

当前以本地运行为主，应用在宿主机启动，共享依赖通过独立 Docker 项目管理。最小技术链路、Redis 持久化及存储故障恢复已有独立验证。后续批次的业务链路以及容量、保留策略和完整组合运行按[后端验证边界](backend/README.md#版本基线与验证边界)继续验证。

## 按需求逐层理解

负责人已确认决定优先。方案维护业务规则，页面专题维护界面行为，原型展示交互；三者冲突时先核对决定与实际内容，不能让旧正文推翻新决定，也不能把原型实现偏差当成新规则。无法判断的业务冲突须提出具体差异及影响，其余独立整理继续。

1. 先读[项目定位](product/modules/01-overview.md)，明确项目目的、角色与主链。
2. 从[产品模块](product/README.md#按模块读取)定位业务规则，按模块解说列出的章／节[读取方案原文](product/README.md#按需读取原文)，需要时再补读关联小节和上下游。
3. 前端开发先按[开发前必读路径](frontend/README.md#开发前必读与完成验收)阅读共用总则、设计与交互规范，再进入对应[页面专题](frontend/pages/README.md)，核对入口、操作、状态及上下游衔接。
4. 从页面专题的原型定位进入相关页面及脚本，按[原型状态](frontend/原型状态.md)识别实际覆盖与固定样例边界，再按[验收要求](frontend/验收.md)验证。
5. 后端开发从[详细设计与验收](backend/详细设计与验收.md)定位模块，按实际改动核对接口、数据模型和验收条件。架构设计或涉及跨端职责与协议时，沿[系统架构](architecture/README.md)读取必要上下游与技术专题。实现与重构任务从[源码定位](source-map/README.md)核对当前代码及可复用实现。

模块入口应提供方案的准确章／节、页面、原型、必要依赖和验收位置。通用规范只读本次任务相关小节；不要求先读全方案、全部页面或旧系统。

需求理解以已确认方案和原型为主，实际代码与验证结果用于核对实现范围，不能反向改写设计。已有实现随变更同步源码定位、配置和使用说明；尚未实施的模块不预写实现路径。

## 保留 更新 删除

| 内容 | 维护方式 |
| --- | --- |
| 当前生效的业务规则、设计结论、必要理由和约束 | 保留在所属正文，只维护一份，各分类链接引用 |
| 当前状态、未定事项及仍有效的源码和运行事实 | 随相关决定和实际变更更新，不把设计确定当作实现完成 |
| 被替代的设计、重复正文、无用空文件和失效入口 | 先保留仍有效信息并修正引用，再直接删除；不建立“已过期”或历史设计区 |
| 执行日期、联调经过、测试数量和临时排查过程 | 不进入长期正文；必要验证结论只保留当前适用范围和依据 |
| 当前仍使用的接口、配置和安全约束 | 按事实维护，不因系统将重构而当成无用历史删除 |

状态只写现在的覆盖、差距和下一步，不续写开发日记。变更追溯使用 Git，文档只展示当前有效内容。

## 维护权限

判断标准是同步已确认的结论和当前事实，还是改变结论、业务边界或实施权限。已有授权持续有效，不重复请求确认。

| 动作 | 是否需要负责人再次决定 | 边界 |
| --- | --- | --- |
| 修正错字、格式、失效链接，拆分、移动和整理导航 | 不需要，可自主完成 | 保留有效内容并检查引用 |
| 将已确认决定写回正文，同步已授权改动的状态与源码说明 | 不需要，可自主完成 | 以实际实现及验证为依据，不编造完成或验证结果 |
| 删除已明确被替代的规则、重复内容、执行流水和无用入口 | 不需要，可自主完成 | 先确认有效信息已归位；不覆盖用户并行修改 |
| 在已授权页面任务内落实既定控件、对齐、文案和交互规则 | 不需要逐项请示 | 不改变业务含义、既定设计方向或授权范围 |
| 新增或改变产品范围、角色权限、登录方式、默认业务行为或数据保留策略 | 需要明确决定 | 提出具体方案与影响，决定后自主实施和同步文档 |
| 改变已定设计原则、换组件库、正式技术选型、架构或接口边界 | 需要明确决定 | 解释当前选择与事实不需再次决定；改变选择本身需要 |
| 开始真实重构或执行超出当前任务的源码、表结构、运行环境变更 | 需要明确实施任务 | 不从原型或整理文档推定授权；授权范围内的常规实现不重复请示 |
| 暂存、提交、推送或重置工作区；生产 SQL、实际数据删除、服务重启、基础设施替换 | 需要明确授权 | 删除旧文档的许可不延伸到这些操作 |
| 无法确定内容是否仍有效，或资料与已定规则发生实质冲突 | 先只读核实，仍不清楚再问具体问题 | 其他独立工作继续；不能把错误实现回填为新规则 |

## 更新顺序

确定变化所属分类 → 修改现行正文 → 同步实际状态和受影响引用 → 删除被替代内容 → 检查链接与相关事实。业务决定改变时同步方案和相关解说；跨端约束更新共用架构；只改界面则维护前端专题。实现、配置和使用说明随真实代码持续更新，不提前宣称未覆盖能力已完成。
