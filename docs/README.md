## 文档维护规则

- 行为变更更新主责模块；页面决定更新前端规范；未完成项只进后续开发；状态页只概括结论并链接证据。不要把同一批测试数字、迁移流水或问题清单复制多处。
- 阶段工作结束后将有效合同并入主责说明。具有设计或范围追溯价值的阶段映射、候选样稿移入 `archive/`，标明时点与后续去向；完全被替代且无独立价值的计划、阶段规格和临时诊断可删除，从 Git 历史回溯，不复制一份继续维护。
- 验收报告保留在 `acceptance/`，按环境与范围索引；旧阶段结果按历史批次阅读。合并同环境的重复记录时保留原提交、失败和覆盖限制，不为每次小修新开报告。
- 已执行数据库迁移保持字节不变，不为文档整理修改其中的历史注释。
- 原始截图、失败批次和运行日志保留其原时点结论；合并报告不把失败改成通过，也不把 H2/Mock、真实 MySQL、模型和页面验证混作一个结果。许多本机原件不随仓库分发，换机器需核实可用性。
- 用户后续明确决定优先；较新日期、已勾选任务或代码存在不构成需求批准或完整验收。旧文档不是迁移、bootstrap、建容器、删除或生产操作授权。
- 需要已删除的原始设计时从 Git 历史回溯；[specs 入口](../specs/README.md)仅作旧路径兼容。不得从历史正文恢复旧权限双读、旧 Agent、发布即索引或过期环境步骤。

默认 ripgrep 搜索排除验收与归档，避免把环境快照和旧样稿当现行实现。需要追溯时显式打开文件，或运行 `rg --no-ignore <关键词> docs/acceptance docs/archive`。现行行为说明指向主责模块；验收和设计来源可以链接历史材料，但应明确其时点与用途。
