## 保留 更新 删除

| 内容 | 维护方式 |
| --- | --- |
| 当前生效的业务规则、设计结论、必要理由和约束 | 保留在所属正文，只维护一份，各分类链接引用 |
| 当前状态、未定事项及仍有效的源码和运行事实 | 随相关决定和实际变更更新，不把设计确定当作实现完成 |
| 被替代的设计、重复正文、无用空文件和失效入口 | 先保留仍有效信息并修正引用，再直接删除；不建立“已过期”或历史设计区 |
| 执行日期、联调经过、测试数量和临时排查过程 | 不进入长期正文；必要验证结论只保留当前适用范围和依据 |
| 当前仍使用的接口、配置和安全约束 | 按事实维护，不因系统将重构而当成无用历史删除 |

状态只写现在的覆盖、差距和下一步，不续写开发日记。变更追溯使用 Git，文档只展示当前有效内容。

## 维护权限

判断标准是同步已确认的结论和当前事实，还是改变结论、业务边界或实施权限。已有授权持续有效，不重复请求确认。

| 动作 | 是否需要负责人再次决定 | 边界 |
| --- | --- | --- |
| 修正错字、格式、失效链接，拆分、移动和整理导航 | 不需要，可自主完成 | 保留有效内容并检查引用 |
| 将已确认决定写回正文，同步已授权改动的状态与源码说明 | 不需要，可自主完成 | 以实际实现及验证为依据，不编造完成或验证结果 |
| 删除已明确被替代的规则、重复内容、执行流水和无用入口 | 不需要，可自主完成 | 先确认有效信息已归位；不覆盖用户并行修改 |
| 在已授权页面任务内落实既定控件、对齐、文案和交互规则 | 不需要逐项请示 | 不改变业务含义、既定设计方向或授权范围 |
| 新增或改变产品范围、角色权限、登录方式、默认业务行为或数据保留策略 | 需要明确决定 | 提出具体方案与影响，决定后自主实施和同步文档 |
| 改变已定设计原则、换组件库、正式技术选型、架构或接口边界 | 需要明确决定 | 解释当前选择与事实不需再次决定；改变选择本身需要 |
| 开始真实重构或执行超出当前任务的源码、表结构、运行环境变更 | 需要明确实施任务 | 不从原型或整理文档推定授权；授权范围内的常规实现不重复请示 |
| 暂存、提交、推送或重置工作区；生产 SQL、实际数据删除、服务重启、基础设施替换 | 需要明确授权 | 删除旧文档的许可不延伸到这些操作 |
| 无法确定内容是否仍有效，或资料与已定规则发生实质冲突 | 先只读核实，仍不清楚再问具体问题 | 其他独立工作继续；不能把错误实现回填为新规则 |

## 更新顺序

确定变化所属分类 → 修改现行正文 → 同步实际状态和受影响引用 → 删除被替代内容 → 检查链接与相关事实。业务决定改变时同步方案和相关解说；跨端约束更新共用架构；只改界面则维护前端专题。真实实现开始后再记录与实际代码一致的实现、配置和使用说明。
