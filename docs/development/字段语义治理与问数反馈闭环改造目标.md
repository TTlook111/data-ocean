# 字段语义治理与问数反馈闭环改造目标

> 用户已确认的产品合同。实现看模块说明，状态看项目现状，未完成事项看后续开发；本文不记录实施流水。

## 1. 用户最终希望实现什么

在平台内理解数据源用途、表粒度与关系、指标及字段含义，形成可信知识，服务文档/RAG 和智能问数；用户反馈推动持续纠正。业务源保持只读，治理不要求用户到数据库修改数据或注释。

## 2. 完整闭环

选定源与快照 → 规则发现缺口 → AI 整理候选 → 人工补充审核 → 精确修订复查 → 文档审核发布 → 明确确认 RAG 构建 → 问数使用与反馈归因 → 再治理及原问题验收。

候选生成、知识复查、文档发布、RAG 生效和原问题修复是不同结果。资料不足、争议、不适用、失败与部分完成各自保留原因；新修订出现不能自动关闭原问题，缩小范围不能补造原批次成功。

## 3. 每个字段最终呈现什么

字段档案集中展示业务角色/标签、解释、单位/枚举、使用场景与限制、来源修订、审核复查及使用证据。按字段类型要求必要内容，不强迫填写不适用项。

- 稳定知识按修订审核，标签独立分类；原始注释、AI 推断与人工确认分开。
- 动态使用分属于对象、来源及语义修订，不能给每个公共标签复制一份权威分数。
- 跨快照复用需核验身份、结构、完整依赖并明确绑定，不能只按同名继承，也不无差别全库重做。

## 4. 规则到底负责什么

知识规则发现解释、用途、粒度、关系、口径与证据缺口；来源质量规则独立检查结构和合规只读数据。检查项是系统可执行能力，规则是该能力的对象/条件配置，不能用新增字典项冒充新执行器。

规则不替代业务事实确认：名称像金额不代表单位已知；字段可用状态、权限、审核和使用证据也不能互相替代。提供起步规则和适用前提，避免用户先配置大量规则才能治理。

## 5. AI、人工和系统复查分别做什么

| 角色 | 职责 |
| --- | --- |
| AI | 在合规元数据、有效平台知识和人工业务资料内整理建议；标明依据与未知项，不创建虚构事实或自行审核 |
| 人工 | 采纳、修改、补充或退回候选，核对原始资料、来源和修订；无资料时保留待确认 |
| 系统 | 检查必要内容、来源、完整依赖、权限、审核及同修订证据；报告可验证条件和无法判定事项，不宣称证明业务真值 |

先由 Java 在模型输入前过滤受限内容；禁止对象的完整事实应剔除，不能裁掉依赖后继续使用。旧 AI 响应不得覆盖人工修改，逐对象记录失败、恢复、执行轮次和预算。

## 6. 治理成果如何进入文档和 RAG

按主题生成多篇文档：数据源概览、表职责与粒度、关系/基数/聚合风险、指标公式与过滤去重口径、字段说明。每篇引用确切知识修订和完整资源依赖，整组核对覆盖、版本与排除范围。

文档是稳定知识投影。人工文案保留，受控事实变化回到知识修订，重新生成不得覆盖人工内容；单纯分数变化不改正文、重切片或重建向量。

查询先固定用户/源/build 并在权限范围内检索，再按完整依赖读取相同语义修订的标签和动态档案。实际依赖覆盖输出、筛选、连接、分组和排序；相关性及适用性优先于分数，不能换用高分但无关的字段。

来源或修订不匹配时不混用新含义与旧文档。内容变化继续走审核发布及显式构建；新集合验证后切指针，保留在途引用。撤权、封禁、审核失效即时生效，不等待重建或借旧口径降级。

## 7. 用户评分如何形成持续纠正

用户评价结果，可选原因；平台承担技术归因，不要求用户识别字段 ID。检索到不等于实际使用，实际使用也不等于根因。字段、关系、指标、SQL、展示或未知原因分别记录，不能把差评平均扣给所有字段。

经确认的版本化证据形成事件账本：来源任务、实际对象、修订、原因、审核和撤回可追溯；重试、重复意见及同任务修改不能累加计分。无反馈显示证据不足，不默认零分或正确。

参考分结合场景和证据量，参数通过人工确认样例校准，不代表绝对正确概率、不授予权限、不自动改定义。新修订不能默认继承旧分；低分必需字段应触发澄清或复核，不改变 SQL 业务含义。

负向问题绑定原情景、预期结果和修复目标，产生新治理修订；复查后仍须按原问题验证，保留旧问数依据与新版本差异。

## 8. 用户最终在页面上应看到什么

任务首先显示对象、缺什么、当前阶段和下一步；原资料、候选、有效版、草稿及使用证据可区分。审核明细、技术信息和历史按需展开，局部失败可直接处理。

复用现有字段解释、标签、知识和反馈工作面，通过公共范围及深链串联，不复制多套编辑器。知识已确认、文档已发布、RAG 已生效及反馈已验证分别呈现；范围切换后旧读取、保存和结束回调不影响新范围。

## 9. 当前已经有什么，主要差距在哪里

只在[项目现状](../项目现状.md)、[模块说明](../modules/README.md)和[后续开发](后续开发.md)维护，不在本合同复制阶段表。

### 9.1 工程验收底线

可信依据绑定内容/来源；表达式完整依赖；发布组事实覆盖；原问题修复验收；版本化反馈与去重；执行令牌、轮次和预算；新旧知识及安全失效隔离。不能以 SQL 可执行、AI 自评、任务完成数或分数上涨替代业务收益。

## 10. 变更约束

### 10.1 已确认原则

首期使用合规元数据、平台知识及人工资料，沿用现有 IAM/审核合同。新增业务样本读取、强制双人审核、跨场景评分或更大调度范围属于独立设计，不从历史草案推导授权。

明确影响范围，区分新增/删除/改名/结构或含义变化；不因一个对象变化宣称整库失效。先验证一个源的完整小业务链，再扩大范围。

## 11. 最终验收应验证哪些事情

- 真实范围与缺口可定位，AI 有依据和未知项，人工完成补充审核，受限内容不进入模型。
- 同来源、同修订复查及原问题验收可追溯；部分完成、失败、不适用和证据不足不会伪装全部通过。
- 多篇文档覆盖数据源、表、关系、指标及字段；审核/构建独立，问数能证明使用了指定合规版本。
- 分数变化不改变正文/build，新任务读取相应证据；来源、单位或权限变化不混用旧知识。
- 完整依赖和实际使用归因正确，重复/修改反馈不多计分，关系重复计数不误扣正确字段。
- 过期 AI、并发修改、恢复/预算、跨快照绑定、人工文案保留和撤权/在途引用有反例验证。
- 人工确认的标准问题与预期口径证明召回、关系和答案改进；业务争议仍可保留未知。
