**状态映射一致性**：发现并修复一处**真实的线上不一致**——全局共用组件 `BusinessStatusBadge` 内置的映射与 `utils/enumLabels.ts` 对同一状态给出不同中文：

| 状态 | 原 `BusinessStatusBadge` | 原 `enumLabels`（快照域） |
| --- | --- | --- |
| `CHECKING` | 检查中 | 校验中 |
| `ISSUE_FOUND` | 发现问题 | 存在问题 |
| `APPROVED` | 已批准 | 已审核 |

即同一个快照状态在不同页面会显示成两种中文，违反 §11.3 与 `实施任务清单` UI-11「相同状态在全站含义一致」。修正：无歧义的两项改为域映射的值；`APPROVED` 的语义随域不同（快照=已审核、知识=已批准），通用表无法兼顾，因此**渲染域状态时调用方必须显式传 `label`**，并为 **5 处**渲染快照状态的位置补传 `snapshotStatusLabel(...)`：`ReleasesView.vue` 的候选快照表「状态」列与快照详情标题（2 处）、`SnapshotDetailView.vue` 的状态栏（1 处）、`DataSourceDetailView.vue`「最近快照」列表的徽标（1 处）——以上 4 处由本阶段补入；`KnowledgeDocView.vue` 来源快照表的「快照状态」列（第 5 处）由 2026-09-12 修复 B27 时补入。`AssetsView` 自带的实体类型映射也已删除、改用共享映射。

**设计令牌**：`--do-*` 变量此前已收敛为唯一定义（`styles/variables.css`，`style.css` 只引用不定义），本项无需处理。本轮把 4 个文件里的品牌色字面量改为令牌（如 `#2563eb`→`var(--do-tone-blue)`、`#d95f5f`→`var(--do-danger)`）。

## 验证结果

### 构建和类型检查

- `cd frontend && npm run build`（`vue-tsc -b && vite build`）：**通过**。
- 死代码复核：**103 个代码文件全部可达，0 个不可达，0 个未引用资源**。
- 旧 URL 兼容：34 个表项全部就位（33 个重定向、1 个保持原路由）。
- 裸 API URL：视图与组件层为零。

> **「构建通过」覆盖不到什么（2026-09-12 审查确认）**
>
> `frontend/tsconfig*.json` **没有配置 `vueCompilerOptions.strictTemplates`**，该项默认关闭，因此 **`vue-tsc` 不检查模板中的组件解析**——模板里引用了未导入的组件不会产生类型错误。
>
> **实证**：`DataLineage.vue` 的 `LoadingState` / `ErrorState` 与 `OperationLogList.vue` 的 `ChevronDown` 三个未导入组件**全部穿过了 `npm run build`，退出码为 0**，直到运行到那段模板时才表现为空白弹窗。同类地，`aria-label` 有没有补也完全不影响构建结果。
>
> 因此：**构建通过只能证明类型与打包无误，不能证明模板引用的组件都存在**，也不能证明任何「结构断言」成立。本阶段与阶段 5–7 总结里「构建通过 = 结构断言成立」的表述均按此降级——那些结构断言是独立的只读脚本核对结果，与构建无关。
>
> **可复用的补充检查**（本轮审查所用，脚本化，三项抓出了全部「静默失效」类问题的另一半）：
>
> 1. 以 `main.ts` 为根解析真实 import 路径做传递可达性分析；
> 2. 交叉核对全部 `.vue` 模板中的 PascalCase 标签与 script 导入（排除 `El*` 前缀与全局注册项）——全仓只有 `DataLineage.vue` 与 `OperationLogList.vue` 两个文件命中；
> 3. 对模板里每个字段访问与导入类型做并集比对。

## 剩余风险

1. **全流程无运行时验证。** 阶段 0–8 的所有「完成」结论都基于静态阅读、结构断言与构建验证，**没有任何一次浏览器验收记录**。
2. **阶段 8 的删除不可逆地改变了代码结构。** 27 个文件已从工作区移除（仍在 git history 中）。若后续发现某个旧页面仍有未被识别的用途，需要从 git 恢复。
3. **`BusinessStatusBadge` 的 `APPROVED` 歧义只做了约定，未做强制。** 新页面渲染域状态时若忘记传 `label`，仍会落到通用表的「已批准」。已在组件注释中写明约束。
4. **状态映射仍有两处未收敛**：`OperationLogList` 的 HTTP 方法与操作类型映射、`AiConfig` / `RuntimeView` 各自的状态映射都是页面专用、单处使用，未并入 `enumLabels.ts`；若后续出现第二处使用，需要收敛。
5. **`utils/error.ts` 删除后，错误提取逻辑在各模块内就地实现**（`apiError` / `extractError`），存在多个近似副本。属阶段 8 未覆盖的清理项。
6. **环境恢复后需要一次性验证的范围很大**：阶段 5 补齐的 12 项、阶段 6 的 3 个工作区、阶段 7 的 5 个工作区、阶段 8 的结构性删除，外加此前 2026-09-12 的两轮缺陷修复。建议按 `项目真实状态看板.md` 的「第 1 步」分批进行。
