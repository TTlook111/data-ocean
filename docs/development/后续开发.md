### 当前建议执行顺序

> **本节在 2026-09-12 调整过。** 原顺序（P9 → P12 → P3/测试 → P4）是**功能待办**排序，其前提是「主链路已闭环，只剩功能增强」。2026-09-11 的前后端审查推翻了这个前提：后台前端重构的信息架构尚未冻结，且阶段 1–7 从未做过运行时验收。
>
> **执行顺序的唯一权威版本在 `docs/development/项目真实状态看板.md` 的「当前开发顺序」一节。** 本节只做摘要，避免两处各写一份而漂移。

#### 为什么调整

后台前端重构的信息架构是权限体系设计的**硬前置** —— `开发指导` §17 完成定义第 10 条要求「新前端信息架构稳定，可以作为后续权限系统重新设计的业务基础」，§18 禁止事项也明说「不在后台整体结构稳定前实施新的权限体系」。实质理由：新权限模型要定义菜单权限、页面权限、Tab 权限、操作权限、数据范围这五类，而这五类的划分依据就是业务域 / 工作区 / Tab 的最终形态。结构还在动的时候设计权限粒度，等于给一个还在改的目录编索引。

#### 轨道 A：环境与前端收尾（当前主线）

1. **恢复可运行环境**（阻塞项）—— 补 `docker-compose.yml` 并修正 README / CLAUDE.md 的启动说明。在此之前所有需要 MySQL / Redis / Milvus 的运行时验证都做不了。
2. **阶段 6–8 重构** —— 阶段 6–7 **未做**（`/admin/access`、`/admin/operations/*`、`/admin/platform/*` 路由可达但指向重构前的实现，需按 `开发指导` §7.13–§7.18 的目标设计重做）；随后做阶段 1–5 的真实验收（按 §16 四组场景，此前从未运行时验证）；最后阶段 8 收敛（删旧视图、合并重复 API 封装）。
3. **随收尾一起修的后端缺陷** —— P1 审核意见查询接口（唯一卡住验收标准的后端缺口）、`review_status` 死列、P2-3.2 术语删除清理、C1、C2。详见 `docs/review/2026-09-11-后台前端重构审查-后端事实问题.md`。

#### 轨道 B：独立安全修复（不跟任何阶段）

- **P0 知识回滚绕过审核** —— 已登记的流程绕过漏洞，任何调用方都能把未审核内容写入 Milvus。单方法前置校验，成本极低，**不应等前端收尾**。

#### 轨道 C：权限体系重构（轨道 A 完成后）

- 先更新《DataOcean 完整权限体系设计》再实施，不要从零写。前后端必须成对改：前端当前按 `开发指导` §13 硬编码「真实 `*` 超级管理员」假设，且 `guards.ts` 中故意不实现 `meta.permission`（2026-09-12 清理死代码时已留注释），新模型落地时前端需专门做一次「消费权限」改造。

#### 轨道 D：原有功能待办（轨道 A 之后按需）

原来的排序在此保留，只是不再是「下一步」：

1. ~~**Phase 1：代码可信度**~~（✅ 已完成 2026-08-21，详见 CLAUDE.md）
2. **Phase 2：后端真执行**（~2-3 天）—— P9 告警触发执行逻辑（定时扫描 metric + 触发通知 + 告警历史）
   > **理由**：开源项目应避免「前端能配置，后端没实现」的空壳功能；告警需要真实执行才能形成可验证的运维闭环。
3. **Phase 3：管理端闭环**（~1-2 天）—— P12 告警规则与告警历史前端页面
   > **理由**：Phase 2 后端能力就绪后，前端页面才有实际展示价值。
4. **Phase 4：用户覆盖面扩展**（~4-6 天）—— P3 PostgreSQL 数据源支持、Agent workflow 集成测试补强
   > **理由**：PG 用户群体庞大，只支持 MySQL 会劝退大量潜在用户（sqlglot 已支持 PG 方言，改动量可控）。集成测试是开源协作基础设施——没有测试保护，贡献者的 PR 不敢合。
5. **Phase 5：规模化优化**（按需）—— P4 图数据库血缘迁移
   > **触发条件**：当血缘关系超过数万条、SQL JOIN 查询响应 > 2s 时再实施。
6. **P13 / P14 / P15**（2026-09-12 新增，见下）—— 后端能力补全，可与轨道 A 的第 3 项合并排期。

### P5 — Java 持久化会话与异步长期摘要 [已完成 ✅]

> **现状**：Java 持久化完整会话消息和结构化长期摘要；Python 不保存会话状态，也不接收 conversationId。每次查询由 Java 组装长期摘要和最近三轮完整对话，按请求发送给 Python。

**实现内容**：
- 新增 `conversation_context_summary` 表，保存摘要 JSON、已覆盖消息游标和摘要版本
- Java 新增摘要服务：从消息表提取增量，过滤查询结果明细，只保留查询事实后异步调用 Python
- Python 新增 `/internal/query/context-summary`，复用现有外部 LLM 配置生成结构化摘要
- 查询请求发送 `conversation_summary` + 最近三轮完整对话；摘要失败时保留原有查询链路
- 摘要调用使用独立线程池，不占用查询 Agent 线程

### P9 — 告警触发执行逻辑

> 近期功能增强任务，不是占位项；P12 的告警历史页面需要依赖这里的执行与历史数据。

**背景**：后端 `alert_rule` 表和 `AlertController` 已完整实现（CRUD + toggle），但缺少定时扫描 metric 并触发通知的实际执行逻辑。告警规则定义了 ERROR_RATE / SLOW_QUERY_COUNT 两种监控指标和阈值（实体字段名为 `metric`），但无后台任务去比对和触发。

> 注：Controller 实际类名为 `AlertController`（非 `AlertRuleController`），API 路径为 `/api/admin/alert-rules`。

**改动范围**：

1. 新增 `AlertEvaluateJob` 定时任务（每 5 分钟执行）：
   - 读取所有启用的 `AlertRule`
   - 按 `metric` 字段查询对应指标（ERROR_RATE 查 query_audit_log 的成功率、SLOW_QUERY_COUNT 查慢查询数）
   - 与阈值比较，触发时调用 `NotificationService.send()` 发通知
   - 记录告警历史（避免重复告警：同一规则在恢复前只告警一次）

2. 新增 `alert_history` 表：
   - Flyway 迁移脚本
   - 字段：rule_id、triggered_at、resolved_at、metric_value、threshold_value

**涉及文件**：
- 新增 `backend/.../audit/service/impl/AlertEvaluateJob.java`
- 新增 `backend/.../audit/entity/AlertHistory.java`
- 新增 `backend/.../audit/mapper/AlertHistoryMapper.java`
