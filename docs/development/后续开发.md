## 已确认的开发任务

### 执行口径

本文档只保留**未完成/未开始**的后续开发任务。已完成任务从正文删除，完成记录以 git history、CLAUDE.md 和对应审查报告为准。

P 系列按"执行优先级"组织，而不是严格按编号连续推进：`P0` 是独立的管理端补齐任务，`P3-P4` 是远期规划，`P5-P12` 是近期功能增强。依赖图中如果出现编号跳跃，是为了把远期任务和近期任务分开，不代表缺少任务定义。

### 当前建议执行顺序（面向开源项目）

截至 2026-08-21，主链路已经闭环，优化指导文档 32 项问题已全部修复，Phase 0-3 深度优化和 P6 操作日志覆盖已完成。后续按"开源项目"标准推进，优先级逻辑为：**代码可信度 → 功能完整性 → 管理端闭环 → 用户覆盖面扩展 → 规模化优化**。

1. **Phase 1：代码可信度**（~2-3 天）
   - 质量扫描 7 处严重问题修复（吞异常、SQL 拼接、Map 无校验、明文密码缓存）
   - P0 管理员反馈特权（让反馈→置信度链路按设计运转）
   - P5 Java 侧 Redis 记忆（消除多轮对话每次打 DB 的延迟差异）
   > **理由**：开源项目第一天就有人 review 代码。吞异常和 SQL 拼接会直接拉低项目可信度；P0/P5 都是半天级小任务，闭合已有设计不留半成品。

2. **Phase 2：后端真执行**（~2-3 天）
   - P9 告警触发执行逻辑（定时扫描 metric + 触发通知 + 告警历史）
   - P10 配额维度扩展（DEPARTMENT/DATASOURCE 维度校验 + 月度成本校验）
   > **理由**：开源项目最忌"前端能配置，后端没实现"。告警和配额的 CRUD 已暴露在管理端，后端不真执行 = 空壳功能，用户配了规则却不生效的体验比没有这个功能还差。

3. **Phase 3：管理端闭环**（~1-2 天）
   - P12 告警历史 + 配额管理前端页面
   > **理由**：Phase 2 后端能力就绪后，前端页面才有实际展示价值。告警历史列表 + 配额用量可视化让管理端完整可用。

4. **Phase 4：用户覆盖面扩展**（~4-6 天）
   - P3 PostgreSQL 数据源支持
   - Agent workflow 集成测试补强
   > **理由**：PG 用户群体庞大，只支持 MySQL 会劝退大量潜在用户（sqlglot 已支持 PG 方言，改动量可控）。集成测试是开源协作基础设施——没有测试保护，贡献者的 PR 不敢合。

5. **Phase 5：规模化优化**（按需）
   - P4 图数据库血缘迁移
   > **触发条件**：当血缘关系超过数万条、SQL JOIN 查询响应 > 2s 时再实施。

### P0 — 管理员反馈特权（反滥用机制补全）

**背景**：设计文档要求管理员/分析师的"踩"直接生效且权重为普通用户 3 倍，当前实现中所有用户走相同流程，未区分角色。

**改动范围**：

- `UserFeedbackServiceImpl.submitFeedback()` 增加角色判断逻辑
- 管理员/分析师的 DISLIKE 跳过审核队列，直接触发 `USER_DISLIKE_CONFIRMED` 事件，delta 使用 -45（普通用户 -15 的 3 倍）
- 普通用户流程不变（限流 → 审核队列 → 组阈值检测）

**涉及文件**：
- `backend/.../fieldtag/service/impl/UserFeedbackServiceImpl.java`
- `backend/.../fieldtag/service/impl/FeedbackReviewServiceImpl.java`

**文档更新**：完成后更新 CLAUDE.md 的 fieldtag 模块描述（如行为变了）

- 引入图数据库（如 Neo4j 或 NebulaGraph）

### P9 — 告警触发执行逻辑

> 近期功能增强任务，不是占位项；P12 的告警历史页面需要依赖这里的执行与历史数据。

**背景**：后端 `alert_rule` 表和 `AlertController` 已完整实现（CRUD + toggle），但缺少定时扫描 metric 并触发通知的实际执行逻辑。告警规则定义了 ERROR_RATE / SLOW_QUERY_COUNT / COST_DAILY 三种监控指标和阈值（实体字段名为 `metric`），但无后台任务去比对和触发。

> 注：Controller 实际类名为 `AlertController`（非 `AlertRuleController`），API 路径为 `/api/admin/alert-rules`。

**改动范围**：

1. 新增 `AlertEvaluateJob` 定时任务（每 5 分钟执行）：
   - 读取所有启用的 `AlertRule`
   - 按 `metric` 字段查询对应指标（ERROR_RATE 查 query_audit_log 的成功率、SLOW_QUERY_COUNT 查慢查询数、COST_DAILY 查 llm_usage_log 的当日费用）
   - 与阈值比较，触发时调用 `NotificationService.send()` 发通知
   - 记录告警历史（避免重复告警：同一规则在恢复前只告警一次）

2. 新增 `alert_history` 表：
   - Flyway 迁移脚本
   - 字段：rule_id、triggered_at、resolved_at、metric_value、threshold_value

**涉及文件**：
- 新增 `backend/.../audit/service/impl/AlertEvaluateJob.java`
- 新增 `backend/.../audit/entity/AlertHistory.java`
- 新增 `backend/.../audit/mapper/AlertHistoryMapper.java`
- 新增 `src/main/resources/db/migration/V48__create_alert_history.sql`（当前迁移已到 V47）

**文档更新**：完成后更新 CLAUDE.md 的 audit 模块描述
