## 开发流程

### 日常开发（每个任务完成后）

1. 代码实现并提交
2. **更新 CLAUDE.md** — 如果改了架构、模块职责、技术栈、API 边界
3. **更新本文档** — 删除已完成任务，记录新发现的待办

### 大版本完成后

4. **跑一次文档一致性检查** — 对比 CLAUDE.md 和实际代码，修复不一致

一致性检查方法：让 AI Agent 读 CLAUDE.md 的每一项声明，与代码交叉验证（技术栈版本、模块列表、API 端点、枚举值、测试数量等）。

#### 轨道 B：权限体系重构（轨道 A 完成后）

先更新《DataOcean 完整权限体系设计》再实施，不要从零写。前后端必须成对改：前端当前按 `开发指导` §13 硬编码「真实 `*` 超级管理员」假设，且 `guards.ts` 中故意不实现 `meta.permission`（2026-09-12 清理死代码时已留注释），新模型落地时前端需专门做一次「消费权限」改造。

原因见状态看板：新权限模型要定义菜单权限、页面权限、Tab 权限、操作权限、数据范围五类，其划分依据就是业务域 / 工作区 / Tab 的最终形态。结构还在动的时候设计权限粒度会返工。

#### 轨道 C：功能待办（轨道 A 之后按需）

1. **P9 告警触发执行逻辑**（~2-3 天）
   > **理由**：开源项目应避免「前端能配置，后端没实现」的空壳功能；告警需要真实执行才能形成可验证的运维闭环。
2. **P12 告警规则与告警历史前端页面**（~1-2 天）—— 依赖 P9
   > **理由**：P9 后端能力就绪后，前端页面才有实际展示价值。
3. **P3 PostgreSQL 数据源支持** + **Agent workflow 集成测试补强**（~4-6 天）
   > **理由**：PG 用户群体庞大，只支持 MySQL 会劝退大量潜在用户（sqlglot 已支持 PG 方言，改动量可控）。集成测试是开源协作基础设施——没有测试保护，贡献者的 PR 不敢合。
4. **P4 图数据库血缘迁移**（按需）
   > **触发条件**：当血缘关系超过数万条、SQL JOIN 查询响应 > 2s 时再实施。

### 待产品确认的取舍

> 2026-09-12 实施责任人筛选时做的取舍，**未经确认**，改动量都很小。

**问题中心的「分配给我的」是显式筛选，不是默认开启。**

`开发指导` §7.7 原文是「默认**优先**展示高危、阻断和分配给当前用户的问题」。当前实现为筛选按钮（默认关）：「强制默认过滤会让多数管理员首次进入就看到空列表，反而不知道系统里存在问题」；而规范的意图是「优先」而非「只显示」，要真正落实需后端按责任人排序。

- 若要求「默认开启」：改 `frontend/src/views/admin/governance/IssueList.vue` 的 `toggleMyIssues()`，在 `onMounted` 里默认选中。
- 若要求「按责任人排序」：需后端 `QualityIssueServiceImpl.listIssues` 的 `orderBy` 增加排序参数。

### P4 — 数据血缘图数据库

> **标注为远期规划**：基于 SQL 的数据血缘已在 2026-08 实现（V46/V47 迁移，17 个 Java 文件，前端 LineageGraph/LineageViewer/DataLineage）。P4 特指当 SQL JOIN 查询性能成为瓶颈时，将存储和查询引擎从 MySQL 迁移到图数据库。当前血缘数据量不大，SQL JOIN 查询可满足需求。图数据库引入需要新的运维成本，应在血缘查询性能成为瓶颈时再考虑。

### P9 — 告警触发执行逻辑

> 近期功能增强任务，不是占位项；P12 的告警历史页面需要依赖这里的执行与历史数据。

**背景**：后端 `alert_rule` 表和 `AlertController` 已完整实现（CRUD + toggle），但缺少定时扫描 metric 并触发通知的实际执行逻辑。告警规则定义了 ERROR_RATE / SLOW_QUERY_COUNT 两种监控指标和阈值（实体字段名为 `metric`），但无后台任务去比对和触发。

> 注：Controller 实际类名为 `AlertController`（非 `AlertRuleController`），API 路径为 `/api/admin/alert-rules`。

**改动范围**：

1. 新增 `AlertEvaluateJob` 定时任务（每 5 分钟执行）：
   - 读取所有启用的 `AlertRule`
   - 按 `metric` 字段查询对应指标（ERROR_RATE 查 query_audit_log 的成功率、SLOW_QUERY_COUNT 查慢查询数）
   - 与阈值比较，触发时调用 `NotificationService.send()` 发通知
   - 记录告警历史（避免重复告警：同一规则在恢复前只告警一次）

2. 新增 `alert_history` 表：
   - Flyway 迁移脚本（当前迁移已到 V51）
   - 字段：rule_id、triggered_at、resolved_at、metric_value、threshold_value

**涉及文件**：
- 新增 `backend/.../audit/service/impl/AlertEvaluateJob.java`
- 新增 `backend/.../audit/entity/AlertHistory.java`
- 新增 `backend/.../audit/mapper/AlertHistoryMapper.java`
- 新增 `src/main/resources/db/migration/V52__create_alert_history.sql`

**文档更新**：完成后更新 CLAUDE.md 的 audit 模块描述
