**步骤 3：`/api/iam-s1/subjects` 语义修正（已完成）**

原实现用 `requireGlobalFunction('security:permission:view')`，而 B0 冻结该码依赖**负责源**（B0 权限清单第 31 项标注「源」；同类 `security:permission:manage` / `mask:view` / `effective:view` / `approval:*` 全是「源」，只有 `organization:*` 是「全」）。同类三处实现都正确带了负责源，`/subjects` 是唯一漏掉的一处——属实现偏离，不是设计取舍。

该接口同时服务三种用途，现按 `scope` 显式分派：

| scope | datasourceId | 服务端判定 | 调用方 |
|---|---|---|---|
| `GRANT` | **必填** | `security:permission:view` + 该数据源负责源（同一绑定） | 数据授权面板 |
| `EFFECTIVE` | **必填** | `security:effective:view` + 该数据源负责源（同一绑定） | 实际权限面板 |
| `ORGANIZATION` | 不接受 | `organization:user:view`（全局只读，不要求 `manage`） | 用户角色与负责源页面 |

`scope` 为必填枚举，缺失或未知值直接拒绝。`GRANT` / `EFFECTIVE` 必须校验**请求中的 datasourceId**，而非“至少负责一个数据源”——否则负责 A 源的人可以按 B 源的用途加载主体。前端两个面板的对应下拉改为按当前数据源加载，切换数据源时重载。

**并发幂等闭环（第三轮复审后补完）**

上一轮的幂等只在顺序调用下成立：`查询 ACTIVE → 无同策略 → 撤销旧策略 → 新增`，两个请求并发时会各自读到“没有 ACTIVE”并各插一条，而 V55 没有唯一约束兜底。修复：

- `DbColumnMetaMapper.selectForUpdate`：按快照 + 表 + 列对字段元数据行取 `SELECT ... FOR UPDATE`，把并发确认串行化。`confirm` 与 `reject` 抢同一把锁，避免“一个写保护、另一个清标记”的不可复现结果。
- `MetadataEntityMapper.selectByIdForUpdate`：锁后重读候选状态必须用**当前读**。MySQL 默认 REPEATABLE READ 下普通 `SELECT` 读的是事务开始时的快照（该快照在拿锁前就已建立），看不到等待期间其他事务的提交。
- 候选取到锁后若已被处理（`pending_mask` 不存在）→ 幂等成功返回，不重复写保护、不重复清理。
- `clearPendingMask` 检查 `updateById` 返回值：更新 0 行抛 409 并回滚，否则会留下“保护已写入但候选没清掉”的不一致状态。
- 迁移到 `MetadataEntityService.getEntityByIdForUpdate` 也顺带修掉了一个隐患：`SELECT ... FOR UPDATE` 与普通 `SELECT` 混用时的快照问题。

**说明**：并发测试验证的是**锁机制本身**（`selectForUpdate` 的串行化与当前读语义），“service 是否按‘先锁后读’的顺序调用”由单测的顺序断言钉住。端到端的“两个完整 `confirm` 调用最终只剩一条 ACTIVE”需要建 `metadata_entity` / `db_column_meta` / `iam_s1_*` 的完整 fixture（含 `saveProtection` 依赖的权限与修订表），尚未补。
