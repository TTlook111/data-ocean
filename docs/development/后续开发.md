## 待产品确认的取舍

**问题中心的「分配给我的」是显式筛选，不是默认开启。**

`开发指导` §7.7 原文是「默认**优先**展示高危、阻断和分配给当前用户的问题」。当前实现为筛选按钮（默认关）：强制默认过滤会让多数管理员首次进入就看到空列表，反而不知道系统里存在问题；而规范的意图是「优先」而非「只显示」，要真正落实需后端按责任人排序。

- 若要求「默认开启」：改 `frontend/src/views/admin/governance/IssueList.vue` 的 `toggleMyIssues()`，在 `onMounted` 里默认选中。
- 若要求「按责任人排序」：需后端 `QualityIssueServiceImpl.listIssues` 的 `orderBy` 增加排序参数。

## P3 — PostgreSQL 数据源支持

> **远期规划**：项目处于 MVP 阶段，MySQL 是唯一数据源。PostgreSQL 支持涉及元数据采集器、SQL 方言、连接池的全面适配，应在核心功能稳定后再考虑。

**改动范围**：

- 数据源模块增加 PostgreSQL 类型支持
- 元数据采集器适配 PostgreSQL 的 `information_schema` 和 `pg_catalog`
- SQL 沙箱适配 PostgreSQL 方言（sqlglot 已支持）
- 连接池管理适配 PostgreSQL JDBC 驱动

**文档更新**：完成后更新 CLAUDE.md 的 MVP scope 描述

## P4 — 数据血缘图数据库

> **远期 / 按需**：基于 SQL 的数据血缘已实现。P4 特指当 SQL JOIN 查询性能成为瓶颈时，把存储和查询引擎从 MySQL 迁移到图数据库。当前血缘数据量不大，SQL JOIN 可满足需求；引入图数据库需要新的运维成本。

**触发条件**：血缘关系超过数万条、SQL JOIN 查询响应 > 2s。

**改动范围**：

- 引入图数据库（如 Neo4j 或 NebulaGraph）
- 将表/列血缘关系写入图数据库
- 血缘查询从 SQL JOIN 改为图遍历
- 前端血缘可视化适配图数据库查询结果

## P9 — 告警触发执行逻辑

> P12 依赖本任务的执行与历史数据。

**背景**：后端 `alert_rule` 表和 `AlertController` 已实现 CRUD + toggle，但缺少定时扫描 metric 并触发通知的执行逻辑。告警规则定义了 ERROR_RATE / SLOW_QUERY_COUNT 两种指标和阈值（实体字段名为 `metric`），但没有后台任务去比对和触发。

> 注：Controller 实际类名为 `AlertController`（非 `AlertRuleController`），API 路径为 `/api/admin/alert-rules`。

**改动范围**：

1. 新增 `AlertEvaluateJob` 定时任务（每 5 分钟执行）：
   - 读取所有启用的 `AlertRule`
   - 按 `metric` 字段查询对应指标（ERROR_RATE 查 query_audit_log 的成功率、SLOW_QUERY_COUNT 查慢查询数）
   - 与阈值比较，触发时调用 `NotificationService.send()` 发通知
   - 记录告警历史（避免重复告警：同一规则在恢复前只告警一次）

2. 新增 `alert_history` 表：Flyway 脚本 `V52__create_alert_history.sql`（当前迁移已到 V51），字段 rule_id、triggered_at、resolved_at、metric_value、threshold_value

**涉及文件**：
- 新增 `backend/.../audit/service/impl/AlertEvaluateJob.java`
- 新增 `backend/.../audit/entity/AlertHistory.java`
- 新增 `backend/.../audit/mapper/AlertHistoryMapper.java`
- 新增 `src/main/resources/db/migration/V52__create_alert_history.sql`

**文档更新**：完成后更新 CLAUDE.md 的 audit 模块描述
