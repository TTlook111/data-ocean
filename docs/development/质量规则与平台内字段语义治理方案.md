# 质量规则页面与平台内字段语义治理方案

> 状态：方案整理稿；平台内字段解释方向已明确，页面与功能尚未实施。日期：2026-10-21。
> 依据：用户本轮提供的质量规则列表、规则详情两张截图，以及本轮读取的现存代码。截图是用户提供的页面证据；未操作浏览器、未进行交互或可访问性实测。本轮只编写方案，不修改业务实现、数据库或运行配置。

## 1. 产品目标

DataOcean 应帮助用户把接入的数据解释清楚，形成可维护、可审核、可复用的业务知识。字段含义不清时，用户能在平台内获得解释建议、补充业务依据、确认定义，并看到这些治理成果何时用于问数。

治理成果保存在 DataOcean。业务数据源继续使用只读连接，平台保存原始采集事实、平台业务解释及各自来源；重新采集后保留有效的人工治理成果，并对结构变化提示复核。

本轮已经明确的方向是“在平台内帮助理解和治理字段”。下文的页面布局、字段模型、规则调整和实施顺序属于设计建议，不能当作已有能力。本次用户请求是整理文档与核查 Git 忽略规则，不包含实施页面、增加迁移或修改应用数据。

当前能力与证据以[治理模块](../modules/004-metadata-governance.md)、[知识模块](../modules/006-knowledge.md)和[项目现状](../项目现状.md)为准；本方案只维护目标、差距与设计建议，剩余执行事项进入[后续开发](后续开发.md#11-质量规则页面与平台内字段解释)。

## 2. 当前功能实际承担什么

| 入口 | 当前职责 | 用户使用它要完成的任务 |
| --- | --- | --- |
| 质量规则 | 根据已注册模板配置范围、条件、严重程度、扣分和启停 | 定义检查标准 |
| 治理总览 | 针对数据源和快照执行检查，查看批次覆盖和问题 | 了解哪些对象存在什么问题 |
| 问题中心 | 查看、分派、确认、处理和复查问题 | 跟踪问题处理过程 |
| 资产状态 | 管理发现、正常、推荐、废弃、禁止等状态 | 决定对象的治理准入状态 |
| 字段治理 | 当前主要是标签、可信度、反馈和脱敏候选 | 管理字段标识和使用保护 |
| 语义中心 | 术语、字段映射、AI 释义候选、知识审核发布及后续索引构建 | 沉淀和发布业务口径 |

质量规则页是标准配置入口。字段的业务解释需要通过字段治理、问题处理与语义知识流程协作完成。

本轮代码核对确认以下情况：

1. `CompletenessChecker` 用采集快照的 `tableComment/columnComment` 判断注释缺失，提示“建议补充注释”；尚未在这项检查中消费经过审核的平台字段解释。
2. `GovernanceFieldsView` 当前展示标签、可信度、反馈审核和脱敏候选，没有承接字段业务解释的完整操作流程。
3. 现有知识流程已经支持 AI 释义候选、人工采纳、审核和发布；候选以文档为操作中心，用户从字段问题进入时仍缺少集中入口。
4. 规则同时包含元数据结构检查和真实数据只读检查，不能全部按同一种处理方式呈现。数据级检查当前有抽样覆盖限制。
5. `TIME_TABLE_NO_UPDATE` 当前根据估算行数为零提示“可能长期无数据写入”；这个证据不足以证明长期未更新。它和基于时间字段的 `DATA_STALE_TABLE` 应有明确的含义区分，后续需核对命名与执行依据，历史记录保留原依据。

因此，现有能力可以复用，但“字段含义不清”的发现、解释、确认、复查和问数使用尚未在字段这一层形成完整流程。

## 3. 两张截图的页面问题与美化方向

### 3.1 列表：减少重复，让规则更容易理解

截图 1 中，规则名称与检查类型大量重复；操作列同时展开详情、编辑、复制、删除，占用较多空间。表格右侧仍有启用状态等信息，当前宽度分配让核心状态不容易被看到。标题与表格之间的留白较大，筛选项的用途主要依赖占位文案。

沿用现有海蓝画布、侧栏、公共 ScopeBar 和白色工作面板，集中调整内容区域：

- 标题与主要操作在同一行，收紧标题上下留白。保留一个页面主标题和标题旁说明入口。
- 常用筛选保留搜索、检查类别和状态；范围、维度和已删除筛选放入可展开的筛选区。展开后仍有清楚的可见标签，收起时保留已生效条件与清除入口。
- 范围切换建议改为“当前数据源适用规则 / 全局规则”。前者可以包含全局继承规则，行内明确标为“全局默认”，避免截图中选择“数据源规则”却看到“全局”而产生误解。
- 全局规则维护视图明确说明不受上方快照限制；继续使用现有公共范围栏，不新增第二套数据源或快照选择器。
- 规则名点击查看详情；每行保留“编辑”和“更多”，将复制、删除等放入菜单，保留权限控制、删除确认及恢复语义。
- “资产状态维护”放到次要关联入口，主操作仍为新增规则。

建议的主表结构：

| 列 | 呈现方式 |
| --- | --- |
| 规则 | 主行名称；次行显示不重复的条件摘要，维度用文字或轻量标签表示 |
| 检查对象 | 明确“元数据 / 业务数据”；未来已实现的语义规则可标“平台语义” |
| 适用范围 | 全局默认、当前源、表或字段；长路径可查看完整内容 |
| 级别与影响 | 高/中/低文字、扣分及必要说明；不能只靠颜色识别 |
| 状态 | 启用、停用、部分目标被覆盖、无执行模板等真实状态 |
| 操作 | 编辑、更多；查看详情由规则名承担 |

配置版本移入详情。首轮不新增装饰性统计卡片；若后续展示最近执行和命中数，必须由后端按真实范围聚合，不能用当前页条数或缺少记录推导执行结论。

桌面优先保证规则、范围、启停和操作可见。必要横向滚动只发生在表格区域；窄屏筛选自然换行，不挤压成无法辨认的小控件。固定操作列的阴影只在确有横向溢出时出现。

### 3.2 详情：先解释规则，再展示技术与历史

截图 2 的信息顺序接近配置对象的字段顺序，参数直接显示 JSON，执行与迁移说明同时占据主区域。用户仍需要自行理解检查条件、覆盖范围和下一步操作。

建议使用桌面右侧详情抽屉，窄屏全屏展示；沿用现有组件与样式令牌。抽屉顶部显示规则名称、启用状态及可执行性，正文分为三个页签：

1. **检查说明**：检查什么对象、何时触发、使用什么证据、会带来什么影响，以及去哪里处理。
2. **执行记录**：批次、实际配置版本、目标数量、检查覆盖、发现问题与失败原因；可跳到对应问题。
3. **配置记录**：版本、操作人、时间、变更内容；迁移基线与真实后续变更分开标识。

参数默认转换为业务文案。例如 `staleDays: 30` 显示“超过 30 天未更新时提示”。具体读取哪个时间字段应以可核对的执行记录为准，不能在未执行时假定使用了某个字段。原始配置放入“技术详情”。

没有带版本的历史记录时显示“暂无可追溯执行记录”，不推断“从未执行”。旧结果缺少版本依据的限制继续保留在适当说明中，不补造历史。

### 3.3 新增和编辑：配置时看得懂影响

保留模板驱动表单，将流程清晰分为“选择检查 → 指定对象与条件 → 设置影响”。选择模板后实时显示自然语言预览；范围覆盖和启用影响在保存前可见。仅展示已有执行器支持的模板，不添加不可执行的装饰性选项。

可访问性方面需在实施后检查筛选标签、菜单及抽屉键盘操作、焦点返回、状态说明、对比度和窄屏滚动；本轮截图只能支持风险判断，不能作为这些交互已经通过的证据。

## 4. 平台内治理应该形成的操作流程

### 4.1 从“发现缺少说明”直接进入解释工作

问题详情中的操作应根据问题类型提供：

- 字段含义不清：在平台补充解释、AI 辅助解释、关联已有术语。
- 字段口径冲突：对比原始注释与平台定义，查看各自依据，提交澄清。
- 关系不清：查看已确认的逻辑关系，按现有受控流程补充关系说明。
- 空值、重复、引用异常：查看检查证据、分派与跟进处置，复查真实数据结果。

处理语义问题时，保留当前数据源、快照、表和字段上下文，不让用户重新寻找对象。

### 4.2 字段页同时展示原始事实和平台解释

建议把“业务解释”作为字段治理的主要工作面，现有标签、可信度和脱敏功能继续保留在相应页签。

一个字段的业务解释至少包含：业务名称、含义、单位或币种、适用口径、已确认枚举含义、关联术语，以及确认人、审核状态、版本和来源。不是所有字段都要求填写所有项目，必填项由字段类型与实际场景决定。

示例，仅用于说明目标交互，不代表当前数据：

| 内容 | 示例 |
| --- | --- |
| 字段 | `orders.pay_amt` |
| 数据库原始注释 | 空 |
| AI 候选 | 可能表示订单支付金额；单位、退款处理方式待确认 |
| 业务人员确认后的定义 | 订单实际支付金额，单位为人民币元；退款另行记账，不从本字段扣减 |
| 平台语义状态 | 已审核；可查看确认依据和适用版本 |
| 问数使用状态 | 单独显示是否已收录到当前知识索引 |

用户在平台内完成业务解释后，其他用户能读懂字段。源库原始注释仍保持采集时的真实状态。

### 4.3 AI 提供候选和依据，人工形成业务事实

首版使用已有元数据、同表上下文、合规关系及适用的已审核术语生成候选，继续遵循当前 AI 释义流程不自动读取业务行的边界。已有采样值也不能因为保存在平台就直接发送给模型。

候选需要展示“建议解释、参考依据、仍待确认的问题”。例如字段名为 `status` 时，AI 可以指出可能的状态用途，但不能凭字段名宣称某个数字一定代表“已支付”。没有依据时允许保留未知状态。

字段页应支持接受并编辑、退回、补充依据和提交审核。已审核术语的精确字段映射继续复用；不要求每个字段都人为创建一个独立业务术语。

优先复用现有候选、审核、知识版本和来源依赖能力。确需补充字段级语义修订时，应形成明确的权威记录，并让目录、问题中心和知识文档引用同一版本；不能把字段页备注、实体描述和文档正文分别维护成三份互不一致的定义。

### 4.4 治理状态与问数生效状态分别表达

建议的语义工作状态包括未解释、候选待确认、草稿、待审核、已审核、需复核。它与字段的 NORMAL、BLOCKED 等治理状态是不同维度。

主流程为：

```mermaid
flowchart LR
    A[发现字段缺少解释] --> B[AI 候选或人工填写]
    B --> C[人工校正与审核]
    C --> D[保存平台语义版本]
    D --> E[语义问题复查]
    D --> F[知识版本审核与发布]
    F --> G[单独确认索引构建]
    G --> H[后续问数使用]
```

平台定义审核通过后可以完成相应语义问题的复查；问数仍须遵守知识版本发布与单独确认 RAG 构建的现有合同。页面分别说明“业务解释已审核”和“问数知识待更新”，不能用一个“已生效”标签省略两者的差别。

当前知识生成依赖已发布快照。首版不把新语义完整性检查默认设成快照发布的硬门槛，避免形成“快照未发布，无法整理知识；知识未整理，又无法发布快照”的循环。若后续需要更严格准入，应独立设计待发布快照的语义审核与来源固定机制。

## 5. 质量规则需要如何配合

| 检查类别 | 判断依据 | 可以在平台内完成的治理 | 必须如实保留的边界 |
| --- | --- | --- | --- |
| 平台语义完整性 | 是否有经过审核且仍适用的字段解释 | AI 辅助、人工定义、关联术语、审核与复查 | 不能以未确认的 AI 候选充当已审核事实 |
| 平台口径一致性 | 当前有效定义、术语映射及其依据是否冲突 | 对比、澄清、修订和重新审核 | 不能按字段同名就认定含义相同 |
| 元数据结构与来源完整性 | 源库采集事实、采集时间、物理键与原始注释 | 保留说明、补充受控逻辑关系、更新采集 | 平台解释不代表源库物理注释或约束已经改变 |
| 业务数据质量 | 只读检查的空值、重复、引用或更新时间证据 | 分派、跟进、记录处置和复查 | 写了解释或关闭问题不能证明坏数据已经修复；抽样结果不能声称全表通过 |

建议为“缺少可用业务解释”增加明确的语义检查能力，执行时读取经过审核的平台定义。原始注释缺失作为来源质量事实单独可见，不能简单把新定义塞回 `columnComment` 来制造源库已修复的结果。

首轮保留既有历史质量分和原检查依据，新增可解释的语义覆盖状态。是否调整评分权重、发布门槛或停用某些原始结构规则，需要另行评估；未确定前不重复计分，也不回写旧批次结果。

物理外键缺失与平台缺少已确认的逻辑关系同样应分清。通过平台确认关系能补充理解和受控查询依据，不能描述成业务库已经新增了外键约束。

重新采集后，以数据源及对象身份、结构变化和来源版本核对语义适用性。相同字段名不足以自动继承定义；字段类型、含义或依赖变化时提示复核。被禁止或废弃的字段不因拥有平台解释而恢复检索或问数资格。

## 6. 建议实施顺序与验收

| 阶段 | 交付 | 验收重点 |
| --- | --- | --- |
| 第一阶段：规则页美化和表达整理 | 列表列宽与去重、范围表达、操作菜单、自然语言参数、详情抽屉与历史分区 | 两张截图对应的页面清晰可读；权限、范围、覆盖优先级和历史证据不被改写 |
| 第二阶段：字段解释最小流程 | 从一个字段问题进入、生成候选、人工修订审核、保存适用版本、复查语义问题 | 源库注释为空时，用户仍能在平台完成解释；候选不自动成为事实，失败不丢人工内容 |
| 第三阶段：知识与采集协作 | 目录和问题页读取同一语义版本、进入现有知识发布与独立索引构建流程、重新采集后的复核 | 新定义用于后续受保护问数；旧版本可追溯，结构变化和撤销定义不会静默沿用 |

涉及新的字段语义持久化或规则执行器时，再根据批准后的详细设计评估迁移；本方案不预占迁移号，也不授权迁移、新建容器、修改业务库或变更账号权限。

实施中的检查分为三类：配置与业务逻辑用定向测试验证；真实权限和字段处理流程用隔离环境 API 验证；列表、抽屉、窄屏与键盘操作由实际页面验收。当前两张截图仅证明相应页面状态，不证明完整交互已通过。
