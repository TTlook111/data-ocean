# DataOcean 自然语言问数、LangGraph 编排与会话记忆方案

> 状态：待评审的产品与技术方案，尚未获得代码实施授权。
> 基线：main 的 d8cda57；代码事实核查日期 2026-09-25；按 2026-09-26 对产品目标的澄清整理。
> 本文先说明要交付的问数体验和知识维护流程，再记录当前差距与实施顺序。在明确同意实施之前，只修订本文，不修改代码、依赖、数据库迁移、运行服务或业务数据。

## 1. 要做成什么

DataOcean 面向不熟悉数据库表结构的业务用户。用户选择一个有权使用的数据源，在会话里直接提出自然语言问题；系统自行从该数据源的已治理知识中寻找表、字段、关联关系和业务口径，生成并安全执行只读 SQL，把得到的数据主要通过 ECharts 图表展示，并附必要的文字说明和表格。用户可以继续追问，不必每轮重新解释背景或手选表字段。

一次生成的 SQL 不一定能回答问题，因此正式问数链路使用 LangGraph 组织**有边界的检查和修正**：理解问题、检索知识、生成候选 SQL、核对 SQL 与问题是否相符；证据不足时补查知识，SQL 写法可修正时重新生成。每次候选 SQL 都必须重新经过权限与安全校验，只有通过校验才允许执行。执行后的结果也要核对是否足以回答原问题；不能确定时继续在预算内修正，或向用户澄清、说明无法可靠回答。循环次数、总时间和查询成本必须有上限，不能无限试错。

这是**一次提问内为得到用户所需数据而进行的有限次检索、SQL 生成与修正**。每次尝试都重新核对问题、权限和 SQL 安全性；得到符合问题的安全数据后结束本轮任务，超出重试或时间预算仍未得到时说明原因或请用户澄清。首期交付以最终得到一份可核验的安全查询结果为目标；一个问题同时规划多份独立子查询、进行开放式探索分析，可以在这条主链稳定后单独评审。

本方案还有两条支撑链：

- **会话链：**Java/MySQL 保存完整对话、任务和历史结果；Redis 为 LangGraph 保存同一会话的短期状态与 checkpoint，支持连续追问和中断后的受控恢复。
- **知识链：**连接数据源后采集元数据形成快照，完成治理并发布可信快照；AI 根据快照和已审核治理事实生成描述数据源的 skills.md 类文档草稿，由人审核、修订并确认发布/构建，随后切分、Embedding 并写入 Milvus。问数时通过 RAG 只取相关且获授权的知识，不把全库表字段一次性塞进模型上下文。

## 2. 用户实际经历的流程

1. 用户进入问数页，明确选择一个可用数据源，新建或打开该数据源下的会话。一个会话从创建到结束只属于这个数据源；支持同库多表关联，当前不做跨库 SQL。
2. 用户用自然语言提问，例如“上个月各地区销售额是多少”。用户无需知道表名、字段名、Join 条件或 SQL。
3. Java 校验用户、会话归属、数据源就绪状态和当前 S1 权限，给本轮规划提供获授权的候选范围。
4. LangGraph 结合本会话历史与术语表改写问题，再从当前数据源**现行 RAG 构建所绑定的来源快照**中逐层检索业务域、表、字段、关联和指标证据。来源快照可以早于最新已发布快照，页面显示版本落后提示；检索到的旧知识只是生成 SQL 的候选上下文，表字段是否仍可用以当前已发布元数据和 S1 授权为准。
5. 图根据证据生成候选 SQL，先对照问题检查所选指标、时间、筛选、分组、关联及输出列。缺少可信证据就补查 RAG；可修正的 SQL 问题就重新生成；业务口径无法确定时先请用户澄清，不猜测。
6. 每份候选 SQL 都用当前已发布快照经 S1 精确授权、AST 只读及危险操作校验、行条件和来源校验；旧 RAG 中已经不存在或不再获授权的表字段不能通过。非 SELECT、越权或危险函数直接拒绝，不能让模型通过改写绕过安全边界。通过后才在当前数据源的只读沙箱执行 SQL，取得实时数据。
7. 执行结果与用户问题再次核对。零行不自动等于 SQL 错误；结果形状或口径不符时，在剩余重试和时间预算内回到检索或生成节点，直到得到符合问题的安全数据或明确停止。Java 对可用结果复查权限并最终脱敏；前端以 ECharts 图表为主要展示方式，同时提供必要的说明、数据表和口径。结果不适合画图或图表生成失败时，说明原因并展示安全数据表，不编造图表。
8. Java 保存用户消息、助手回复、结果引用、任务终态和审计。用户稍后打开会话能看到完整历史，并继续追问。

图的主线可以概括为：

~~~mermaid
flowchart LR
    U[用户选源并提问] --> J[Java 会话与权限校验]
    J --> Q[LangGraph 理解和改写问题]
    Q --> R[在授权知识中 RAG 检索]
    R --> G[生成候选 SQL]
    G --> M[核对 SQL 是否回答问题]
    M -->|证据不足| R
    M -->|SQL 写法可修正| G
    M -->|含糊| C[请求澄清]
    M -->|语义符合| V[S1 授权与 SQL 安全校验]
    V -->|危险或越权| X[拒绝并说明]
    V -->|通过| E[只读沙箱执行]
    E --> K[核对结果与问题]
    K -->|证据不足且未超预算| R
    K -->|SQL 口径可修正且未超预算| G
    K -->|可用| P[Java 复查并脱敏]
    P --> A[ECharts 图表、说明和数据表]
    A --> H[MySQL 保存会话与审计]
~~~

这里的“SQL 满足用户要求”不是只让模型说“我觉得对”。至少要把结构化问题意图与 SQL AST、所用表字段、过滤条件、聚合和结果列对照；执行后再核对实际结果。对于没有足够业务证据的问题，正确行为是澄清或告知限制，不是反复生成到某条 SQL 恰好能执行。

## 3. skills.md 类文档是什么

skills.md 类文档是**一个数据源的可检索业务说明书**。文档体系本身要完整列出所绑定发布快照中的每张表、每个字段，帮助系统回答“这张表做什么、字段表示什么、哪些字段可以关联、指标怎么算、有哪些容易误用的地方”。它可以按业务域或表拆成多篇文档，也可以把从快照生成的完整字段清单作为文档体系的一部分，不要求把整个数据库写成一个巨大文件。RAG 只把与本次问题相关且允许使用的小段送入模型。

一份完整的发布清单至少说明：

| 知识 | 必须记录的内容 |
| --- | --- |
| 数据源与业务域 | 该源处理的业务主题、文档来源和对应的发布快照 |
| 表 | 发布快照中每张表的名称、用途、稳定身份、治理状态及适用范围 |
| 字段 | 发布快照中每个字段的名称、类型、所属表、可核实的释义、释义来源与审核状态 |
| 表与字段关联 | 经确认的表间关联、两端字段和具体 Join 条件；区分真实外键、人工确认关系与尚未确认的推断关系 |
| 血缘 | 经确认的表级上游/下游、字段级派生与列映射、转换含义和来源；明确标注它是数据流向还是可用于 Join 的关系 |
| 指标与场景 | 已审核的口径、表达式、时间/单位规则和真实查询场景；没有依据时可以为空 |
| 使用限制 | 敏感、禁用、废弃或含义待确认的表字段及其使用限制 |

**完整覆盖不等于 AI 可以编造完整释义。** 表字段的名称、所属关系、类型和治理状态必须直接从所绑定快照生成，不能交给模型自由补全；AI 只依据已有元数据和已审核业务事实撰写用途、释义及场景草稿，不能仅凭字段名推断业务意思或虚构 Join、指标。缺少注释或人工确认的字段仍列入清单，但业务释义标为“待确认”；依赖该释义的自动口径选择必须等待确认。人可以按实际业务逐步补齐释义，不因一个字段待确认就阻断整个数据源中其他可信字段。

现有 [skills.md 生成模板](../../python-service/dataocean/knowledge/prompts/skills_md_template.j2) 只要求每表列出 3～5 个核心字段，字段防坑指南也只覆盖易误用字段，**还没有达到上述完整字段覆盖目标**。实施时应让发布的文档体系列出该快照全部表字段，并为已有依据的字段提供可检索的已审核解释；Java 的结构化字段字典是校验字段存在、类型和治理状态的权威来源。释义待确认的字段仍应出现在文档清单中，不能把“有一篇文档”或“chunk 数量足够”当成覆盖完整。

**发布前必须逐表逐字段校验。** 以快照中的表 ID、字段 ID 或稳定表字段标识为基准，比对整套 skills.md 类文档：表和字段覆盖率必须为 100%，不得漏项、重复、错属表、改错字段名/类型，也不得出现快照中不存在的表字段。Join 条件、指标表达式和业务释义须能指向已确认的来源；无法证明的内容标为待确认，不写成事实。生成草稿不合格时报告具体差异并重新生成或人工修订；结构校验与人工业务审核都通过后才能发布并进入 RAG。禁用、废弃字段仍保留在内部文档清单中并标明限制，但不得作为可用字段进入问数检索或 SQL 规划；敏感字段仅在获授权时携带保护信息进入检索，最终结果仍由 Java 脱敏。

生成质量还要看文档是否能帮助问数：表用途与字段释义应具体、可核实，不用空泛的模板句充数；已确认的 Join 要写出两端字段和条件，指标要写明表达式、时间与单位口径。切分和索引后，核对每项允许检索的表字段事实都有可追溯的 chunk，并用固定测试问题验证能召回正确的表、字段和关联证据。结构覆盖、业务审核或检索验收任一不通过，都保持草稿/待处理状态，不把不合格文档发布给问数链路。

知识进入模型前还要经过当前用户的 S1 权限过滤。表描述、字段释义、Join 和指标都要能追溯到来源资源；涉及多表或多字段的事实，只有依赖项全部获授权才可使用。混合 chunk 不能只检查关联元数据就把整段原文送给模型，无法安全拆分时整段排除。权限过滤必须在候选检索阶段生效，避免无权知识占满 Top K 后才被丢弃。

### 3.1 skills.md 草稿的生成数据来源

生成时先固定一个 datasourceId 和一个已发布 snapshotId。Java 按这个快照组装结构化、带来源的事实输入，再让 Python 生成说明文字；不能只按 datasourceId 把不同时期的表、字段和关系拼在一起。每个事实保留来源对象 ID、快照 ID、关系类型、审核/治理状态，便于生成后逐项核对。

| 输入层 | 应提供的事实 | 用法与边界 |
| --- | --- | --- |
| 快照结构 | 同一 snapshotId 的表、全部字段、类型、注释、主键、索引和治理状态 | 字段清单由 Java 确定性生成，是完整覆盖和防止编造的基准；没有释义就标待确认 |
| 表与字段关联 | 同一快照的 table_relation，以及对应的 FOREIGN_KEY 图边；保留两端表字段、FK/INFERRED/MANUAL 类型、置信度和确认依据 | 真实外键及已人工确认的关系可形成 Join Path；仅按命名推断的关系只列候选，不能写成可执行 Join |
| 血缘 | metadata_relationship 中有明确来源的 LINEAGE 表级边、DERIVED_FROM 字段级边及列映射；必要时参考 query_lineage_table/column 审计记录 | 经确认的 ETL/人工血缘说明数据从哪里来、如何派生；查询血缘仅表明历史 SQL 用过哪些资源。血缘不等于外键，也不自动给出 Join 等值条件 |
| 治理与保护 | 表字段治理状态、质量问题处理结果、已确认的分类/标签、敏感保护和字段可信度 | 标明禁用、废弃、敏感和待确认范围；未审核的自动标签或质量猜测不得写成确定业务语义 |
| 已审核业务知识 | 已审核术语/同义词、指标口径、人工确认的业务规则和已发布知识版本 | 只为有来源的业务解释、指标和场景提供补充；没有已确认口径就不生成公式 |

关系与血缘必须重新核对两端实体是否仍存在于本次快照、治理状态是否允许使用、关系方向和列映射是否完整；跨数据源或来自旧快照且无法映射的边不进入本轮事实输入。实体关系图目前会随快照发布异步同步；现有同步过程还会清理该数据源的旧实体与关系，因此 ETL/人工血缘不能假定在新快照发布后仍完整存在。实施时要让已确认的血缘有可追溯的持久来源并能重新绑定到本轮快照，再作为生成输入；图尚未同步或血缘未恢复时不能靠模型补出缺失关系。结构字段可先完整生成，关系和血缘缺证据时写“暂无已确认关系”，交由治理人员补充。进入 RAG 的关系/血缘 chunk 还要绑定全部相关表字段，并按当前用户权限过滤。

生成模板要把 **Join Path** 与 **数据血缘/字段派生** 分成不同章节。Join Path 写可执行的关联字段和条件；血缘写上游 → 下游、列映射和已确认的转换说明。只有血缘、没有外键或已审核关联条件时，文档可以说明来源关系，但不能据此编出 JOIN SQL。每段关系文字保留来源边 ID、来源快照和确认状态，供审核与检索时核对。

## 4. 快照、知识文档和向量库如何维护

知识链的权威顺序是：**采集快照 → 治理与审核 → 发布快照 → AI 生成文档草稿 → 人工审核/修订 → 有权用户确认发布或重建 → 系统完成切分、Embedding、向量写入与验证 → 激活新知识版本**。初次建库和之后的重建遵循同一原则。技术处理可在用户确认后由后台任务自动完成；决定何时审核、发布或重建始终由人作出。

问数任务分别记录**当前 S1 校验使用的已发布快照**和**现行 RAG 的来源快照**，以及已发布 skills.md 文档版本、当前生效 RAG 的 Embedding 配置和构建标识 buildId。查询问题生成向量时必须使用该 buildId 构建时的 Embedding 配置，不因管理员保存了新的目标模型就提前切换查询模型。构建新 RAG 时按人工确认的文档形成新索引；检索只使用当前生效的 buildId，不把已退出的旧 buildId 的 chunk、邻块或向量混进结果。现行 RAG 的来源快照可以暂时落后于 S1 快照，旧知识只供规划参考，最终 SQL 必须按当前快照与实时数据库重新校验。buildId 只标识一次知识库构建，**不是另一个数据源版本号**。

| 发生的变化 | 系统应做什么 | 人需要做什么 |
| --- | --- | --- |
| 数据源 Schema 或治理事实变化 | 采集并比较实际差异，提示当前 RAG 所用快照版本与最新采集/发布快照版本的差距；不自动生成或构建新知识 | 查看差异、完成治理和审核；按需要修订 skills.md 类文档并确认重建 |
| 文档内容变化 | 保存草稿/审核状态，提示活动向量仍对应旧发布内容，不自动重新 Embedding | 审核并确认发布/重建 |
| 目标 Embedding 配置与当前生效 RAG 的配置不同 | 标记因 Embedding 变化待重建，显示当前模型与目标模型；查询继续使用当前 RAG 构建时的模型 | 有权用户确认后才用目标配置重建并切换 |
| 目标 Embedding 配置在新 RAG 生效前改回当前生效配置 | 清除仅由这次 Embedding 变更产生的待重建状态；未完成的其他目标构建不得激活 | 无需为了这次来回修改重建；其他快照或文档变化仍按各自状态处理 |
| 仅重新采集但实际问数事实未变 | 记录采集结果和差异判断，不因快照号递增就重建 | 无需仅为版本号变化点击重建 |

**新 RAG 生效后，删除的是 Milvus 向量库里旧 buildId 对应的 chunk/向量记录。** 顺序是：在隔离位置构建新 chunk/向量 → 核验数量、来源快照和 Embedding 配置 → 切换检索到新 buildId，使旧 chunk 立即不可检索 → 等引用旧 buildId 的在途任务结束或超过 deadline → 从 Milvus 物理删除旧 chunk/向量 → 核对旧 buildId 的向量数量为零。清理失败时记录 CLEANUP_PENDING 并重试，不能让旧 chunk 重新进入检索。不能先删旧向量再开始构建；新构建失败时保留旧索引并提示状态。**不删除 MySQL 中的元数据快照、skills.md 原文、文档版本及审核记录。** 若最新快照与旧知识不符，页面提示版本落后；实际问数仍受当前 S1 权限、元数据和 SQL 安全校验约束，不因版本号较低就自动执行危险查询。失败的重建任务不会自行发起下一次重建。

这套维护只针对受影响的数据源，不要求用户每提一问都重建，也不因为普通查询、会话追问或 SQL 生成模型变化而重建全库。具体 collection 布局、逐源切换和清理容量在实施批次中按实际规模验证，不把某种 Milvus 物理布局当作产品需求。

例如当前索引用模型 A 构建：目标改为 B 时提示待重建，问数仍用 A；如果 B 尚未生效，目标又改回 A，就恢复为正常状态，不创建或激活 B 索引。若 B 已经重建并成为当前索引，旧 A 向量也已按规则删除，此时再改回 A 需要重新构建。判断依据是目标配置与**当前生效索引的向量空间指纹**是否一致，不是配置曾经被修改过几次；仅轮换 API Key 且向量空间未变，不触发重建。

## 5. 数据源快照版本与知识库提示

数据源版本只指现有的**元数据快照版本**：同一 datasourceId 下的 metadata_snapshot.snapshot_version、snapshotId、schemaHash、采集时间、治理/发布状态和差异。数据源连接配置、业务数据行、skills.md 文档版本和 Embedding 模型不另算进“数据源版本”，也不新增一个独立的可问数发布版本号。skills.md 和 RAG 构建各自记录其来源 snapshotId，方便与数据源快照比较。

管理界面至少显示三个数字：该数据源**最新采集快照版本**、**当前发布快照版本**、**当前 RAG 所依据的快照版本**。如果最新采集或发布版本高于 RAG 所用版本，界面提示“知识库基于快照 vN，数据源最新快照为 vM”，并提供快照差异入口。采集产生更高版本但实际结构/治理事实没有变化时，应标明“版本号更新、问数知识无实际差异”，不误报为必须重建。版本差异本身只触发提示，不能自动审核 skills.md 或自动重建向量。

人员根据快照差异完成治理、修订和审核 skills.md，再决定是否手动确认重建。重建成功后，RAG 的来源 snapshotId 更新为所确认的快照；旧 Milvus chunk/向量按第 4 节清理，历史快照、文档原文和审核记录仍可查看。Embedding 模型变化也可能触发人工重建，但它不会凭空增加数据源的 snapshot_version。

每次问数记录 datasourceId、当前 S1 已发布 snapshotId、RAG 来源 snapshotId、RAG buildId 和权限修订，用于排查结果与版本提示。**RAG 来源快照落后只给提示，不阻断问数。** 系统仍从现行 RAG 索引检索旧快照知识作为候选，再用当前已发布快照和 S1 权限验证表字段与 SQL，最后到实时数据库执行。旧知识中的字段若已删除、禁用或失去授权，就不能用于最终 SQL；在规定重试内找不到可用方案时说明知识可能过时并请用户处理，不把一次执行失败当作全数据源不可问数。

## 6. 历史对话与多轮记忆

**MySQL 是完整历史的事实源。** Java 保存会话、用户和助手消息、任务、受保护的结果引用及滚动摘要。首期“完整历史”指自会话最后一条消息起在线保留 365 天内，用户能按稳定消息 ID 分页读完仍有权查看的全部原始消息；摘要不能替代或删除原始消息。历史结果读取时重新核对当前权限和保护规则，无法证明仍可展示的旧结果用受限占位说明，不让一条旧结果使整页历史失败。

**首期在线保留期已确认：最后一条消息后 365 天。** 用户主动删除后立即停止展示。原稿提出的“7 天内物理清除在线副本、备份在 30 天轮换期内到期”仍是待部署前确认的清理建议，不视为本次对 365 天在线保留期的确认范围。执行任务的清理不能提前删除历史展示仍需的唯一证据。

**Redis 是本方案中 LangGraph 的短期记忆与 checkpoint。** 同一用户、数据源、会话使用稳定 thread_id；不同会话和不同数据源绝不共用。图内 state 在一次运行的节点间传递；checkpoint 使下一轮能取得当前会话的短期上下文，并使可恢复的中断节点有持久状态。每轮开始清理上一轮的 SQL、候选和错误状态，不能把旧查询当作本轮已授权事实。连接密码、JWT、原始行条件值和未脱敏结果不得写入 checkpoint。

**首期固定为最近 5 轮原文加更早摘要，只在当前这个会话内部计算。** 对本会话的新问题，模型收到本会话最近 5 轮已完成的“用户问题＋助手回复”原文、本会话更早轮次的滚动摘要，以及当前问题一次；其他会话的消息或摘要，即使属于同一用户、同一数据源，也不能混入。这里的 5 轮是随对话前进的窗口，不是只保留会话最开始的 5 轮，更不是只把 5 轮消息存入数据库。例如同一会话第 11 次提问时，模型收到第 1～5 轮的整理摘要、第 6～10 轮原文和第 11 个问题；页面仍可查看第 1～10 轮的完整历史。

每个会话有独立的摘要及其 coveredMessageId，记录已整理到哪一条消息。已进入摘要的轮次不再重复放入最近 5 轮原文；刚滑出窗口、尚未完成整理的消息不能静默丢弃，应先做有界、可追溯的临时整理并重试摘要生成。旧回答和摘要进入下一轮模型前须复查当前权限；用户纠正过的旧结论不能继续作为可信事实。Redis 过期或丢失后，从 Java/MySQL 重建**该会话下一轮**记忆；正在执行的任务若无法证明安全续跑，就明确失败或由用户重试。

Redis 不是保存聊天历史的唯一位置，也不是实现多轮语义的理论前提；它是**本方案选定的 LangGraph checkpoint 存储**。当前 S1 没有 Redis checkpointer，仓库也没有对应 saver 依赖。原稿对本工作区配置所连 Redis 的只读检查显示版本为 7.4.11、未加载 RedisJSON/RediSearch；若采用官方 Redis saver，实施前必须验证所需模块、setup、持久化和重启读回，必要时使用独立兼容实例。该检查不代表其他环境。

## 7. 系统分工与安全底线

- **前端**只调用 Java。问数页呈现“数据源 → 会话”、自然语言输入、真实进度、澄清问题、ECharts 图表、必要的说明与受保护数据表；不要求用户预选表字段。
- **Java**管理登录和 IAM-SIMPLE-1 权限、数据源及治理生命周期、知识文档审核发布、会话与任务状态、历史持久化、精确授权、最终脱敏和审计。用户请求、图的阶段交接和浏览器重连都以 Java 的持久任务状态为准。
- **Python**负责 LangGraph 编排、问题改写、权限范围内的 RAG、Schema Linking、SQL 生成、S1 AST 校验、只读沙箱执行和 ECharts 图表配置生成。图只能使用 Java 提供或确认的授权范围；候选资源在执行前由 Java S1 Resolver 再次精确复核。

未授权的元数据、知识文本和原始查询结果不能先发给模型再指望最终脱敏补救。图表或回答模型只能看到 Java 已确认可公开的安全结果。非法 SQL、越权、权限撤销、取消、超时和危险函数不能被当作“可修正错误”交给模型绕过。可修正的语法或口径问题每次重试都重新校验，并受统一 deadline、尝试次数和成本预算约束。

旧的 Python agent/ 包在 B6 已删除，且使用过时的权限契约；本方案以当前 IAM-SIMPLE-1 问数链为基础新增图，不整体回退旧 Agent。

## 10. 本方案的边界与待定细节

1. **产品目标已确定：**非技术用户自然语言提问；LangGraph 在规定重试内检索和修正 SQL，得到符合问题的安全数据后结束；S1 安全校验；以 ECharts 图表展示并附必要说明/数据表；MySQL 历史、Redis checkpoint；按治理快照生成并由人维护的 skills.md 类 RAG 知识。
2. **会话隔离已确定：**支持多个已接入数据源，但每个会话只绑定一个数据源，同库可多表 Join。历史消息与短期记忆都以用户、数据源和会话隔离。
3. **知识操作权已确定：**系统可发现变化、显示影响和提醒；草稿审核、发布与重建由有权人员决定。用户确认一次构建后，切分/Embedding/验证等技术步骤由任务执行。
4. **数据源版本与旧向量范围已确定：**数据源版本只用现有元数据快照；界面提示当前 RAG 来源快照低于最新采集/发布快照。新 RAG 生效后只删除 Milvus 中旧 buildId 的 chunk/向量，MySQL 快照、skills.md 原文和审核记录保留。
5. **实施时需冻结：**各节点输入输出协议、Redis saver 与部署；G0 在 D 批次前冻结回环次数、总 deadline、费用与正确率门槛。最近 5 轮是首期固定产品要求，调整须单独确认，且不得丢掉完整历史；完整历史自最后一条消息起在线保留 365 天。删除清理与备份轮换细节在部署前确认。
6. **不把模型判断当作安全证明：**SQL 与问题是否相符需要结构化证据核对，是否可执行由 S1 校验决定。知识不足或用户问题含糊时必须允许澄清和拒答。
