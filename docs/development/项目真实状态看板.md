## ⚠️ 当前最高优先级阻塞项：没有可运行环境

仓库内**不存在任何 `docker-compose.yml`**（已确认全仓检索无结果），但 `README.md` 的「快速启动」和 `CLAUDE.md` 的「Development Commands」都让人执行：

```bash
docker compose up -d
```

这带来两个后果：

1. **所有依赖 MySQL / Redis / Milvus 的运行时验证都无法执行** —— 包括后台前端重构 §16 的四组验收场景、Agent 全链路、RAG 真实 Milvus 验证。这是后续每一步的共同前置。
2. **新克隆仓库的人第一步就会卡住** —— 对「开源项目」目标（见 `后续开发.md` 的执行口径）是硬伤。

`后续开发.md` 的「待清理项」曾记录此项并判定「P8 已取消，暂不规划，本地按需自行启动服务即可」。该判定在「只需要写代码」的阶段成立，但在需要验收的阶段不再成立，**建议改为优先补齐**。注意 Milvus Standalone 还需要 etcd 与 MinIO 两个伴生服务。

**离线可用性（2026-09-12 实测）**：

- **Java 测试不需要任何外部服务** —— 测试栈以 Mockito 单测为主，另有 H2 + `src/test/resources/application-test.yml` + `schema.sql` 支撑唯一一个 `@SpringBootTest`。因此在没有 MySQL / Redis / Milvus 的情况下，后端缺陷的修复可以**先写代码并跑单测**，把运行时验证留到环境恢复后一次性做。
- **前端构建不需要任何外部服务**，但**不覆盖任何行为**：项目装了 `vitest` 而零测试用例。
- 依赖真实服务的验证全部被阻塞（见文首）。

> 前端构建通过**不构成行为验证**：项目装了 `vitest` 但**零测试用例**，`npm run build` 只做类型检查与打包，不覆盖任何运行时行为。
>
> 测试运行时禁止向 LangSmith 发送追踪数据，以保证本地 `.env` 中的开发配置不会影响测试结果。

## 当前开发顺序

顺序的判据不是「哪块更想先做」，而是**哪块阻塞其他块**。后台前端重构的信息架构是权限体系设计的硬前置（`开发指导` §17 完成定义第 10 条、§18 禁止事项），所以前端必须先冻结。

### 第 0 步：恢复可运行环境（阻塞项，不解决则后面都无法验证）

补 `docker-compose.yml`（MySQL 8 + Redis + Milvus Standalone + etcd + MinIO），并同步修正 README / CLAUDE.md 的启动说明。

### 第 1 步：验证已交付的修复（环境恢复后立刻做）

2026-09-12 完成的两轮修复**都只有静态验证 + 单元测试**，没有任何运行时验证：

1. **V51 迁移**（`knowledge_doc_version.review_status` 回填）**从未在真实 MySQL 上执行过**。首次启动时必须观察迁移是否成功、回填结果是否符合预期（能还原的行按审核任务还原，其余为 `UNKNOWN`）。
2. **前端缺陷 F1–F9 的 9 项**需按验收清单人工点验（尤其 F1 的 8 种 readiness 状态、F6 的跨工作区 URL 继承、F2 需构造 `ISSUE_FOUND` 快照）。
3. **后端新接口**需接口级验证：`GET /knowledge-docs/{id}/review-tasks`、`GET /knowledge-docs/{id}/vector-tasks`、`PATCH /prompt-templates/{code}/enabled`、`POST /glossary/terms/{id}/revert`。
4. **P0 回滚校验**建议补一次接口级验证，确认对 `DRAFT` 文档回滚会被拒绝（原漏洞路径）。

清单见 `docs/review/2026-09-11-后台前端重构审查-前端缺陷清单.md` §7.1 与同目录后端文档 §9。

### 第 2 步：后台前端阶段 6–8

1. **阶段 6 重构** —— 按 `开发指导` §7.13 / §7.14 / §7.15 重做授权管理（数据源授权 / 表列策略 / 最终权限预览三 Tab，主体驱动流程）、访问审批、组织与角色。当前这三个工作区指向的是重构前的实现，**不是**在已有页面上补缺口。
2. **阶段 7 重构** —— 按 §7.16 / §7.17 / §7.18 重做查询分析、数据血缘、运行监控、操作日志、AI 配置。
3. **阶段 1–5 的真实验收** —— 按 §16 四组场景（数据源上线、上下文隔离、生命周期、异常体验）逐项点验。这是当前最大的空白：阶段 1–5 的「完成」只有静态阅读依据，从未运行时验证。
4. **阶段 8 收敛** —— 删除被阶段 1–5 取代的旧视图、合并重复 API 封装、梳理硬编码颜色、把资产目录与术语关联字段从客户端过滤切到 `/search?datasourceId=`（后端已支持，见 §12.1）。

### 第 3 步：权限体系重构

**从现有设计文档出发，不要从零写** —— `开发指导` §19 把《DataOcean 完整权限体系设计》定位为「后续权限重构输入」，它已写明目标：`RBAC + Data Permission + Row Policy + Mask Policy + Permission-aware RAG`。该项工作应**先更新那份文档**，再实施。

三条必须注意：

1. **前后端必须成对改。** 前端当前按 `开发指导` §13 硬编码了「真实 `*` 超级管理员」假设，且 `guards.ts` 中故意不实现 `meta.permission`（2026-09-12 清理死代码时已留注释说明原因）。新模型落地时前端需要专门做一次「消费权限」的改造：把该分支重新加上，并在 7 个业务域、各二级工作区、各 Tab 和写操作上接入权限点。这不是顺手能带的改动，应单独立项。
2. **必须先冻结信息架构。** 新模型要定义菜单权限、页面权限、Tab 权限、操作权限、数据范围，而这五类的划分依据就是业务域 / 工作区 / Tab 的最终形态。
3. **归属权限语义的既有缺口一并处理**：审批列表未按申请人收窄、无方法级权限限制（`开发指导` §3.12），以及 §3.11 的最终权限预览决策端点、§3.13 的权限项。现在单独修会在新模型中返工。
4. **验收必须用真实账号。** `开发指导` §13 要求本轮用真实 `*` 账号完成访问，前端不得写死或伪造 `*`；后端现有 `@PreAuthorize`、数据范围、安全规则和状态机全部保留。

### 第 4 步：原有功能待办（按需）

P9 告警触发执行 → P12 告警规则与历史前端页面 → P13 问题中心责任人筛选（3 文件 1 行，DB 索引已就绪）→ P3 PostgreSQL / Agent workflow 集成测试 → P4 血缘图数据库。详见 `docs/development/后续开发.md`。

## 已知工程风险

1. **无 `docker-compose.yml`**，运行时验证不可执行（见文首）。
2. **`V51` 迁移从未在真实 MySQL 上执行过**，`UPDATE` 语句与 `MODIFY COLUMN` 均未经实机验证。首次迁移前建议先备份 `knowledge_doc_version` 表。
3. 前端没有 Vitest 用例；新增或改动关键查询页面时应优先补测试。2026-09-12 的前端改动（含 9 项缺陷修复与新接口接入）**全部只有静态验证**。
4. 前端构建有大包告警；将 ECharts 和血缘可视化按路由拆包。
5. 阶段 1–5 的所有「完成」都只有静态阅读依据，**没有任何一次运行时验收记录**，其中可能仍藏有与 F1–F9 同类的问题。
6. Python 测试报告 Redis 客户端 `retry_on_timeout` 的弃用警告。
