# DataOcean 完整权限体系设计

> 文档版本：简明版 1.4，2026-09-16；新执行协议为 IAM-SIMPLE-1。
>
> 状态：设计基线已通过 B0 评审；B1 尚未开始。本次只修改文档，未实施代码、数据库升级或权限删除。
>
> 替换顺序：先建立并验收新权限，再切换到新体系；确认新体系正常后删除旧权限。旧配置不映射、不回填，新请求不混用两套算法。
>
> 技术隔离：旧角色、旧权限关系、旧数据策略、旧 JWT 权限声明和旧缓存均不得成为 IAM-SIMPLE-1 的授权输入；即使权限码字符串同名，也不继承旧授权。

## 0. 目标与边界

权限管理应让管理员一上手就能回答：这个人能做什么、能查什么数据、为什么有这项权限。

第一期采用简单的用户/角色/部门管理，保持 DataOcean 的问数、治理和安全架构，不建设通用大型 IAM 平台。

**管理员日常只需要完成两类配置：给人选角色，给部门或人选可查数据。** 给后台人员选角色时，再选其负责的数据源。记录条件、有效期和禁止规则按需展开，普通授权不要求配置这些选项。

例如新增销售员工：选择“销售部”和“普通问数用户”，保存前看到“可对销售部已授权数据提问；不能查看 SQL 或导出结果”。部门尚未授权时明确显示“可以使用问数，但暂无可查数据”，并提供去配置部门数据的入口，不能显示成已可查询。

“简单”按实际操作验收，不只看名称：首次给员工开通常规问数不必阅读本设计、不必认识权限码、不必到多张策略表重复配置；看到每个选项就能知道勾选后增加哪些能力。

业务依据为当前仓库的账号/组织模块、七个后台业务域和二十个正式工作区（含工作台），以及 Java 管理/持久化、Python AI/RAG/SQL 执行的分工。技术名和权限码放在开发部分，管理员配置时以中文业务名称、简短说明和例子为主。

这次重设计不清空账号、密码、真实部门、业务数据源、元数据、知识文档、会话或业务审计。旧权限在新体系通过验收前保持原运行状态，不提前删除。

## 1. 三个主体分别管什么

| 对象 | 管什么 | 管理员的操作 |
|---|---|---|
| 用户 | 谁使用系统，属于哪个主部门，有哪些角色 | 选部门、分配角色；必要时设置个人特殊数据范围 |
| 角色 | 能使用哪些功能、执行哪些操作 | 按中文功能清单勾选“查看、维护、审核、发布、导出”等 |
| 部门 | 组织结构、部门成员默认能查询的数据 | 给部门选择数据源、表、字段和记录范围 |

一个用户有一个主部门和多个角色。部门不自动授予功能，角色名称不自动授予数据。

推荐分配方法：新员工选择“销售部 + 普通问数用户”，就获得普通问数功能和销售部已配置的默认数据，不再逐个重复配置。

跨部门查询可给业务角色配置数据范围；个人差异可以配置个人数据权限。用户不直接配置普通功能权限，避免每个人变成一份难以维护的功能组合。

## 2. 管理界面必须讲清楚的三件事

### 2.1 功能权限

例如“使用问数”管进入问数页面、提问和本人历史；“导出结果”管产品提供的导出操作。

功能权限在角色里配置一次，不在数据源授权表里重复勾“允许看 SQL、允许导出”。SQL 查看和导出仍只能操作当前用户有权查询的结果。

### 2.2 后台工作范围

后台角色分配时，选择“负责后台工作的数据源”。它限制这个角色能在哪些源查看/维护后台业务，不授予业务数据查询权限。

同一人可以“在销售库处理治理问题，在人事库只看查询审计”。后端必须按同一个角色的功能和负责范围匹配，不能把两个角色的功能/范围分别取并集后相乘。

系统管理员由服务端识别，负责全部后台功能；业务数据仍须明确授权。

### 2.3 业务数据权限

数据授权只回答“可以查询哪些数据”：选择数据源、表、字段、记录范围和有效期。

“业务分析人员”角色有导出功能，但没有数据授权时不能查或导出任何数据。“数据管理员”负责某个源，仍不能因此读取该源业务原值。

## 3. 权限名称与说明规范

### 3.1 每项必须有中文名称和具体作用

名称采用“动作 + 对象”，不用笼统的“高级权限、资源权限、管理权限”，也不让用户理解 DISCOVER、GRANT、UNMASK 等术语才能配置。

下面的说明覆盖第 4 节全部功能点，必须用于角色配置和只读功能说明目录，不能只给少数示例。每个可勾选项旁直接显示作用，不要求先悬停或打开帮助；需要解释的边界放在展开详情中。

| 使用问数 | 对已授权数据提问，查看本人历史，反馈或取消本人任务 |

| 导出结果 | 导出本人当前仍有权查看的结果，脱敏字段保持脱敏 |

字段中文名取自已审核元数据，缺少业务名称时显示物理名，不根据字段名猜业务含义。一个功能如果无法写出具体作用，先检查是否有必要存在，不用“管理某模块”敷衍解释。

### 3.2 查看与维护的包含关系

- 勾“维护”自动包含对应“查看”，保存时后端同样展开，不能仅靠前端。
- 勾“审核”或“发布”自动包含必要的查看，不自动包含维护。
- 发布不自动包含审核，审核不自动包含发布；这保留真实生命周期职责。
- 查看 SQL、导出结果自动包含使用问数，不单独再配置“历史查看”。
- 界面标注“已随维护权限包含”，避免用户取消依赖后得到不可访问页面。

### 3.3 展示方式

先显示常用角色模板及其中文用途。选模板后直接显示“已获得的能力”，例如“可以问数、查看 SQL、导出结果”，再提供“自定义功能”展开入口，不让首次使用者面对完整权限树。

自定义功能按业务域/工作区分组，每行一个明确业务对象，列为“查看、维护、审核、发布、导出”，没有的操作显示不适用，不创造无实际消费的功能点。勾选项显示第 3.1 节的具体作用；已随依赖包含的查看权限明确标注。技术上的独立功能点保留后端校验，管理员无需逐项重复选择。

角色页面首屏显示中文名称和作用；技术码只在开发/排查详情折叠展示，默认不拼在每个名称后面。支持搜索中文名、选择角色模板和查看已选摘要。

## 5. 用户和角色管理

### 5.1 用户

账号只有启用/禁用；禁用后新请求拒绝、会话失效。没有角色只能登录/维护本人资料，不能进入业务工作区。

用户详情显示：基本资料、主部门、角色及负责范围、特殊数据授权、实际权限。新增用户先选部门和角色；有部门默认数据时不重复建个人授权。

用户可有多个角色。角色功能合并后展示中文摘要，例如“可以问数、查看 SQL、导出结果；在销售库可维护治理，在人事库只看审计”。

### 5.2 角色

角色定义只维护名称、说明、状态和功能组合。跨部门业务数据在授权配置中以角色为主体设置，角色详情只展示有权管理范围内的数据摘要和跳转入口，不再维护副本。

普通角色管理员可以按固定目录配置非系统管理功能，不要求自己先拥有所有业务功能。包含组织、数据授权、审批、字段保护或平台配置管理功能的角色，仅系统管理员可配置/分配；界面明确锁定原因，不建设多层权限委派。

系统管理员是唯一受保护内置角色，由服务端固定识别；不能靠改角色名字、传标记或复制模板获得身份。它拥有全部后台功能与工作范围，但业务问数仍需数据授权，任务结果仍校验本人归属。

### 5.3 防止本人修改权限

- 用户和管理员都不能自行改变自己的角色、负责范围、主部门。
- 角色管理员不能修改/禁用/删除自己持有的角色定义；由另一位有权限管理员处理。
- 数据管理员不能编辑本人、本人所属角色/生效部门的数据授权或禁止规则。
- 调部门树若改变操作者自身组织路径，由另一位管理员执行。
- 退出角色、禁用角色或删除禁止规则，可能使原来的禁止失效，保存前须说明实际影响。
- 禁止移除最后一个启用系统管理员。

角色/部门禁用前提示：允许与禁止规则都将不再生效，部分用户的数据范围可能变大；预览来源变化，不声称能证明任意条件的语义包含。

## 6. 部门默认数据

用户首版仅一个主部门，不做多主部门/矩阵组织，部门不绑定功能角色。

每条部门数据权限必须选择中文范围：

| 显示选项 | 含义 |
|---|---|
| 仅本部门 | 仅该部门当前启用成员 |
| 包含下级部门 | 该部门及当前启用后代部门成员 |

父部门授权只有选择“包含下级部门”才能继承。禁用路径不继续继承，循环/损坏路径无法安全计算时拒绝并告警。

部门有成员/启用子部门时不能直接删除。用户调部门不复制原部门授权，下一次请求实时按新主部门计算；有效的个人特殊授权保持独立，管理界面提醒检查是否仍需要。

## 7. 后台工作范围：按角色匹配，不等于问数授权

用户分配后台角色时，可选择它负责的数据源；全局角色不需要选择数据源。系统管理员负责全部后台源，普通角色没有选择源时不能进入相应数据源工作区。

判定某次后台操作时：至少存在一个启用角色，既拥有该操作功能，也在该角色负责的源范围内。

例如角色 A 在销售库可维护治理，角色 B 在人事库只看审计，不能把维护治理权限与人事库范围合在一起。查询端功能与业务数据来源独立，不能套用这条后台职责规则代替部门数据授权。

后台负责范围允许查看结构、治理状态、草稿/阻断/废弃对象并执行获准管理任务；不要求先发布、健康或可问数。业务采样原值、查询记录值和连接密码不因后台角色开放。

创建数据源时，由系统在创建事务中给实际具备创建功能的角色绑定增加这个新源的负责范围；不授予业务查询。这只是新对象管理起点，不是改本人已有源范围的接口。

## 8. 数据授权：一次说明“谁能查哪些数据”

授权配置统一为一份表单，不再先给“数据源查询权”、再到另一张策略表猜测补充关系。

| 配置项 | 管理员看到什么 | 默认与限制 |
|---|---|---|
| 授权给谁 | 用户、角色、部门及中文名称 | 必选；部门另选“仅本部门/包含下级部门” |
| 哪个数据源 | 数据源业务名称 | 必选；仅可操作自己负责的源 |
| 哪些表和字段 | 已发布且允许查询的表、字段 | 必须明确选择；字段未选不代表全部 |
| 哪些记录 | 全部记录，或“字段 + 条件 + 值” | 默认全部记录；设置条件时显示中文摘要 |
| 有效期 | 长期有效，或开始/结束时间 | 默认立即、长期；结束时间必须晚于开始时间 |
| 允许或禁止 | 默认“允许查询”；“禁止查询”在限制区域配置 | 禁止优先，不设数字优先级 |

表单初次打开只展示“授权给谁、哪个数据源、哪些表和字段”；默认查询所选资源的全部记录并长期有效。需要限制记录或时间时展开“限制记录/有效期”，禁止规则有单独的“禁止查询”入口。保存前始终显示完整中文摘要，让默认值可见。

例如：“允许销售部及下级部门查询销售库的订单表，只看订单号、日期和金额，限区域为华东的记录，长期有效”。部门范围决定哪些成员命中授权；记录范围决定命中成员能看哪些业务记录，两者分别解释。

“本部门记录”只有在管理员已经确认业务字段与系统部门的对应关系后才能提供，不根据 `dept_id` 等字段名自动猜。第一期条件只支持当前表的已审核字段、比较/集合/空值操作和明确的“全部满足/任一满足”；值按字段类型校验，不开放手写 SQL、任意函数或跨表子查询。

“选择当前全部表/字段”保存为当前资源清单。以后新增表或字段不自动加入授权；界面提示“新增资源需重新授权”。禁止规则仅支持整个数据源、表或字段，不支持按记录设置禁止例外，避免增加一套难解释的优先级。表级禁止包含该表的全部字段，字段级禁止只影响相应字段。

维护授权配置的人可以给其他主体配置负责源内符合准入要求的数据范围，无须自己先获得这些业务数据；这项能力由系统管理员明确授予。它不能改变字段保护、授予原值例外或绕过第 5.3 节本人修改限制。

## 9. 多份权限如何合并

管理员只需要理解三条规则：**没有允许就不能查；多份允许可以增加范围；任何禁止都会扣掉对应范围。**

1. 只计算启用用户、启用角色、有效部门路径、当前生效且未撤销的规则。
2. 每份允许授权保留自己的“表、字段、记录条件”组合，不把字段和记录条件分别合并后相乘。
3. 对同一表的一次查询，找出同时覆盖全部引用字段的允许授权，记录范围为这些授权条件的“任一满足”；找不到完整覆盖时拒绝并提示调整授权。
4. 扣掉所有命中的数据源/表/字段禁止，再叠加字段保护和治理准入限制。个人授权与临时审批同样不能覆盖禁止。

例子：部门允许看“华东订单”，个人另获“华南订单”的相同字段授权，可以查华东或华南；个人有“金额、华东”权限、部门有“客户姓名、华南”权限，不能组合成“金额和姓名、两个区域都能看”。第一期如需联合查询这两个字段，须增加一份同时覆盖两者的明确授权。

SQL 中的投影、条件、关联、排序、分组、子查询均计入字段引用；多表查询逐表计算记录范围，在实际读取每张表的位置注入条件。允许字段为空、授权资源不存在、部门路径损坏或协议缺失时均拒绝，不解释成全库开放。

功能依赖在角色保存时展开；多个角色的问数功能可以合并。后台操作始终按第 7 节同一角色的功能和负责范围匹配。统一预览与真实查询使用同一计算服务，不做另一套“看起来差不多”的算法。

## 10. 字段保护：允许查询不等于允许看原值

字段保护单独维护，针对数据源中的字段生效，不在每个用户授权里复制手机号掩码等配置。

| 显示名称 | 查询结果中的行为 |
|---|---|
| 正常显示 | 按已授予的字段和记录范围显示 |
| 隐藏字段 | 不进入问数 Schema/RAG，也不能在 SQL 任意位置引用 |
| 脱敏显示 | 允许安全的直接字段展示，返回手机号掩码等保护值 |

敏感分类与保护策略发生冲突时采用更严格的状态。多个掩码无法确认安全包含关系时隐藏字段并提示管理员修正，不使用策略排序选择较弱保护。维护字段保护包含确认敏感状态与收紧策略；解除敏感标记或放宽现有保护仅由系统管理员执行，保存时说明影响并记录理由与审计，不新增一套字段保护审批流程。

第一期不做“查看原值”开关或原值审批。脱敏字段不允许用于筛选、关联、排序、分组或函数运算；否则即使结果打码，仍可能推断原值。需要统计时使用经审核且不会暴露敏感原值的独立指标/字段，不临时绕过限制。

Python 校验所有表达式并追踪结果别名与来源，Java 对整份响应执行最终保护。表格、图表、解释、采样值、SQL 展示、错误、审计详情和导出均受约束；禁止敏感业务原值进入模型上下文，来源无法可靠判断时拒绝返回该结果。

## 11. 访问申请与审批

普通用户在问数入口可查看“我的申请”，选择可申请的数据源、表、字段、记录范围、时长和用途。此入口只展示申请所需的安全名称与说明，不开放后台目录、采样数据或其他用户权限。

| 操作 | 谁能做 | 结果 |
|---|---|---|
| 发起/撤回申请、查看本人申请 | 有“使用问数”的用户 | 待审批申请不授予查询权 |
| 查看负责源申请 | 有“查看访问申请”且负责该源的角色 | 只能看到负责源队列 |
| 同意或拒绝 | 有“审批数据访问”且负责该源的角色 | 不能审批本人申请；通过后生成有期限的个人允许授权 |

同意前后端重新检查申请人状态、审批人职责、资源发布/治理状态、禁止规则和字段保护。通过范围必须是申请范围的子集，时间不超过申请时长，不顺手加 SQL/导出功能；审批人无需本人拥有该业务查询数据。

有效期从批准时间起算；禁止、隐藏、阻断、废弃和未发布资源不能审批开通。到期或撤销按请求计算立即失效，定时清理只负责清理记录，不能决定权限是否已经到期。

申请保存批准范围、生成的授权 ID、审批人、理由和时间，方便解释“为什么能查”。我的申请和管理员审批保持独立入口，不让业务用户进入后台权限工作区。

## 12. 用户实际权限预览

用户详情、部门详情和授权页都跳到同一个实际权限预览，不各维护一份权限副本。

选择“用户 + 数据源”后展示：

- 功能：能否问数、查看 SQL、导出，以及角色来源。
- 数据：可查询的表、字段、每份授权对应的记录范围和有效期。
- 限制：明确禁止、隐藏/脱敏、资源未发布/阻断等原因。
- 后台职责：哪个角色在此源负责哪些工作，与业务查询范围分开显示。

例如：“可问数；订单金额只看华东记录，来自销售部默认授权；手机号不可查询，来自字段保护；导出不可用，因为角色未勾选导出结果”。不能仅显示“最终 ALLOW”或一串角色 ID。

普通用户可看本人业务权限；管理员查看他人时须有“查看用户实际权限”并负责目标源。用于选择对象的用户/角色/部门接口仅返回必要名称，不为打开授权表单额外要求“查看全部用户”。预览不返回业务记录或权限参数原值。

## 13. 首期角色模板与页面调整

模板仅帮助勾选功能，创建后是普通角色，没有按名字识别的特权，也不附送数据授权。

| 模板 | 默认功能 | 数据如何获得 |
|---|---|---|
| 普通问数用户 | 使用问数 | 部门默认或明确授权 |
| 业务分析人员 | 使用问数、查看 SQL、导出结果 | 部门、角色或个人授权 |
| 数据治理人员 | 查看资产、执行检查、处理问题、维护规则与字段治理 | 系统管理员选择其负责源；问数另行授权 |
| 语义维护人员 | 查看资产、维护术语与知识 | 系统管理员选择其负责源；不默认审核/发布 |
| 审核发布人员 | 查看资产、审核/发布快照、审核术语与知识、发布知识 | 系统管理员选择其负责源；不默认维护内容 |

授权/审批、组织和平台配置等管理功能由系统管理员明确分配，不塞入普通业务模板。系统管理员保留为唯一受保护内置角色。

沿用既有七个业务域和两级侧栏：`/admin/access` 的 Tab 调整为“数据授权、字段保护、实际权限”，`/admin/access/approvals` 保持审批工作区；`/admin/access/organization` 保留“用户、角色、部门、功能说明”。

角色分配抽屉只问“选哪个角色、负责哪些数据源”，数据授权表单只问“谁、哪些数据、哪些记录、多久”。组织页把可编辑的“功能权限 CRUD”改为只读说明目录，角色编辑采用第 3 节中文矩阵。

首屏移除主体、策略优先级、MASK、scope 等技术表达；空状态说明下一步操作。例如：“还没有数据授权，请选择部门或用户并添加可查询的数据”，不再显示“未配置策略时默认按数据源开放”。

## 14. 开发契约与职责

本节是目标要求，尚未实现。新协议只使用 IAM-SIMPLE-1，具体字段与业务端点消费矩阵在 B0 固化到对应模块 spec/contract；不恢复旧码映射表。

### 14.1 IAM-SIMPLE-1 是唯一新权限事实源

新权限计算只能读取明确属于 IAM-SIMPLE-1 的功能目录、新角色关系、按角色绑定的负责源、新数据授权和字段保护。现有 `sys_user_role` / `sys_role_permission` / `sys_permission` 中的旧关系、旧数据源授权/策略、旧 Resolver/Calculator/DTO、旧别名表、旧 JWT authority 和旧权限缓存只能服务切换前的旧运行环境，不得被新 Resolver 查询、转换或兜底。

新权限事实必须采用独立新表，或使用所有读写都强制携带 `protocol_version = 'IAM-SIMPLE-1'` 的独立记录；B0 必须在两种方案中冻结一种。不允许只在无版本区分的旧表中“再插入一批新数据”，也不允许通过旧角色名、旧角色 ID、旧 `*` 权限或旧权限码猜测新授权。

目标功能目录中与现系统同名的代码（如 `datasource:manage`、`audit:view`、`knowledge:manage`、`prompt:manage`、`prompt:approve`、`system:ai-config:view`、`system:ai-config:manage`）只表示新目录的功能语义，不表示复用旧权限记录或旧角色关系。新请求若缺少新协议版本、新关系或必需资源清单，必须默认拒绝。

切换前可以保留旧环境对外服务，并在独立验收环境运行新体系；隔离边界必须是环境/入口级的，不得在同一请求中同时调用两套算法，也不得在 IAM-SIMPLE-1 拒绝时自动改用旧权限重试。

### 14.2 首个新系统管理员的显式初始化

保留旧账号不等于保留旧管理权。B5 切换前，部署负责人必须通过受控的一次性初始化流程，显式选定至少一个已保留、已启用的账号，将其绑定到 IAM-SIMPLE-1 的受保护系统管理员角色。不得因为该账号在旧系统中持有 `ADMIN`、`*`、固定角色 ID 或历史管理员名称而自动继承。

初始化必须幂等，记录操作人/部署来源、目标账号、新角色、时间和结果；成功后关闭一次性入口，不保留可长期绕过正常权限管理的后门。切换验收必须证明该管理员能登录、查看新功能目录、创建新角色、分配负责源和配置数据授权；未建立或未验证新系统管理员时不得切换。

### 14.3 分层职责与请求契约

| 层 | 必须承担的工作 |
|---|---|
| Java | 固定功能目录和依赖、角色绑定与负责源、部门路径、数据授权、字段保护、审批、统一计算/预览、失效与审计、结果最终保护 |
| Python | 消费请求级快照，权限感知检索、SQL AST 全字段校验、逐表注入参数化记录条件、来源追踪、只读执行 |
| Vue | 中文功能矩阵、授权表单、原因预览、路由/Tab/按钮可见性、SQL/导出安全交互；所有接口仍由 Java 强制校验 |

新存储需要区分角色定义、用户角色绑定的负责源、明确资源的数据授权及记录条件、部门继承选项、字段保护、申请批准关联和权限修订版本。只能复用账号、真实部门、数据源、元数据等非权限基础实体的标识；不得复用旧角色成员关系、旧角色权限关系、旧数据授权或旧策略记录作为新授权。新权限配置另行初始化，数据库不创建外键，关系由服务层校验。

每次查询快照至少包含协议版本、用户、数据源、活动元数据快照、权限修订版本、计算时间/下次生效边界、非空且明确的表列资源清单、逐表且保留授权关联的记录条件、字段保护和结果能力。旧协议缺少列白名单、默认开放或只传平铺字符串条件的行为不能直接沿用。

记录条件使用结构化、带类型的表达式与参数；参数由服务端解析，不接受前端传入“当前用户/部门”身份值。参数与模型看到的 Schema/问题上下文分离，Python 以 AST 和绑定参数执行，不让模型生成权限条件。

RAG 文档/chunk 必须绑定可验证且完整的表列来源；检索只允许引用当前用户获准且符合治理准入的资源。涉及记录限制的业务值、采样值不进入模型；缺少资源绑定的旧 chunk 不自动视作安全，也不因此删除活动向量，修复须保持既有写入并验证新版本后清理旧版本的生命周期。

权限变化在提交事务后使 Redis 缓存和会话中的旧权限失效；Redis 故障降级到数据库计算。提问、RAG、SQL 执行前、保存/发送结果前、历史恢复、SQL 查看和导出都检查当前权限与生效时间。执行途中权限收紧或无法确认一致性时停止并提示重新提问，不返回先前按较宽权限执行的结果。

历史结果依然要求本人归属与当前授权，并校验原执行记录范围；授权变窄后不能直接回放旧结果。不能证明旧结果仍安全时显示“权限已变化，请重新查询”，不把新行条件简单套到已聚合结果上。

后台查看业务审计不自动获得他人的原始结果或完整 SQL；内部安全日志与面向管理员的安全展示分开控制。批量、按 ID 详情、统计和导出都应用同一资源范围，不能只过滤列表。

## 15. 替换顺序：先验收新权限，最后删除旧权限

| 阶段 | 做什么 | 通过条件 |
|---|---|---|
| B0 设计与消费清单 | 冻结中文功能/依赖/模板，核对路由、Tab、按钮、全部 API 和资源边界，冻结新旧技术隔离、新契约、管理员初始化与 B6 删除对象 | 提交并评审 B0 清单；每项有真实消费；无遗漏的审批/详情/批量入口 |
| B1 新配置基础 | 建立与旧权限事实隔离的固定目录、用户/角色/部门关系、按角色绑定的负责源及新存储 | 旧关系/旧 JWT/旧缓存无法授予新权限；默认拒绝、角色依赖与防本人修改测试通过 |
| B2 授权与计算 | 统一表列/记录授权、字段保护、部门继承、权限预览、Redis 失效 | 合并、禁止、字段记录关联及到期测试通过 |
| B3 安全查询链路 | Java/Python 契约、RAG、AST、来源追踪、响应保护、历史/SQL/导出复查 | 未授权资源与原值无法进入模型/结果 |
| B4 页面和业务接入 | 前后端成对改造组织、授权、审批与业务工作区；完成新体系审批 | 路由/Tab/按钮/直接 API 都使用新语义 |
| B5 初始化与切换验收 | 独立验收环境配置新模板/角色绑定/数据授权，显式初始化首个新系统管理员，完成真实服务及浏览器验收；维护窗口切换正式运行 | 管理员新绑定及管理链路已验证；新系统全链路通过；切换后再次核对账号、资源、权限和查询 |
| B6 旧权限清理 | 按 B0 已评审删除清单，在正式新体系确认正常后删除旧配置、算法、接口、前端入口、旧码测试和兼容分支 | 旧表/字段/类/端点/缓存键/前端入口无运行引用；清理后全链路回归通过 |

B0 必须在仓库中提交 `docs/development/轨道B-B0权限清单与决策冻结.md`，未提交、未评审或仍保留会影响授权边界的待定项时，不进入 B1。该清单至少包含：

1. 新固定功能目录每个代码对应的页面路由、工作区、Tab、按钮、API 方法+路径、Controller/Service 强制点、数据源负责范围和详情/批量/统计/导出覆盖。
2. IAM-SIMPLE-1 的新存储隔离方案、协议版本、Java/Python 字段契约、缺失/未知版本默认拒绝规则、新 JWT 发放与旧会话作废规则。
3. 首个新系统管理员的选定、一次性绑定、审计、入口关闭和验收方式。
4. B6 旧权限删除清单：旧表/字段/索引与旧关联数据、Resolver/Calculator/Mapper/DTO/接口、Controller 权限表达式、前端路由/守卫/Tab/按钮、旧 JWT claim 结构与解析路径、旧缓存键、测试和兼容分支；每项标注“B1～B4 替代物、B6 删除时机、是否保留历史审计”。
5. 保留清单：账号/密码、真实部门、数据源、元数据、知识、会话、业务审计和 Flyway 历史，防止 B6 误删非权限业务数据。

B1～B4 可以分步开发，但正式新请求从 B5 起只走新体系；不进行旧授权映射/回填、双读双写、影子对账或以旧算法兜底。切换前旧环境继续用旧体系，新环境以新配置验收，不允许一次请求混用。

新角色/关系与数据范围由管理员重新确认初始化，不按旧角色名猜测。保留账号、密码、主部门及真实组织、业务资产、会话与审计；权限变更审计保留为历史证据，不参与新计算。账号与组织保留不等于旧角色成员关系继续授权。

新增前向数据库升级文件；已执行的 Flyway 文件不改写或删除。清理升级与初始化升级分开，不能让普通启动自动执行 B6。实施时分配当时可用的迁移编号，不预占目前后续计划使用的 V53。

切换准备包括必要的数据库备份、配置清单、维护窗口和停止接收/排空旧查询任务；作废旧登录会话与权限缓存。新配置缺失时拒绝问数并显示补配入口，不能临时开全库。B5 失败时停止新入口，在旧权限尚未删除的前提下通过受控维护操作回退整套旧环境。这是部署/入口级回退，不是请求级权限兜底；回退时不让新请求自动调用旧 Resolver，旧环境也不读取未正式切换的新权限配置。

只有 B5 切换后的真实复验通过，才能执行 B6；删除旧表/配置前输出明确对象清单并确认没有误删基础数据。真实数据库切换/清理是后续具体实施动作，本次文档修改不执行。

## 16. 必须通过的验收例子

| 场景 | 应有行为 |
|---|---|
| 无角色，或有问数功能但无数据授权 | 前者只能登录/维护本人资料；后者可以申请但不能查 |
| 销售部 + 普通问数用户 | 自动使用有效部门数据，无须再配个人查询权 |
| 父部门仅本部门/含下级、禁用路径、调部门 | 继承严格按选项与当前有效路径；调部门不复制旧授权 |
| 维护/审核/发布依赖与 SQL/导出 | 后端自动包含必要查看；发布不自动带审核；数据授权不能附送结果功能 |
| 治理角色负责销售库、审计角色负责人事库 | 不能在人事库使用销售库治理能力；详情/批量同样受限 |
| 部门华东 + 个人华南；不同字段与记录分别获权 | 相同字段可扩大记录；不同字段不能交叉扩大记录 |
| 任一禁止、未选字段、新增字段 | 禁止优先；空字段拒绝；新增资源未重授时不可查询 |
| 草稿、阻断、废弃资源 | 获准后台人员可修复；问数/RAG/审批仍拒绝 |
| 脱敏字段用于 WHERE/JOIN/排序/表达式 | AST 拒绝；直接投影与别名、图表、错误、SQL、导出不泄露原值 |
| 本人改角色/部门/负责源/持有角色定义/组授权 | 服务端拒绝；角色成员等其他入口不能绕过 |
| 删除最后管理员或通过模板冒充管理员 | 服务端拒绝；系统管理员问数仍需数据授权 |
| 本人审批、超申请范围、明确禁止字段 | 拒绝；合法审批生成可追溯临时授权，不附送导出/SQL |
| 执行中撤权/到期、Redis 故障、部门路径损坏 | 到期不依赖清理任务；不能确认时停止；缓存故障回源且不放宽 |
| 历史恢复、本人结果归属、权限收紧后导出 | 重新校验；不能证明结果安全时要求重新查询 |
| 角色配置首次使用 | 首屏先给模板和中文能力摘要；自定义每个选项都有具体作用，不先展示全部技术码 |
| 数据授权首次使用 | 常规授权只选对象、数据源、表字段；按需展开记录/时限；无重复查询/SQL/导出开关，无任意码 CRUD |
| 新增销售员工、部门尚未授权 | 选部门与角色即可使用既有默认数据；无默认数据时明确提示暂无可查数据，不假装授权完成 |
| B5 切换与 B6 清理 | 新体系先通过真实验收；旧运行权限再删除；基础数据/审计保留 |
| 旧用户仍有同名旧权限码、旧角色关系、旧 JWT 或旧缓存 | 没有 IAM-SIMPLE-1 新关系时全部拒绝；不映射、不继承、不回退旧算法 |
| 首个新系统管理员初始化 | 显式选定保留账号并建立新绑定；不根据旧 `ADMIN` / `*` / 角色 ID 继承；初始化后关闭一次性入口 |
| B0 准入 | B0 清单已入库并评审，新旧隔离、全部消费点、管理员初始化和 B6 删除/保留对象无影响授权边界的待定项 |

Java/Python 对计算、生命周期、SQL 安全和公开接口使用聚焦测试；浏览器截图保存在 `output/playwright/`，验证每项实际可见的权限流程。代码、自动化测试、真实接口、浏览器分别记录证据，最终进度只回写 `DataOcean后台重构状态与整改计划.md`，执行队列只在 `后续开发.md` 维护。
