# DataOcean 前端菜单与信息架构梳理任务

## 1. 任务背景

DataOcean 是一个面向企业场景的「智能问数 + 数据治理」平台。

当前项目已经包含或规划包含以下能力：

- 数据源接入
- 元数据采集
- 元数据治理
- 业务语义治理
- Schema RAG
- NL2SQL 智能问数
- SQL 校验与安全执行
- 用户 / 角色 / 部门
- 数据权限
- 数据脱敏
- 审计
- 指标管理
- 数据发布

目前的问题不是单个页面不好看，而是：

> 现有前端菜单、页面职责、业务流程和数据生命周期之间的关系比较混乱。

尤其一个数据源从“创建”到“最终允许被智能问数”需要经历多个阶段，如果仅按照传统 CRUD 后台的方式组织菜单，会导致：

- 数据源页面承担过多职责
- 数据治理与数据资产边界不清
- 权限配置不知道应该放在哪里
- 发布 / 上线状态不清晰
- 智能问数与治理流程割裂
- 相同功能可能出现在多个菜单
- 后续权限码难以设计

因此，本任务的目标是：

> 基于当前 DataOcean 项目的真实代码、页面、接口和业务能力，重新梳理最终的前端信息架构与菜单体系。

# 5. 菜单设计原则

最终菜单需要满足以下原则。

## 原则一：围绕用户任务，而不是数据库表

不要因为后端有：

```text
sys_user
sys_role
metadata_table
```

前端就机械对应出同名菜单。

菜单应该围绕用户真正要完成的任务设计。

---

## 原则二：一个页面只承担明确职责

避免：

> 数据源详情页同时负责连接、元数据、治理、权限、发布、问数。

如果一个页面包含完整生命周期，应通过明确的详情页分区、Tab 或工作流表达，而不是把所有东西混在一起。

---

## 原则三：区分“资产”和“治理”

简单理解：

```text
数据资产
=
我有哪些数据

数据治理
=
这些数据是什么意思、是否可信、是否可用
```

---

## 原则四：区分“治理”和“权限”

```text
治理
=
定义数据

权限
=
定义谁能使用数据
```

两者需要关联，但职责不能混在一起。

---

## 原则五：智能问数是消费端

完整关系应该更接近：

```text
数据接入
↓
数据资产
↓
数据治理
↓
权限控制
↓
发布
↓
智能问数
```

智能问数消费治理后的、已发布的、当前用户有权限的数据。

# 7. 权限系统对菜单设计的约束

最终菜单规划需要为以下权限模型预留空间：

```text
User
├── Role
├── Department
└── User Data Grant
```

其中：

```text
Role
→ Function Permission

Department
→ 默认 Data Permission

Role
→ 可选 Data Permission

User
→ 特殊 Data Permission
```

Data Permission 最终需要支持：

```text
DataSource
Database
Schema
Table
Column
Metric
```

以及：

```text
Row Policy
Mask Policy
```

因此菜单设计时必须提前考虑：

- 用户管理
- 角色管理
- 部门管理
- 功能权限
- 数据权限
- 行级策略
- 脱敏策略
- 权限申请
- 权限审批
- 审计

但不要为了权限模型强行创建过多一级菜单。

# 8. 与智能问数的关系

最终产品结构必须体现：

```text
数据治理
↓
PUBLISHED
↓
数据权限过滤
↓
Schema RAG
↓
NL2SQL
↓
SQL Validator
↓
SQL Executor
```

无权限或未发布的数据：

```text
不能进入正式智能问数范围
```

因此前端必须能够让用户清楚看到：

- 当前数据是否已经治理
- 当前数据是否已经发布
- 是否已经进入知识库
- 当前权限配置情况
- 是否允许智能问数
- 如果不能问，具体缺少哪个步骤

# 10. 最终目标

最终希望 DataOcean 的产品逻辑能够清晰表达为：

```text
接入数据
↓
认识数据
↓
治理数据
↓
控制数据
↓
发布数据
↓
使用数据
↓
审计数据
```

菜单和页面应该服务于这条主线，而不是把技术模块简单堆到左侧导航栏。
