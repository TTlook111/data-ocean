# DataOcean 后台前端整体重构任务与实施指导

## 1. 文档定位

本文是 DataOcean 后台前端整体重构的主任务文档，用于统一后续的业务盘点、信息架构设计、页面设计、前端实施和验收标准。

本次任务不再限定为“调整现有菜单”或“在现有页面上进行小范围优化”，而是以后端现有业务能力和接口为事实基础，重新设计整个后台前端。

允许重新设计或替换：

- 后台一级菜单和二级导航。
- 页面归属和工作区边界。
- 页面布局、交互结构和视觉层级。
- 列表页、详情页、步骤页、Tab、Drawer 和对话框的使用方式。
- 前端路由和 URL。
- 前端组件拆分方式。
- 页面之间的跳转关系和业务流程引导。
- 现有后台前端代码，只要新方案能够提供更合理的使用体验。

本次任务不以“减少代码改动量”为目标。前端改动规模不作为否决设计方案的理由。

## 2. 核心目标

本次重构需要解决的不是单纯的菜单命名问题，而是后台功能分散、页面关系不清晰、业务状态难以理解、用户不知道下一步应该做什么的问题。

最终后台应达到以下目标：

1. 每项功能位于符合业务认知的位置。
2. 菜单表达用户任务，而不是简单平铺后端对象或技术模块。
3. 用户能够理解当前所在业务阶段、当前状态和阻断原因。
4. 页面能够给出清晰的主要操作和下一步入口。
5. 同一业务对象的列表、详情、审核、版本和记录形成连续流程。
6. 数据源、快照、知识文档等上下文不会互相污染。
7. 用户不需要反复返回菜单寻找后续页面。
8. 后端已经具备但当前前端没有合理承载的能力，应被识别并纳入设计。
9. 后台信息架构稳定后，再据此规划新的权限系统。

## 3. 本次重构的事实基础

### 3.1 后端是业务能力的事实来源

新前端必须从实际后端代码和接口出发设计，不能只根据当前前端页面反推业务能力。

盘点时以以下内容为准：

- Java Controller 及其公开 API。
- 请求 DTO、查询对象和响应 VO。
- Service 中的业务校验、状态流转和前置条件。
- 数据库实体和状态字段。
- 当前权限注解和后端权限判断。
- Java 调用 Python 的内部服务边界。
- 已实现的通知、审计、任务状态和就绪度接口。

当前前端仅作为以下证据：

- 已经存在的交互和页面能力。
- 当前使用体验中的问题。
- 可复用组件和样式资产。
- 接口调用示例。

当前前端页面结构、菜单和 URL 不作为新设计的强制约束。

### 3.2 后端业务边界保持不变

本轮重点是后台前端整体重构，不主动改变以下后端边界：

- Java 负责用户、权限、数据源、元数据、治理、审核、版本、发布、任务状态、脱敏、审计和持久化。
- Python 负责 AI、RAG、切分、向量化、检索、SQL 生成与校验、沙箱执行和图表生成。
- 前端只调用 Java 公共 API。
- 安全校验不能只依赖前端。
- 后端状态机和业务约束不能为了页面展示被前端擅自改写。

如果盘点发现现有接口无法支持必要的页面体验，应单独记录接口缺口，不得用虚假前端状态掩盖。

## 4. 目标业务主流程

后台整体设计应围绕以下主流程展开：

```text
创建数据源
→ 配置并验证连接
→ 发起元数据采集
→ 查看采集任务和结果
→ 检查元数据快照
→ 发现并处理治理问题
→ 审核并发布快照
→ 生成语义知识
→ 编辑和审核语义知识
→ 切分、索引并发布知识
→ 配置数据访问范围和策略
→ 检查可问数就绪度
→ 进入智能问数
→ 查看查询审计、反馈、性能和血缘
→ 将反馈重新用于治理和语义优化
```

该流程不是要求把所有能力放在一个页面，而是要求页面之间具备清晰关系、状态说明和下一步入口。

## 5. 页面设计的统一问题

设计每个工作区和页面时，必须回答以下问题：

1. 哪类用户会进入这里？
2. 用户进入页面是为了完成什么任务？
3. 页面对应哪个业务对象或生命周期阶段？
4. 用户进入页面后最先需要看到什么？
5. 当前状态是什么？
6. 当前是否存在阻断？
7. 阻断原因和责任角色是什么？
8. 当前主要操作是什么？
9. 完成当前操作后，下一步是什么？
10. 下一步应在当前页面、详情页、Tab、Drawer 还是另一个工作区完成？
11. 用户如何返回上一步或业务对象总览？
12. 页面刷新、浏览器前进后退和直接访问 URL 时，状态能否恢复？
13. 登录失效、后端拒绝或业务状态不允许时，页面和操作应该如何表现？
14. 空状态、错误状态、加载状态和部分成功状态如何表达？

不能回答这些问题的页面，不应直接进入实施阶段。

## 6. 后端接口与能力盘点要求

### 6.1 盘点范围

必须完整盘点以下业务域：

| 业务域 | 重点能力 |
| --- | --- |
| 工作台与就绪度 | 统计、待办、阻断原因、可问数状态、快捷处理入口 |
| 数据源 | 创建、编辑、连接测试、启停、健康检查、删除和详情 |
| 采集与同步 | 手动同步、同步任务、调度策略、进度、失败原因和重试 |
| 元数据与目录 | 快照、表、字段、关系、搜索、详情和影响分析 |
| 版本与发布 | 快照检查、审核、发布、撤回、版本历史和差异比较 |
| 数据治理 | 质量检查、问题处理、治理状态、评分、趋势和事件 |
| 分类与可信度 | 分类、标签、自动标记、字段可信度和反馈审核 |
| 业务术语 | 术语、同义词、审核、状态和查询改写使用范围 |
| 语义知识 | 生成、编辑、审核、版本、发布、回滚、切分、索引和任务状态 |
| Prompt | 模板、版本、审核通过后生效和回滚；当前没有独立发布状态 |
| 权限 | 数据源授权、表列范围、行过滤、脱敏、策略优先级和有效期 |
| 访问审批 | 申请、审核、临时授权、到期和审计记录 |
| 组织管理 | 用户、角色、部门、成员关系和角色授权 |
| 运营与审计 | 查询审计、慢查询、操作日志、血缘和通知 |
| 平台运行 | 服务健康、任务状态、系统配置和 AI 配置 |

### 6.2 接口台账字段

每个接口至少记录：

| 字段 | 说明 |
| --- | --- |
| 业务域 | 接口所属业务领域 |
| 用户任务 | 用户通过该接口完成什么任务 |
| 方法与 URL | HTTP 方法和实际路径 |
| Controller | 后端代码位置 |
| 权限码 | 当前后端要求的权限 |
| 请求参数 | 路径、查询和请求体参数 |
| 返回结构 | 关键字段、分页结构和状态字段 |
| 前置条件 | 调用前必须满足的业务条件 |
| 状态变化 | 调用成功后哪些状态发生变化 |
| 失败条件 | 主要错误和阻断原因 |
| 上一步 | 用户通常从哪里进入 |
| 下一步 | 操作完成后应进入哪里 |
| 当前前端入口 | 是否已有页面或按钮 |
| 设计结论 | 保留、重组、新建页面或暂不承载 |

### 6.3 接口盘点输出要求

盘点结果必须区分：

- 后端已经完整实现且可直接用于新前端的能力。
- 后端接口存在，但当前前端没有入口的能力。
- 当前前端存在展示，但后端能力不完整的内容。
- 只有规划或文档描述、实际代码尚未实现的内容。
- 需要真实环境才能验证的接口。

不得把接口存在等同于运行态已经验证，也不得把页面存在等同于业务闭环已经完成。

## 7. 信息架构设计原则

### 7.1 菜单表达长期稳定的业务域

一级菜单只承载长期稳定且包含多个用户任务的业务域，不直接平铺表、字段、快照、角色等对象。

菜单数量在早期盘点阶段不预先锁定；当前盘点和方案设计已经完成，本轮开发以《DataOcean 后台前端整体重构开发指导》中冻结的七个一级业务域为准。发现后端事实冲突时，应先修订生效文档并记录依据，不能由开发人员临时恢复旧菜单。

### 7.2 工作区表达用户任务

二级导航用于切换相对独立的用户任务，例如：

- 接入和管理数据源。
- 浏览和理解数据资产。
- 处理治理问题。
- 管理语义知识。
- 配置访问策略。
- 查看审计和运行状态。

列表、版本、审核、差异等技术页面不应因为已经存在路由就自动成为稳定二级入口。

### 7.3 对象详情承载连续操作

同一业务对象的概览、配置、状态、审核、版本和记录优先在对象详情流程中组织。

详情页可以使用：

- Tab：同一对象的不同信息维度。
- 步骤条：有明确先后顺序的流程。
- Drawer：不打断主任务的快速查看或编辑。
- 独立详情页：信息密度高或需要可分享 URL 的对象。
- 页面内行动卡片：提示阻断原因和下一步。

不能为了减少路由数量，把无关任务机械塞入同一个 Tab 页面。

### 7.4 下一步引导是必要能力

关键页面必须提供下一步引导，至少包括：

- 当前生命周期阶段。
- 已完成步骤。
- 首个阻断原因。
- 责任角色。
- 推荐处理动作。
- 可直接跳转的目标页面。

例如：

```text
当前状态：元数据已采集，但存在 2 个高等级治理问题
阻断结果：暂不能发布快照
责任角色：数据治理人员
下一步：处理治理问题
[进入问题处理]
```

### 7.5 前端上下文必须有唯一事实来源

数据源、快照、知识文档等上下文必须由统一状态或路由对象决定。

禁止出现：

- 顶部数据源与页面实际请求数据源不一致。
- 切换数据源后保留旧快照。
- 详情页可以通过全局选择器切换到另一个对象。
- 页面刷新后恢复到错误的数据源或对象。
- 一个页面同时存在两个互不联动的数据源选择器。

## 8. 路由与 URL 设计原则

### 8.1 URL 可以重新设计

本轮不要求无条件保留所有现有 URL。新 URL 应优先表达业务任务和对象关系。

信息架构设计已经完成，最终目标 URL 以《DataOcean 后台前端整体重构开发指导》和《DataOcean 后台前端整体重构实施任务清单》中的冻结路由表为准。开发过程中不得另起一套路由命名；确因对象标识或接口事实无法实现时，先更新文档再修改方案。

### 8.2 旧 URL 的处理方式

每个旧 URL 应根据实际需要选择一种状态：

| 状态 | 说明 |
| --- | --- |
| 保留 | 新设计仍然需要该独立页面 |
| 重定向 | 存在书签、外部跳转或兼容价值，应跳转到新位置 |
| 合并 | 能力进入新的工作区、对象详情或 Tab |
| 废弃 | 没有兼容价值且新前端不再使用 |

旧 URL 不是默认必须保留。重定向也不能在目标页面尚未具备原能力时提前启用。

### 8.3 URL 应支持状态恢复

需要刷新和分享的页面状态应进入 URL，例如：

- 当前对象 ID。
- 当前 Tab。
- 必要的数据源或快照 ID。
- 对业务定位有意义的筛选条件。

纯视觉状态和短期交互状态不应全部写入 URL。

## 9. 页面布局指导

后台页面建议使用一致的任务结构：

```text
页面标题和任务说明
→ 当前对象或业务范围
→ 状态、就绪度或关键指标
→ 主要操作与下一步
→ 核心内容区
→ 历史、审计或辅助信息
```

页面应明确区分：

- 主操作与次要操作。
- 当前状态与历史状态。
- 业务结果与技术日志。
- 可执行动作与只读信息。
- 正常状态、警告状态和阻断状态。

不应把所有操作都放在同一排按钮中，也不应要求用户仅凭状态码判断下一步。

## 10. 权限系统的当前处理方式

### 10.1 本轮不重新设计权限模型

后台前端整体重构期间：

- 开发和验收统一使用真实拥有 `*` 权限的超级管理员账号。
- 后台全部菜单、工作区、Tab 和操作默认可见，不实施复杂的前端权限组合过滤。
- 写操作仍然依赖后端现有权限、安全校验和业务状态机，不能在前端伪造 `*` 权限或绕过接口校验。
- 本轮保留授权管理、访问审批、用户、角色、部门和权限项等已有业务页面，但不据此设计新的权限模型。
- 不因为当前权限粒度不理想而降低页面设计质量。

### 10.2 新权限系统后置规划

在新的业务域、工作区和用户任务稳定后，再规划：

- 菜单访问权限。
- 页面查看权限。
- 操作权限。
- 数据范围权限。
- 审批权限。
- 运维和配置权限。
- 角色模板和职责边界。

新的权限系统应适配最终信息架构，而不是让最终信息架构迁就当前前端页面和权限名称。

本轮完成后，再补充普通管理员、审核人员、只读人员等角色下的菜单、页面、Tab 和操作权限验收；这些不属于本轮前端整体重构的完成条件。

## 11. 当前代码处理原则

### 11.1 不立即回退

当前 V1 修改暂不删除、不执行整体回退，原因如下：

- 可作为现状和目标方案的对照。
- 路由元数据、上下文管理、菜单归类和面包屑中可能存在可复用实现。
- 在新设计确定前无法准确判断哪些代码应保留、替换或删除。
- 直接回退会丢失已经完成的分析和验证证据。

### 11.2 不把 V1 当作新方案约束

后续可以：

- 保留合适的通用组件。
- 重写 `AppShell.vue`。
- 重新定义菜单数据结构。
- 重新设计路由。
- 合并、拆分或删除现有页面组件。
- 新建完整工作区和对象详情页。
- 替换当前上下文条和页面布局。

是否复用现有代码，只根据最终方案和维护成本判断。

### 11.3 新设计确认后再处理旧代码

新方案确认后，建立“旧页面到新页面”的迁移矩阵，再逐项决定：

```text
保留复用
部分改造
能力迁移后删除
旧 URL 重定向
完全废弃
```

不得在迁移目标尚未实现前删除原有功能。

## 12. 实施阶段

### 阶段一：后端接口与业务能力盘点

1. 扫描全部后台 Controller。
2. 按业务域整理公共 API。
3. 检查 DTO、VO、状态枚举和后端现有权限事实；本轮统一由 `*` 账号满足权限。
4. 追踪关键 Service 的业务前置条件和状态变化。
5. 对照当前前端 API 调用和页面入口。
6. 输出完整能力台账和前端缺口。

阶段交付物：

- 《DataOcean 后端接口与业务能力盘点》

### 阶段二：业务流程与用户任务设计

1. 确定主要后台用户类型和职责。
2. 梳理数据源接入到可问数的主流程。
3. 梳理治理、知识、权限、审计的反馈闭环。
4. 明确每一步的前置条件、阻断原因和下一步。
5. 输出跨页面用户流程。

阶段交付物：

- 《DataOcean 后台业务流程与用户任务设计》

### 阶段三：信息架构和页面方案

1. 重新确定一级业务域。
2. 确定每个业务域的稳定工作区。
3. 确定对象详情、Tab、步骤页、Drawer 和操作入口。
4. 设计全局壳层、上下文和导航方式。
5. 设计关键页面线框和状态结构。
6. 设计新路由和旧 URL 迁移策略。
7. 形成完整菜单、页面和接口映射。

阶段交付物：

- 《DataOcean 后台信息架构、菜单与页面布局方案》

### 阶段四：前端实施计划

1. 按业务闭环划分实施批次。
2. 明确每批新增、重写、迁移和删除的文件。
3. 明确接口复用和接口缺口。
4. 明确路由迁移时机。
5. 明确测试数据和角色要求。
6. 明确每批回归范围。

阶段交付物：

- 《DataOcean 后台前端整体重构实施指导》

### 阶段五：分批实现

每一批必须形成完整用户任务，不以“完成若干页面文件”为完成标准。

推荐按以下业务闭环分批：

1. 后台壳层、导航和工作台。
2. 数据源接入、连接和就绪度。
3. 采集、目录、快照和发布。
4. 治理、分类、可信度和反馈。
5. 术语、语义知识和 Prompt。
6. 访问控制和组织管理。
7. 审计、血缘、性能和运行状态。
8. 全链路引导、兼容迁移和视觉收敛。

具体顺序应在接口盘点和页面设计完成后调整。

## 13. 每批实施要求

每批前端实施至少完成：

1. 页面结构和主要交互。
2. 真实后端接口接入。
3. 加载、空、错误、登录失效和业务阻断状态。
4. 上一步和下一步入口。
5. URL 刷新和前进后退恢复。
6. 数据源和对象上下文隔离。
7. `*` 超级管理员的全部页面和操作可达性。
8. 前端生产构建。
9. 关键页面截图。
10. 功能迁移清单和未完成项说明。

## 14. 验收标准

### 14.1 信息架构

- 一级菜单表达稳定业务域。
- 二级工作区表达用户任务。
- 每项后端能力都有明确前端归属或明确暂不承载原因。
- 不存在因为历史路由而保留的无意义菜单。
- 页面名称、菜单名称、面包屑和业务术语一致。

### 14.2 业务流程

- 用户能够从创建数据源连续完成到可问数准备。
- 每个关键状态都能看到阻断原因和下一步。
- 治理问题、快照发布和知识发布不会混成一个状态。
- 列表、详情、审核、版本和审计之间具备合理跳转。
- 不要求用户记住隐藏 URL 或反复返回菜单找功能。

### 14.3 页面体验

- 主要操作明确。
- 页面信息层级清晰。
- 空状态能够解释为什么为空以及下一步是什么。
- 错误状态能够给出可恢复动作。
- 对象锁定页面不会被全局上下文错误切换。
- 相同概念在不同页面中使用一致的组件和表达。

### 14.4 技术质量

- 前端构建通过。
- 页面接口与 Java 实际协议一致。
- 不绕过后端权限和业务校验。
- URL 可以刷新、分享和恢复必要状态。
- 跨数据源不会残留旧快照、知识文档或筛选条件。
- 旧功能迁移后没有能力丢失。
- 浏览器控制台没有新增运行时错误。
