# DataOcean 技术栈与模块职责

> 本文档是 DataOcean 当前实现的技术栈、模块职责、数据归属和异步边界的详细说明。
> 文档类型：现行架构说明；核对日期：2026-10-17；代码基线：`619bca6`。本轮静态核对，未重跑业务验收。版本号以 `frontend/package.json`、`backend/DataOcean/pom.xml` 和 `python-service/pyproject.toml` 为准；阶段验收结果见 [问数验收记录](acceptance/LangGraph问数与会话记忆验收记录.md)。

## 1. 文档定位

本文档回答三个问题：

1. 项目使用了哪些技术。
2. 每项技术参与哪些模块，以及它负责什么、不负责什么。
3. 哪些流程应该异步，哪些流程必须等待结果。

`README.md` 只保留快速概览；`AGENTS.md` 和 `CLAUDE.md` 记录协作约束与稳定架构事实；项目完成度、验证范围和已知限制以 [项目现状](项目现状.md) 为准；模块级接口和数据模型从[当前模块说明](modules/README.md)进入；原始 specs 按[适用性索引](../specs/README.md)核对，不能直接作为当前完整契约。

本项目不引入 Google ADK，也不通过 API Gateway 平台转发模型请求。Java 负责业务网关和持久化，Python 负责 AI/RAG 执行，模型通过外部 OpenAI 兼容 API（当前为 Qwen/通义千问配置）调用。

## 2. 总体架构

```text
Vue 3 前端
  ├─ 查询端：提问、任务状态、SSE 结果、会话恢复
  └─ 管理端：数据源、元数据治理、语义、权限、运营与系统设置
          │ 只调用 Java 公共 API
          ▼
Spring Boot Java 网关
  ├─ 认证、权限、数据源和治理生命周期
  ├─ 查询任务、会话消息、长期摘要和审计持久化
  └─ 通过 RestClient 调用 Python 内部 API
          │ 内部 HTTP / SSE
          ▼
Python FastAPI AI 服务
  ├─ iam_s1/graph.py：有预算的 LangGraph 问数工作流
  ├─ LangChain 模型、Prompt、工具和输出解析
  ├─ Schema RAG、Embedding、Milvus 检索与重排
  └─ sqlglot 校验、权限改写和只读 SQL Sandbox
          │
          ├─ 外部 Qwen/OpenAI 兼容 API：LLM 与 Embedding
          ├─ Milvus：可重建的向量索引
          └─ 外部业务 MySQL：只读查询执行
```

会话数据的边界如下：

```text
Java MySQL：conversation、conversation_message、conversation_context_summary
        │ 每次查询组装
        ▼
Python：Java 提供的 conversationId/threadId、最近 5 轮、较早摘要和当前请求
        │ Redis 8 checkpoint 仅保存可恢复的安全图状态
        └─ 不以 Redis 保存完整聊天历史；MySQL 仍是会话事实源
```

## 3. 技术栈与职责矩阵

#### Java 对象目录与分页查询

各模块的 `entity` 按职责分为四类，枚举放在模块的 `enums` 包：

| 目录 | 职责与命名 | 当前示例 |
| --- | --- | --- |
| `entity.po` | 数据库实体及 Mapper 持久化投影 | [SysUser](../backend/DataOcean/src/main/java/com/dataocean/module/user/entity/po/SysUser.java) |
| `entity.dto` | 写入请求、业务动作及跨服务传输对象，使用 `*DTO` | [UserCreateDTO](../backend/DataOcean/src/main/java/com/dataocean/module/user/entity/dto/UserCreateDTO.java) |
| `entity.query` | 列表筛选与分页查询条件，使用 `*Query` | [UserQuery](../backend/DataOcean/src/main/java/com/dataocean/module/user/entity/query/UserQuery.java) |
| `entity.vo` | 响应与展示对象，使用 `*VO` | [UserVO](../backend/DataOcean/src/main/java/com/dataocean/module/user/entity/vo/UserVO.java) |

`PageQuery` 是公共分页基类；`UserQuery` 等业务查询对象继承它，并增加自己的筛选条件。问数模块中的提问等业务动作仍使用 DTO，不因类名含有 Query 就归入查询条件目录。原审计、操作日志查询 DTO 已分别改为 `entity.query.AuditLogQuery`、`entity.query.OperationLogQuery`；不再使用 `AuditLogQueryDTO`、`OperationLogQueryDTO` 或公共 `PageRequest`。

分页查询条件继承 [PageQuery](../backend/DataOcean/src/main/java/com/dataocean/common/entity/query/PageQuery.java)，业务类只定义筛选条件与排序字段白名单。标准参数为 `pageNo/pageSize/sortBy/isAsc`，兼容既有 `page/pageNum`，页码优先级为 `pageNo > page > pageNum`；默认第 1 页、每页 20 条，单页最多 100 条，无效页码/大小使用默认值，偏移量溢出时拒绝请求。使用 `toMpPage()` 或提供默认排序的重载转换为 MyBatis-Plus `Page`；当前表的创建时间列为 `created_at`。

客户端排序字段必须映射到业务查询类定义的固定列名，不将请求中的 `sortBy` 直接作为 SQL 列名；非白名单字段返回业务错误 400。显式 `OrderItem` 和默认排序列仅由后端代码提供。分页拦截器仍在乐观锁之后执行，`mybatis-plus-jsqlparser` 与主包共用版本属性，不因目录整理升级依赖。

当前继承公共分页基类的业务查询对象如下。它们在未指定排序时均按 `created_at` 降序；`createdAt` 与 `created_at` 都映射到该固定列。指定白名单字段后，`isAsc` 决定方向，未传时为升序。

| 查询对象 | 接受的 `sortBy` |
| --- | --- |
| [UserQuery](../backend/DataOcean/src/main/java/com/dataocean/module/user/entity/query/UserQuery.java) | `id`、`username`、`realName`、`status`、`createdAt`、`created_at` |
| [DatasourceQuery](../backend/DataOcean/src/main/java/com/dataocean/module/datasource/entity/query/DatasourceQuery.java) | `id`、`name`、`status`、`healthStatus`、`createdAt`、`created_at` |
| [QueryHistoryQuery](../backend/DataOcean/src/main/java/com/dataocean/module/query/entity/query/QueryHistoryQuery.java) | `status`、`createdAt`、`created_at` |
| [AuditLogQuery](../backend/DataOcean/src/main/java/com/dataocean/module/audit/entity/query/AuditLogQuery.java) | `id`、`executionTimeMs`、`createdAt`、`created_at` |
| [OperationLogQuery](../backend/DataOcean/src/main/java/com/dataocean/module/system/entity/query/OperationLogQuery.java) | `id`、`operatorName`、`operationType`、`createdAt`、`created_at` |

Service 使用 `query.toMpPageDefaultSortByCreatedAtDesc()` 构造传给 Mapper 的 `Page`，无需再在条件 Wrapper 中添加同一默认排序。`toMpPage()` 不附加默认排序；`toMpPage("固定列名", false)` 提供后端默认排序；`toMpPage(OrderItem...)` 中后端显式排序优先于客户端排序。新增业务查询时按自己的字段定义白名单，不复制分页字段。

这次统一接入上述五类查询对象；其他散参分页接口继续沿用各自 Controller 的参数约定。改动时按[分页回归说明](development/本地开发与验证.md#java-对象分层与分页回归)验证，当前测试结果和验收限制见[项目现状](项目现状.md#已有验收证据)。

### 3.4 数据与模型基础设施

| 技术/服务 | 当前定位 | 关键模块或数据 | 权威性 |
| --- | --- | --- | --- |
| Java 应用 MySQL | Java 持久化数据库 | 用户、数据源、元数据、权限、任务、会话、消息、摘要、审计、知识切片 | 业务事实和会话事实的权威源 |
| 外部业务 MySQL | 被查询的数据源 | 业务表和业务数据 | 查询结果的外部数据源；必须只读 |
| Redis 8（含 RedisJSON/RediSearch） | 缓存与 LangGraph checkpoint | JWT、验证码、限频、Embedding/Fallback 缓存和 S1 安全图状态 | 缓存故障可降级；S1 checkpoint 不可用时拒绝启动问数；不是完整会话事实源 |
| Milvus | RAG 向量索引 | 经确认的 buildId 专属活动 collection | 可重建的派生索引，不是权威源；默认 `schema_knowledge` 来源未核验，不作为 S1 活动集合 |
| Qwen/外部 OpenAI 兼容 API | 模型服务 | 查询改写、SQL 生成、摘要、Embedding、图表等模型调用 | 只提供推理结果，不保存项目业务状态 |

RAG 的数据归属进一步明确为：Python 负责语义切分、Embedding、Milvus 写入/检索/重排和
相邻上下文扩展；Java 负责 `knowledge_chunk` 的完整 chunk 快照、审核、版本和发布状态。
Milvus 中的 metadata 是用于过滤和扩展的轻量副本，不替代 Java MySQL 的权威数据。

## 4. LangChain 与 LangGraph 的边界

两者不是同一个职责：

1. LangChain 是“组件层”：模型客户端、Prompt、工具、Document、Embedding、输出解析器和 Agent 构建能力都属于这一层。
2. LangGraph 是“流程层”：把改写、元数据预取、RAG、SQL 生成、校验、执行和图表生成组织成有状态的节点图。
3. LangGraph 的图状态以用户、数据源和会话绑定 threadId，由 Redis 8 保存安全 checkpoint；它不是完整聊天历史。
4. 长期会话仍由 Java 写入 MySQL；Python 接受 Java 组装的最近轮次、摘要和会话标识，用于受控恢复。

## 5. 异步边界

### 5.1 三种不同含义

| 类型 | 含义 | 当前例子 | 是否需要等待 |
| --- | --- | --- | --- |
| 异步 I/O | 调用期间不阻塞事件循环，但业务仍依赖结果 | `await chat.ainvoke()`、异步 Redis | 需要 |
| 线程卸载 | 把同步阻塞库放到线程执行，保护事件循环 | `asyncio.to_thread()` 执行 SQL、Milvus | 需要 |
| 后台任务 | 调用方先返回，任务稍后执行 | Java `@Async`、Python `create_task` | 不需要，但必须允许失败或重试 |

### 5.2 当前正确的异步位置

| 流程 | 当前实现 | 判断 |
| --- | --- | --- |
| 用户提问后的 Agent 执行 | Java `queryExecutor` + Python `create_task` + LangGraph | 正确，前端通过任务 ID/SSE 获取结果 |
| 会话长期摘要 | 助手消息落库后调用 `conversationSummaryExecutor` | 正确，摘要失败不影响本次查询 |
| 元数据全量同步 | Java 同步任务表 + 未指定执行器的 `@Async`，使用默认 `taskExecutor` | 返回任务 ID；默认执行器饱和时采用 `CallerRunsPolicy`，采集可能由调用线程执行，不能保证始终快速返回 |
| RAG build 执行 | Java 构建调度器执行，Python 内部等待写入与校验 | 活动指针切换等待校验；文档发布与构建确认独立 |
| SQL、Milvus、健康检查阻塞调用 | Python `asyncio.to_thread()` | 正确，避免阻塞事件循环，但业务仍需等待结果 |
| 审计、操作日志、血缘、通知和快照同步 | Spring 异步事件/服务 | 适合后台执行，但要明确是否允许进程异常时丢失 |
| 清理、健康检查、过期处理 | Spring/Python 定时任务 | 适合后台执行，不属于用户请求链路 |

### 5.3 必须保持等待的流程

以下内容不能简单改成 fire-and-forget：

1. 权限计算、数据源 readiness 和敏感字段策略。
2. 历史消息、摘要、Few-shot 样例、Glossary、Fallback 和 Schema RAG 加载。
3. 查询改写、SQL 生成、AST 校验、权限改写和只读执行。
4. 查询结果、任务状态、用户消息和助手消息的必要持久化。
5. 新 build 向量写入、数量与 manifest 校验。成功后 Java 才能切换活动 build 指针；旧集合还需等待进行中查询引用结束后再清理，失败进入清理待重试状态。知识文档发布不等待或自动触发这一流程。

### 5.4 执行约束

1. DatasourceHealthCheckScheduler 使用 datasourceHealthExecutor，不占用公共 ForkJoinPool；单个源异常不应中断其他检查。该执行器饱和时采用 CallerRunsPolicy，由提交任务的调度调用方执行；这与查询、摘要执行器的拒绝策略不同。
2. conversationSummaryExecutor 满载时跳过摘要，queryExecutor 满载时拒绝新查询；二者都不能回落到请求线程执行整段 LLM 工作。
3. Few-shot 样例由 Java 在组装请求时，从当前用户、当前数据源的已完成任务中读取，并按本次请求的表字段范围筛选；Python 再按绑定快照过滤。Python `rag/fewshot.py` 中保留的 Redis 自学习工具未接入当前 S1 主链，不属于当前后台任务。
4. 构建调度与并发按当前任务状态、幂等和并发上限处理；不能只加线程而忽略指针切换和引用清理。
5. SQL Engine、KILL QUERY、连接池和 Milvus 等同步调用，以及 token-aware 文本处理通过线程卸载保护事件循环。
6. 独立知识域草稿生成使用有上限的 TaskGroup；单域失败取消同批其余调用，避免无效并发。
7. 默认 taskExecutor 也采用 CallerRunsPolicy，元数据采集等未指定执行器的 @Async 方法不具有查询、摘要执行器的同等饱和隔离保证。这里描述现有行为，不代表本轮修改了线程池实现。

## 6. 数据一致性和失败原则

1. Java MySQL 是会话、任务、治理和发布状态的权威来源。
2. 一般 Redis 缓存故障可降级为较慢路径；IAM-SIMPLE-1 LangGraph checkpoint 是安全恢复边界，不可用时问数明确失败，不退回无 checkpoint 的执行路径。
3. Milvus 是派生索引。新 build 向量和 manifest 未验证成功前，不能删除活动或进行中查询引用的集合；Java 切换活动指针后旧集合清理失败应通过 `CLEANUP_PENDING` 重试。
4. 外部模型 API 失败时，查询任务必须进入明确的失败或降级状态，不能把异常吞掉后伪装成成功。
5. 后台副作用如果将来具备审计或合规上的“不能丢失”要求，应采用 MySQL outbox/任务表保证投递；当前项目没有为此额外引入消息平台。
