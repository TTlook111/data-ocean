# 用户反馈与持续改进

本页帮助理解方案第 7 章的职责和衔接，详细规则以[方案原件](../产品方案.docx)为准；不表示模块已经实现。

## 职责与使用者

分流者指定责任，治理或技术处理者核查原因，验证者确认结果。

## 主流程

接收反馈 → 核对与分派 → 补充或处理 → 按影响分级验收 → 结案并回告原提问人。无需修复时可凭依据说明结案。

## 衔接与边界

- 反馈是线索，不能直接改写治理事实或放宽权限；分派任务不授予业务数据访问权。
- 反馈功能统一走已有角色，具体处理按事项与任务分派；建立或调整任务另核分派功能，提交结果核对当前任务负责人。
- 业务数据权限沿用已有数据源授权及输出限制，所有页签、历史与预填共同核对原文证据；分派不授予业务查询权。
- 待我处理按当前可执行动作筛选，我负责的保留等待他人的跟进事项；最近更新不表示当前状态等待时长。
- 误建或无需变更任务可凭依据退出并恢复，未覆盖影响保持未结；全部退出只能其他结案。
- 允许复用当前有效修复，核对原引用与覆盖范围，不为结案制造额外治理修订。
- 技术与源数据任务先记进展，实际完成后再提交修正内容、复查结果及生效确认；现有工单、批次等作补充记录，不强制专业编号。
- 知识、技术影响和源数据修正分别验收；查询安全相关测试仍须通过，进展记录不计解决，人工登记不表示系统已执行测试。
- 用户回告使用受控模板，内部自由结论不直接发送，发送与回看复核当前权限。
- 状态沿用方案统一字典；已解决、其他结案、已合并分别统计。
- 处理结论、验证结果和通知投递分别记录，知识修正需经过治理与发布。
